# GameQueue: working notes

Personal video game collection and "what do I play next" manager. npm workspaces monorepo:
`apps/web` (React + Vite + TanStack Query), `apps/server` (Hono + Drizzle + SQLite), `packages/shared` (Zod schemas/types, consumed as TS source).
Full design (data model, API surface, rationale): `/Users/joe/.claude/plans/floating-exploring-brook.md` (outside the repo; if missing, the sections below plus the code are the source of truth).

## How we work

- Build one milestone at a time. After each: run `npm run typecheck` and `npm test`, make a git commit, give a 3-5 line summary and what to try manually. **Don't start the next milestone until the user says so.**
- If a requirement is ambiguous or needs a product decision, ask instead of guessing. Technical choices inside the stack are mine to make; mention the notable ones.
- Code style is enforced by Prettier (`.prettierrc.json`: 4 spaces, single quotes, semicolons, no trailing commas, width 100). Run `npm run format` before committing; `npm run format:check` verifies.
- Keep `ARCHITECTURE.md` up to date: when a change adds or alters routes, tables, services, auth/session behaviour, IGDB communication or web pages, update the matching section in the same commit.
- `OVERVIEW.md` is the plain-language, diagram-led tour of the subsystems (for learning, not reference). Update it when a subsystem is added or its shape changes; small details belong only in `ARCHITECTURE.md`.
- Commit message footer: follow the attribution line given by the session's system reminder.

## Product decisions (confirmed by the user)

- **Playing:** Home shows every game whose status is `playing` (no cap, each with Pause / Finished / Abandon) and a smaller Paused row beneath it; the public profile's "Currently playing" is the same set. Every start action (game page, queue row, pick result, add dialog's "Playing") is the plain start flow: open a playthrough, set `playing`, remove from the queue, no confirmation (a game on several platforms asks which one in place). The UI says **Not Started** for the stored status `unplayed` (`statusLabel` in shared); "Backlog" stays the name of that view.
- **Backlog:** strictly `unplayed` entries (derived, never stored). Random pick can use it as a source. It is the Not Started tab of the Collection (`/backlog` redirects there), and the Wishlist is a tab of the Collection too (`/wishlist` redirects); neither has a page of its own.
- **Collection page:** status tabs with counts (All, Playing, Paused, Finished, Abandoned, Not Started, Wishlist), a compact filter bar (no side panel), sort (default Recently added; also Title, IGDB score, Release date, My rating, Time to beat) and a Wall / Grid / List density kept per user in `localStorage`. Wall is the default on desktop; touch screens and widths below 768 px get Grid with titles visible. A status is always visible without hovering (chip on Grid cards, 4px bar on the Wall). There is no progress bar: the app has no progress data, and hours are shown only when the journal logged some. No time-to-beat filter (only the sort).
- **Tags:** the user's own, separate from IGDB genres. A new game starts with none (genres and themes are not copied in); new tags are stored trimmed, with spaces collapsed, lowercase; matching stays case-insensitive and an existing tag keeps the spelling it was saved with. Existing tags are not migrated.
- **Ratings:** entry rating is its own field; finishing a rated playthrough pre-fills it only if empty.
- **Playthrough dates may be unknown** (null start/end) so games finished long ago can be logged; stats must skip nulls. Dates are `YYYY-MM-DD`; the web client sends its local date, the server falls back to UTC today.
- **Lists hold any game:** `list_items` is keyed `(list_id, game_id)` (IGDB id), so a list can hold games the user doesn't own; a game's collection entry is found by joining on `(user_id, game_id)`. Items are addressed by IGDB id: `POST /lists/:id/items {igdbId}` (caches the game from IGDB if needed), `DELETE /lists/:id/items/:igdbId`, `PUT /lists/:id/move {igdbId, toIndex}`, `PUT /lists/:id/order {igdbIds}` (must be exactly the list's games). Adding twice is a no-op. `ListDetailDto.items` are `{igdbId, game, entry | null}`; the list page shows each game's status, or "Not in collection". Removing a game from the collection drops it from the queue only; regular lists keep it as a game you no longer own. Counts, stats, backlog, CSV (owned games only) and smart lists ignore unowned items; random pick from a list skips them and says how many (`skippedUnowned`). Export/import carry list games by IGDB id (unknown ones skipped with a note). Public list pages show unowned games without a status. The wishlist uses this table too.
- **Queue:** the user's one ordered "up next" plan, stored as a `lists` row with `kind = 'queue'` (partial unique index per user, created lazily by `ensureQueue`), so ordering, pick and export reuse the list code. Any collection game can be queued whatever its status; a game you don't own is refused (400, "Only games in your collection can go on the queue"). **Starting a game takes it off the queue** (`dequeue` in `startPlaythrough`); pause/resume/finish don't touch it. Starting from the queue is manual: nothing starts a game automatically. It's excluded from `/lists`, from `EntryDto.lists` (see `EntryDto.queued`) and from list-by-name import matching; it can't be renamed or deleted. API: `/api/queue` (`GET`, `POST items`, `DELETE items/:igdbId`, `PUT order`); the generic `/lists/:id` routes work on it too. Export carries it as top-level `queue` (IGDB ids in order), an optional field so it is still format v1; import appends missing games to the end of the existing queue.
- **Wishlist:** games the user wants but doesn't own, as the user's one `wishlist`-kind row in `lists` (partial unique index per user, created lazily by `ensureWishlist`), items in `list_items` keyed by IGDB game id with no entry, so nothing about the collection (backlog, stats, pick) has to know about unowned games. `/api/wishlist` (`GET`, `releasing-soon`, `POST items`, `PATCH|DELETE items/:igdbId`, `PUT move|order`) is a thin wrapper over that list that keeps the wishlist response shape; `/api/lists/:id/...` works on it too, and the owned-game 409 lives in `addToList`. It can't be renamed or deleted and is not in `/api/lists`. Items have a manual order (top = most wanted), an optional target platform and a private note. A game can't be both owned and wishlisted: wishlisting an owned game is a 409 with the `entryId`, and adding it to the collection (UI "Got it" button, search add, or import) removes it from the wishlist. Public like the rest of the profile (`/u/:username/wishlist`, notes excluded). Export carries it as optional top-level `wishlist` (still format v1).
- **Smart lists:** user-defined saved rules (name + AND-ed rules + sort), computed from the collection on every read, never stored per game, collection only (no wishlist), public on the profile (rules in words plus the matching games, never notes). Rules: status/platform/genre/tag/year-finished any-of (year finished = the end year of any finished playthrough, so a replayed game matches each year it was finished; unknown dates never match), or number fields (time to beat, IGDB score, your rating, days since added / last changed / last finished, release year) with at least/at most/unknown. Only AND, no OR groups yet. No manual order (sorted by a chosen field). Five presets (`SMART_LIST_PRESETS`: Quick wins, Hidden gems, Long-neglected, Gathering dust, Replay candidates) are offered as one-click Add on the lists page and create ordinary editable lists; they are not seeded per user. Random pick can use one as a source, with the same status filter as any other source. `changedDays` is based on `entries.updated_at`, so editing a rating or note also resets "gathering dust". Replay candidates uses 4+ stars (ratings are 1-5, not 1-10). Smart lists are in the export file as optional `smartLists` (rules only).
- **Stats:** a private Stats page and a public one (`/u/:username/stats`, linked from the profile), same payload, no notes. Sections: overview, finished per year and last 12 months, platform/genre/tag breakdowns (top 10), rating distribution and top rated, total play time. Play time is the optional hours the user enters per playthrough (finish dialog, past-playthrough log, edit form; `playthroughs.playtime_minutes`), summed over finished playthroughs; finishes without one are skipped and counted as not entered. There is no per-game time-to-beat override any more (removed as confusing); `ttbMinutes` is IGDB's "normally" only.
- **CSV export:** one-way spreadsheet export of a list, the queue, a smart list or the whole collection (`/api/lists/:id/export.csv`, `/api/smart-lists/:id/export.csv`, `/api/data/export.csv`); not importable. UTF-8 BOM, CRLF, formula-like text defused with a leading apostrophe.
- **Random pick:** by default any owned game can be picked, from the whole collection (`collection` source, the default), the backlog (Not Started only), the queue, a list or a smart list. A status filter (`filters.statuses`, any-of, empty = any; replaced `includePaused`) narrows it. Filters: status, platform/tag/genre are any-of within a group and AND across groups; a max time-to-beat excludes games with unknown time. Re-roll sends `excludeEntryIds`; when all were shown it wraps, never repeating the last pick. Pick of three (`count` up to 3) draws distinct games the same way and the user chooses one; nothing starts until they press Start playing. Logic is pure in `packages/shared/src/pick.ts` with an injectable RNG.
- **Import = merge** (decided by the user; no replace mode). Match games by `igdb_id`, lists by name (case-insensitive), playthroughs by platform+dates+outcome. Your existing values win; empty ones are filled; platforms and tags are unioned; playthroughs/list items are added, never removed. An in-progress playthrough is skipped if one is already open; Importing the same file twice changes nothing.
- **Status rules:** start (unplayed/finished/abandoned → playing, opens playthrough), pause, resume, finish/abandon (closes playthrough), log past playthrough. At most one open playthrough per entry (partial unique index).
- **Score gauge** (`apps/web/src/components/ScoreGauge.tsx`, tier logic and geometry in `src/gauge.ts`): 270° arc coloured by tier, 75+ green / 50-74 yellow / below 50 red (Metacritic cut-offs, applied to the percentage so 7.5/10 matches 75/100). The user asked for red/yellow/green; the status colours are tokens in `tokens.css` (`--status-bad|mid|good`, light and dark), picked for >= 3:1 contrast on the page and panel surfaces and checked with the dataviz validator. The validator always fails red vs green under deuteranopia (any red/green pair does), so colour is never the only cue: the score is real text, notches cut into the arc at the 50 and 75 boundaries show the zone by position, and the tier is in `aria-label`/`title`. Animated draw-in respects reduced motion. Props: `value`, `max`, `label`, `size`. Below 64px it drops the visible caption (the `aria-label` keeps it). Used for the IGDB score on the game page and, at 56px, in the add-game search results (`SearchResultDto.igdbRating`, from IGDB's `total_rating`; null when IGDB has no rating); also takes the user's 1-10 rating (`max={10}`).
- **AI:** off without `ANTHROPIC_API_KEY`; each user also needs `users.ai_enabled`, switched on by an admin on the user page (default off, admins included: the budget is shared). One monthly budget for the instance (calendar month UTC, default $5, Admin > AI): warn at 80%, refuse at 100%. The game helper's prompt holds only the asking user's data (IGDB game data, latest journal posts of the open playthrough, notes when the visible toggle is on) plus a no-spoiler instruction. Chats are saved (the user's decision): `ai_chats`, one row per conversation with the messages as JSON, capped at 20 messages / 24,000 characters, at most 5 per game and 50 per user (least recently used dropped), deleted after 90 days unused, with the game or account, or by the user; private, never logged, not in the export file. The server owns the history: the client sends only `chatId` plus the new question, and a turn is saved only once its answer completes. Summaries are drafts saved only by the user's click, as a private note, public note or journal post. The UI says what is sent to Anthropic.
- **Ask AI:** a top-level nav item and page (`/chat`, named "Ask AI" by the user) shown to accounts with AI switched on: the pick-my-next-game chat (suggestions only from the user's own queue and backlog, ids outside that list dropped, never changes anything by itself, not saved) and the list of saved game chats with a search to start one.
- **Journals:** every playthrough has a journal (`playthrough_posts`: `note`, `hours`, `screenshot`, each with a spoiler flag; `post_images`). Only the owner writes, and anyone else's post, image or playthrough is a 404. Started/Finished-or-Abandoned markers come from the playthrough's own dates and outcome (none when unknown); pauses and resumes are not posts. Visibility is per playthrough: `private` (default, 404 for everyone but the owner), `unlisted` (works by link, not on the profile), `public` (also under Journals on the profile). The link is `share_slug`, 128 random bits, minted when first shared and **deleted when set back to private** (so the old link stays dead). The finish dialog (one dialog from the game page and Home) takes date, total time (pre-filled from the sum of hours posts, editable; stored in `playthroughs.playtime_minutes`), rating and final thoughts (`playthroughs.final_thoughts`); abandoning stays the small inline form. Images: JPEG/PNG/WebP in, originals over 8 MB refused, at most 6 per post, re-encoded to WebP at most 1920 px with all metadata dropped, stored as `<sha256>.webp` under `SCREENSHOTS_PATH`; total storage capped by the `screenshot_cap_bytes` setting (default 1 GiB, Admin > Screenshots). Journals never include entry notes, and `/p/:slug` is `noindex` with a generic text-only preview. Not in the export file (out of scope).
- **Notes:** many per game, each private (default) or public. Public notes appear only on `/u/:username/games/:igdbId`, never in tiles, lists, stats, recap, share cards or the feed. Editing a note's text or adding/deleting one counts as touching the game (`changedDays`); flipping visibility doesn't. Import merges by identical text.
- **Public profile:** `GET /api/profiles/:username` (web `/u/:username`) needs no login and is public for everyone: username, join date, the games being played, status counts, lists (never notes or email). Sub-pages: every stat tile links to `/u/:username/:view` (`GET /api/profiles/:username/:view`; views in `PROFILE_VIEWS`: queue, collection, backlog, playing, paused, finished, abandoned), all public and rendered by the shared `PublicGameList`.
- **Share cards:** public profile and Save File links carry `og:*`/`twitter:*` tags and a generated 1200x630 PNG (`/api/og/...`). Cards show only public data and never game titles or notes (satori only draws the bundled latin glyphs). Cached in memory only (LRU of 32, content-hash `?v=` in the URL), no disk cache; lists, series, wishlist and stats cards are not built yet. Free text a user wrote is never printed on a card (the bundled fonts are latin-only), so use a generic title. Needs `PUBLIC_URL` (or `ALLOWED_ORIGINS` set to the real URL) for absolute image URLs.
- **Logo:** (hovering or focusing the logo link darkens the icon and wordmark in light mode, lightens them in dark mode, and sweeps a glint across the icon; off under reduced motion; CSS next to `.logo` in `app.css`) a custom controller whose face buttons are a queue of three bars (`packages/shared/src/logo.ts`, one 64x64 path with the d-pad and bars as even-odd holes). Used by `Logo`, the home greeting tile, the favicon and splash in `index.html`, `Splash`, the canvas share images (`shareImage.ts`) and the server link-preview cards (`og/cards.ts`). Other `Gamepad2` Lucide icons stay: they mean "playing", not the brand.
- **Design:** flat modern look (hairline borders, no offset shadows), deep navy dark theme with three surface levels (`--bg-0..3`) and a cool-paper light counterpart under the same token names (redesign brief: `docs/ux-redesign.md`, plan: `docs/ux-redesign-plan.md`; the old names `--bg --surface --surface-2 --ink --ink-muted` are aliases of them until the redesign's last phase), cobalt accent (solid blue buttons and badges use the subtle vertical gradient `--accent-grad` from `tokens.css`, derived from `--accent` so it follows the theme: primary buttons, sidebar count badges, the logo mark), a status colour per game state (`--status-*`, always through `statusColor()` in `statusColor.ts`, and always with a dot and the word, via `StatusChip` or `.badge--*`), Outfit (headings) + Inter (text; the server's share cards still use Bricolage Grotesque + Figtree), Lucide icons (`lucide-react`; decorative, so keep a text label or `aria-label` on the button), light/dark. Keep it responsive and keyboard accessible.

## Technical notes worth knowing

- **IGDB** (checked against api-docs.igdb.com): 4 req/s and max 8 open requests; token via Twitch client credentials (cached, refreshed 1h before expiry); a new game is one `/multiquery` (game + `game_time_to_beats`, values in seconds). Without a mirror, cached metadata is never re-fetched, except release dates of unreleased wishlisted games (daily, see ARCHITECTURE.md). With one, every cached game is overwritten from it whenever a new dump is built (`services/mirror-sync.ts`). Covers are stored as `image_id` only (`packages/shared/src/igdb-images.ts`).
- **Search filtering:** only add-ons are excluded, by IGDB `game_type.type` _name_ in `apps/server/src/igdb/mappers.ts` (`EXCLUDED_TYPES`: DLC, Mod, Pack / Addon). Everything else is kept on purpose: IGDB files real ownable games under surprising types (Bundle = Kingdom Hearts HD 1.5 + 2.5 Remix, Update = Witcher 3 Remastered, Fork = Predecessor, Episode = Deltarune Chapter 1). The full type list was read from live IGDB (`/v4/game_types`); a name guess is what caused two missing-game bugs, so check live data before excluding anything. Editions are excluded by the query itself (`version_parent = null`).
- **Body limit:** every `/api/*` request body is capped at 256 KB (`MAX_JSON_BODY_BYTES` in `app.ts`, 413 past it); only `/api/data/import` is exempt, with its own 50 MB, and the screenshot upload (`POST /api/posts/:id/images`, `IMAGE_UPLOAD_PATH`) has its own 8 MB limit. A new route that needs more must be added to `OWN_BODY_LIMIT` with its own `bodyLimit`.
- **CSRF:** Hono `csrf()` only checks form-style content types, so `app.ts` also rejects mutations with a disallowed `Origin` and any non-JSON `Content-Type`. Body-less mutations (DELETE, logout) need an `Origin` header (browsers send it; tests/curl must add it). The screenshot upload is the one route that accepts an image `Content-Type` instead of JSON, and keeps the `Origin` check.
- **Auth:** argon2id (`@node-rs/argon2`), session token hashed with SHA-256 in the DB, `gq_session` cookie (httpOnly, SameSite=Lax), login by `username` (lowercase, 3-30 of `a-z0-9_-`; email is kept but not used to log in), generic login error, in-memory login rate limit, `SIGNUPS_ENABLED=false` → 403 on register.
- **Export/import** (`apps/server/src/services/export.ts`, `import.ts`, routes at `/api/data/*`; schema in `packages/shared/src/export.ts`): one versioned JSON (`format: gamequeue-export`, `version: 1`) with a metadata snapshot per game, which import never stores: games come from the mirror or IGDB (`resolveImportCatalog`, `fetchGames`), and games or platforms IGDB doesn't know are skipped. Caps: 10,000 games per file, 5,000 uncached games looked up per run, 10 committed imports per user per day. `POST /api/data/import` is a **dry run unless `?commit=true`**; the dry run executes the real merge inside a transaction and rolls back, so its report is exactly what commit does. Changing the file format means bumping `EXPORT_VERSION` and keeping a reader for the old one. Mount new routers under a specific prefix: a sub-router with `use('*', requireAuth)` mounted at `/api` would also gate `/api/auth/login`.
- **Shared game cache holds IGDB data only** (security review, `docs/archive/REVIEW.md`): import used to write the file's own metadata into the shared cache for uncached games, so a crafted file could seed a wrong name or cover for everyone. Now import looks every uncached game up in the mirror or on IGDB and skips what IGDB doesn't know, cover ids must be real IGDB image ids (`IGDB_IMAGE_ID`), image URLs encode the id, and the public landing page showcase reads only the mirror.
- **Migrations gotcha:** drizzle-kit drops `ON DELETE ...` from `ALTER TABLE ... ADD COLUMN ... REFERENCES` on SQLite. Check generated SQL for added FK columns and patch it by hand.
- **Confirmations:** never use `window.confirm`. `useConfirm()` (`components/Confirm.tsx`, provider mounted in `main.tsx`) returns a promise: `if (await confirm({ title, message, confirmLabel, tone: 'danger' })) …`. Cancel has initial focus; use `tone: 'danger'` for deletes.
- **Loading states:** there must ALWAYS be a loading skeleton while data loads, never a bare "Loading…" line or an empty page. Build placeholders on the real component's own classes so sizes match (`GridSkeletons`/`RowSkeletons` in `components/GridSkeletons.tsx`, `ListLoading` for whole list pages, `PlayingSkeletons`/`UpNextSkeletons` on home, `ResultSkeletons`/`ResultListSkeleton` for search results, `PageSkeletons.tsx` for the game page, profile, list cards, selects, checkboxes and playthrough history): shimmering `.skeleton` blocks, `role="status"` plus `aria-label` on the container, `aria-hidden` on the pieces, and no animation under reduced motion. Show them only on the first load (`isPending`); background refetches keep the old data. Any new page, list or panel that fetches data ships with its skeleton in the same change. Before the JS bundle has loaded, the inline splash in `apps/web/index.html` (the pulsing logo mark with its queue bars lighting up in turn, plain CSS, colours copied from `tokens.css`) fills `#root` and React replaces it on mount, and while `/api/auth/me` is pending `App` renders the same mark as `components/Splash.tsx` (no skeleton: the page layout isn't known yet; `--splash-t` keeps the animation continuous across the hand-over). When `/api/auth/me` resolves after the loader was visible, `useSplashExit` (in `Splash.tsx`) plays a ~0.75s exit: the mark shrinks and fades, then a veil (the splash portalled to `body` with `.splash--leaving`) lifts while `#root` fades in (`.root-enter`); skipped for fast loads and under reduced motion; the CSS lives in `index.html`.
- **Dialogs:** native `<dialog>` via `useModalDialog` (`components/useModalDialog.ts`). To focus a field on open, mark it `data-autofocus` (and keep `autoFocus` for re-mounts); React's `autoFocus` alone fails because the field is created before the dialog is opened, so the ✕ button gets focus instead.
- **Nested transactions:** services call each other inside `db.transaction` (drizzle uses savepoints), e.g. `startPlaythrough` dequeues the game; a thrown `HttpError` rolls everything back.
- **Migrations:** edit `apps/server/src/db/schema.ts`, run `npm run db:generate`, commit the new file in `apps/server/drizzle/`. They run at startup and in every test DB.
- **Tests:** Vitest against in-memory SQLite via `createApp({db, config, igdb})` and `app.request()`; helpers in `apps/server/test/helpers.ts` (`makeApp`, `fakeIgdb`, `fakeGame`). Drizzle throws on empty `.values([])`, so guard inserts of possibly-empty arrays.
- **TypeScript** is pinned to 5.9 (npm lists 7.x; not tried).
- **Prod:** `npm run build && NODE_ENV=production npm start` serves API + built web on one port.
- **Router:** a data router with one splat route (`main.tsx`); the routes themselves are the descendant `<Routes>` in `App.tsx`. `withPageTransitions` turns on view transitions for every navigation that changes the pathname, so pass `viewTransition: false` to opt one out. A `view-transition-name` must be unique on the page or the browser skips the transition, so name an element only while its own transition runs (`useViewTransitionState`, as `useEntryLink` does). The browser also puts its own animations on the old/new layers, one of which animates `mix-blend-mode` to `plus-lighter` (images get added together and light up); a static `mix-blend-mode: normal` does not beat it, so give those layers an `animation` of your own (see `game-cover-in`). To see a real transition, run the real server with a fake IGDB (`makeApp` from the server tests, `mountWeb`, seeded through `app.request`) and drive Chrome over CDP with `Animation.setPlaybackRate` 0.05. Headless Chrome with `--virtual-time-budget` never runs a view transition's update callback; drive it in real time over CDP (`--remote-debugging-port`) to check one.
- Collection filter options come from `GET /entries/facets` (the plan's `GET /tags` was folded into it).
