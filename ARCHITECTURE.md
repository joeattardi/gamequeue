# Architecture

How GameQueue is put together. `CLAUDE.md` holds the working notes and product decisions; this file explains the structure and the main flows. New to the codebase? Read `OVERVIEW.md` first: a gentler, diagram-led tour of the same subsystems. **Keep it up to date whenever functionality is added or changed** (new routes, tables, services, auth or IGDB behaviour, web pages).

## Repo layout

npm workspaces monorepo.

```
apps/
  server/            Hono API + Drizzle (SQLite)
    src/
      index.ts       Entry point: load config, open DB, build app, serve built web, start listening
      app.ts         createApp({db, config, igdb}): middleware, route mounting, error handler
      config.ts      Env vars -> Config
      web.ts         Production serving of the built web app: static files + SPA fallback (adds link-preview tags, robots rules)
      og/            Share cards: satori layout (cards.ts, social-cards.ts for grids and tier lists), resvg PNG + LRU (render.ts), cover/font loading, meta tags (meta.ts)
      errors.ts      HttpError (status + message + extra JSON)
      http.ts        validate(zodSchema, value), parseId
      auth/          password hashing, sessions, requireAuth middleware, login rate limiter
      db/            schema.ts (Drizzle tables), client.ts (open + migrate)
      igdb/          IGDB client, token provider, request limiter, mappers, search cache
      routes/        Thin HTTP layer: parse + validate input, call a service, return JSON
      services/      Business logic; all DB work lives here
    drizzle/         Generated SQL migrations (committed)
    test/            Vitest suites + helpers (in-memory SQLite, fake IGDB)
  web/               React + Vite + TanStack Query + React Router
    src/
      main.tsx       Providers: QueryClient, Router, ConfirmProvider
      App.tsx        Auth gate + route table
      api/           fetch wrapper (client.ts) and TanStack Query hooks per area
      routes/        One component per page
      components/    Shared UI (dialogs, slot bay, score gauge, ...)
      styles/        tokens.css (design tokens, light/dark), app.css
packages/
  shared/            Zod schemas, DTO types and pure logic used by both apps (consumed as TS source)
```

`packages/shared` is the contract between the two apps: request schemas (`addEntrySchema`, `loginSchema`, ...), response DTOs (`EntryDto`, `SlotDto`, ...), the export file schema, status rules (`status.ts`), the random-pick algorithm (`pick.ts`, pure with an injectable RNG), smart-list rules and their evaluator (`smart-lists.ts`, pure with an injectable clock; also runs in the web editor's live preview), the CSV writer (`csv.ts`), the stats computation (`stats.ts`, pure), the year-in-review computation (`recap.ts`, pure), the avatar identicon generator (`avatar.ts`, pure) and IGDB image URL helpers. There is no build step for it; both apps import the TypeScript directly.

Useful commands: `npm run dev` (server :3000 + web :5173, Vite proxies `/api`), `npm run build && NODE_ENV=production npm start` (one process serves API and built web), `npm test`, `npm run typecheck`, `npm run db:generate`.

## Request flow

```
Browser
  -> React component calls a TanStack Query hook (apps/web/src/api/*.ts)
  -> api() in client.ts: fetch('/api/...'), same-origin cookies, JSON body
  -> Hono app (apps/server/src/app.ts)
       1. csrf() on /api/*
       2. origin + content-type guard for POST/PUT/PATCH/DELETE
       3. router matched by prefix
       4. requireAuth(db, config)   (every router except /api/auth, /api/health and /api/profiles)
       5. route handler: validate(sharedSchema, input) -> service function(db, userId, ...)
  -> service reads/writes SQLite via Drizzle, returns a DTO
  -> JSON response; errors thrown as HttpError (or Zod failures via validate) are turned into
     { error, ...extra } by app.onError; anything else is a 500
  -> mutation hook's onSuccess invalidates related query keys, so the UI refetches
```

Details:

- **Route mounting** (`app.ts`): `/api/auth`, `/api/admin` (admin role only), `/api/igdb`, `/api/entries` (two routers share the prefix: CRUD and playthrough/status actions), `/api/playthroughs`, `/api/slots`, `/api/lists`, `/api/smart-lists`, `/api/queue`, `/api/wishlist`, `/api/discover`, `/api/series`, `/api/stats`, `/api/recap`, `/api/pick`, `/api/data`, and the public `/api/profiles`, `/api/showcase` and `/api/og`. Each router applies `requireAuth` itself; `requireAuth` is a no-op if an earlier router on the same prefix already authenticated the request. Mount new routers under a specific prefix, never a `use('*', requireAuth)` router at `/api`, which would also gate login.
- **Pagination** (`packages/shared/src/pagination.ts`, `usePagedQuery` in `apps/web/src/api/paging.ts`, `LoadMore` component): every endpoint that returns games takes `?limit=&offset=` (`pageQuerySchema`: default 48, max 200) and answers with one page plus `total` (the whole match count): `GET /api/entries` (`pageEntries`), `GET /api/lists/:id` and `GET /api/queue` (`getList`), `GET /api/smart-lists/:id`, `GET /api/wishlist`, and on the public profile `/:username/:view`, `/:username/wishlist` and the per-list `/:username/lists/:id` and `/:username/smart-lists/:id` (the profile itself shows each list and smart list only as a tile, `ProfileListTileDto`: name, total and a few covers, like the Lists page's `ListCard`; a tile links to `/u/:username/lists/:id` or `/smart-lists/:id`, `ProfileListPage`, which pages the games). Offset paging is enough here: one user's data, and clients only ever load a contiguous prefix. Server-side callers that need everything (stats, recap, pick, exports, smart-list evaluation) call `listEntries`/`getList`/`wishlistItemsOf` without a page. Mutation responses return the first page. The web uses `useInfiniteQuery` with a "Load more" button (not scroll-triggered, so the footer stays reachable and navigating back keeps the loaded pages in the query cache). A page's first response also carries the list's own fields (name, years…), which `usePagedQuery` exposes as `head`. Purpose-built endpoints replace "fetch everything and filter" in the client: `GET /api/entries/candidates?q=&exclude=` (slot picker: queue first, then playing, paused, unplayed), `GET /api/wishlist/releasing-soon?days=&today=` (home page), `POST /api/smart-lists/preview` (the editor's live preview; rules and sort in the body), and `GET /api/entries/facets` carries `finishedYears`.
- **List descriptions**: `POST /api/lists` takes an optional `description`; `PATCH /api/lists/:id` takes `name` and/or `description` (whatever is left out stays; the queue can't be edited); smart lists carry it in their `PUT`/`POST` body. It is shown under the title on the list pages and on the public list pages (so it is public like the rest of a list), and it is in the export file as an optional `description` on `lists` and `smartLists` (still format v1). Import fills an empty description on a list you already have and never overwrites one.
- **Reordering** (queue, lists, wishlist): `PUT /api/lists/:id/move`, `/api/queue/move` and `/api/wishlist/move` take one item and an absolute `toIndex` (`moveInOrder` in `services/order.ts`; only the rows between the old and new place are rewritten), so they work while only the first pages are loaded. The old whole-list `PUT .../order` still exists for API callers; the web no longer uses it. Because the client holds a contiguous prefix, an index in the loaded items is also the item's index in the whole list, and drag-and-drop can only move within what is loaded.
- **CSRF**: Hono's `csrf()` only checks form content types, so `app.ts` additionally rejects mutations whose `Origin` isn't same-origin or in `ALLOWED_ORIGINS` (403), and any body that isn't `application/json` (415). Body-less mutations (DELETE, logout) need an `Origin` header; browsers send one, curl and tests must add it.
- **Validation**: input schemas live in `packages/shared` and are applied with `validate()`; failure is a 400 with `details: [{path, message}]`.
- **Errors**: `HttpError(status, message, extra)` is thrown from services. Statuses in use: 400, 404, 409 (e.g. already collected, slot occupied; `extra` carries the conflicting data), 502 (IGDB down), 503 (IGDB not configured). Throwing inside `db.transaction` rolls it back.
- **Transactions**: services call each other inside `db.transaction` (Drizzle uses savepoints for nesting). For example `assignToSlot` reuses `startPlaythrough` and `togglePause`. `POST /entries/:id/start` also accepts `paused: true` (open the playthrough already paused, for a game started before tracking; the game page offers it for unplayed games as "Mark paused"). The game page's "Mark abandoned" for an unplayed game is just `POST /entries/:id/playthroughs {outcome: 'abandoned'}` with unknown dates.
- **Services** (`apps/server/src/services/`): `entries` (collection CRUD, listing/filtering, facets, tags, hydrating `EntryDto`), `playthroughs` (status transitions, history, `vacateSlots`, `syncStatus`), `slots`, `lists` (lists and the queue), `smart-lists` (saved rules, evaluation, export rows), `wishlist`, `stats`, `recap`, `pick`, `games` (IGDB-backed metadata cache, plus `loadGames`, which builds `GameDto`s from it for entries and wishlist items alike), `export`, `import`.
- **Production serving** (`index.ts`): if the built web dir exists (`WEB_DIST`, default `../web/dist`) it is served statically with an SPA fallback to `index.html` (`web.ts`, `mountWeb`).
- **Share cards / link previews** (`og/`, `routes/og.ts`, `services/og.ts`, `web.ts`): crawlers (Discord, Twitter, Slack) don't run the SPA, so the SPA fallback in `web.ts` adds `<title>`, `og:*` and `twitter:*` tags to `index.html` for `/u/:username`, `/u/:username/recap[/:year]`, `/u/:username/grids/:id` and `/u/:username/tiers/:id` (`pageMeta`/`injectMeta` in `og/meta.ts`; unknown users and every other path get the plain shell, and a failure while building tags is logged and the plain page served). `og:image` points at the public, login-free `GET /api/og/profile/:username.png` `GET /api/og/recap/:username/:year.png`, `GET /api/og/grid/:username/:id.png` or `GET /api/og/tiers/:username/:id.png` (1200x630; anything else, including a missing `.png`, is a 404). Absolute URLs use `PUBLIC_URL` (default: the first `ALLOWED_ORIGINS` entry). The card shows only public, reduced data (`services/og.ts`: `profileCardData`/`recapCardData`; counts, genre names, the username and cover art, never game titles or notes, which also keeps it to glyphs the bundled fonts have). The sha1 of that data is `cardKey`: it is the `?v=` in the `og:image` URL (so a changed profile is a new URL for the unfurlers' own caches) and the key of the in-memory LRU (`og/lru.ts`, 32 cards, roughly 20 MB; concurrent requests for one key share a single render). Nothing is written to disk. Layout is plain objects for satori (`og/cards.ts`: flexbox-only CSS, Bricolage Grotesque and Figtree static WOFF from `@fontsource/*`, since satori can't read WOFF2 or variable fonts) rasterised by `@resvg/resvg-js` (`og/render.ts`). Cover art is fetched from the IGDB CDN as data URIs (`og/covers.ts`, own small LRU, 4 s timeout; a failed fetch draws a placeholder, never an error). **Grid and tier list cards** (`og/social-cards.ts`, `gridCardData`/`tierCardData` in `services/og.ts`): the grid card draws the board as a mosaic of its covers (empty cells as dashed tiles), the tier card up to 5 non-empty tiers as coloured rows with up to 6 covers each and a "+N" for the rest (the unranked pool isn't drawn). Both show the avatar, "by username", a count and the page path. They carry the owner's own words, which the bundled latin fonts may not have, so the title and a short tier name are printed only when `drawable` (`og/text.ts`: Basic Latin, Latin-1 and common punctuation) says so; otherwise the card says "Game grid"/"Tier list" and a tier shows just its colour. Cell labels and game titles are never drawn. These cards draw many covers, so the loader fetches the small size (`cover_small_2x`) for them (the profile and recap cards keep `cover_big_2x`; the loader caches per size) and a card costs at most about 30 cover fetches, mostly already cached; the link-preview description is the owner's own description if they wrote one, else a summary. Uploaded avatars are converted to PNG with `sharp` first because resvg silently draws nothing for WebP; a corrupt upload falls back to the identicon.
- **Search engines** (`seo.ts`, `web.ts`): `GET /robots.txt` (production only, from `mountWeb`) disallows `/api/` except `/api/og/` (share-card images stay fetchable for link previews). The app and profile pages are deliberately _not_ disallowed in `robots.txt`: a crawler must fetch a page to see its `noindex`, and a blocked URL can still be listed. The indexing rules live in `pageSeo` (used by the SPA fallback): `/` is indexable and gets a description, canonical and text-only (`twitter:card=summary`) tags; `/u/:username/...` is indexable only when that user ticked **Allow search engines to index my public profile** (`users.search_indexable`, default off; `PUT /api/account/search-indexing {searchIndexable}`, Account page, `UserDto.searchIndexable`), otherwise it is served with `X-Robots-Tag: noindex`; a username that doesn't exist is a real 404 (still with the app shell, so the web app shows its not-found page); everything else (login, register, the signed-in app) is `noindex`. Link-preview and canonical tags are added whatever the opt-in, so shared links keep their previews. Not done yet: sitemap, server-rendered landing/profile content, JSON-LD. Unknown top-level paths still return 200 with the shell (the server doesn't know the web routes), but are `noindex`.
  Expired sessions are purged at startup and every 6 hours.
- **Web client**: `App.tsx` calls `useMe()`; unauthenticated users get the marketing landing page `LandingPage` at `/` (hero with a slots/queue mock whose three covers come from the public `GET /api/showcase`: three random cached games that have a cover, `Cache-Control: no-store`, game metadata only, fetched once per visit by `useShowcase`, with a skeleton while loading and a plain placeholder for any missing game, how it works, feature grid, call to action; the sign-up buttons follow `useAuthConfig().signupsEnabled`), `/login` and `/register` (`AuthPage`, a form card beside the `AuthShowcase` brand panel from 900px up (the neon controller photo, resized to 900/1600px WebP in `src/assets/`, under a navy scrim with the tagline and three feature pills; the original `controller.jpg` at the repo root is not committed); any other path shows `NotFoundPage`, standalone with its own header and footer) and the public profile `/u/:username`, `/u/:username/wishlist` (`ProfileWishlistPage`), `/u/:username/lists/:id` and `/u/:username/smart-lists/:id` (`ProfileListPage`) and `/u/:username/:view` (`ProfilePage`, `ProfileGamesPage`, which bring their own header and `Footer` instead of the `Shell`; also reachable when logged in), authenticated users get the `Shell` layout (a sticky left sidebar with the logo, a search field (a link to `/search`; the `/` key does the same unless typing in a field), the main nav in labelled groups (Play, Library, Insights; Queue, Backlog and Wishlist carry a count from `useNavCounts` in `api/counts.ts`, each a one-game request read for its `total`, keyed under the collection groups so any change refreshes them; Recap is promoted there only in December and January, `isRecapSeason` in `lib.ts`) and the `UserMenu` (avatar and name opening a panel with profile, account, data, admin for admins, and sign out); from 900px up a Collapse button shrinks the sidebar to a 64px icon rail (the column width animates and the labels fade out, staying in the DOM and clipped by the sidebar edge, with tooltips on the links; the transitions are off under reduced motion; counts become badges, the user menu panel is `position: fixed` so the scrolling sidebar can't clip it; remembered in `localStorage` as `gq.sidebar.collapsed`; the drawer is never collapsed); under 900px the sidebar becomes a slide-in drawer opened by the hamburger in a slim bar at the top (it scrolls away with the page), closed by its ✕, the backdrop, Escape or navigating, with the rest of the page `inert` while it is open; the main column ends in a `Footer` whose `sitemap` links list every signed-in page, Recap always included) with pages for home, search (`/search?q=`, `SearchPage`: IGDB search whose results link to the game's page), collection, backlog, game (`games/:id`, owned games), game by IGDB id (`games/igdb/:igdbId`, `GameDetailPage`: summary, score, time to beat and platforms with Add to collection (the platform step of `AddGameDialog`) and Add/Remove wishlist; redirects to `games/:id` when the game is owned), queue, wishlist, lists, list, smart list (`smart-lists/:id`, plus `smart-lists/new` and `smart-lists/:id/edit`), stats (`StatsPage`, with the public twin `ProfileStatsPage` at `/u/:username/stats`; both render the shared `StatsView`, which draws its bar charts as plain HTML/CSS in the accent colour: vertical bars from a zero baseline with values over non-empty bars, horizontal two-tone bars for the breakdowns, a visually hidden table behind each chart), recap (`RecapPage` at `/recap` and `/recap/:year`, public twin `ProfileRecapPage`; the private page has a Share button that copies the public URL for the shown year at `/u/:username/recap[/:year]`; both render the shared `RecapView`, a stack of big coloured "Wrapped" cards on the fixed `--recap-*` tokens, with a year picker), pick, data (export/import) and, for admins only, admin (`/admin`). Signed-in paths no route matches show the same `NotFoundPage` inside the shell (the web app has no redirect-to-home catch-all any more; the server still answers 200 for them, see Search engines). Collection and backlog (`CollectionPage`) show games as a cover-art grid (title and details in a band over the cover on hover or focus) or as rows, chosen with the shared `LayoutToggle`/`useLayout` (`components/LayoutToggle.tsx`, also used by `PublicGameList`; remembered in `localStorage`), with matching skeletons while loading (the grid card is `GameCard` in `components/GameCard.tsx`). Beside the results sits a faceted-filter sidebar (`FacetSidebar` in `components/FacetSidebar.tsx`; above the results as a collapsible "Filters" disclosure under 900px): status (collection only), platform, genre and tag checkboxes with counts, kept in the URL as repeated params (`?platform=1&platform=2`). Values within a facet are any-of, facets combine with AND (`filterWhere` in `services/entries.ts`); `GET /api/entries/facet-counts` takes the same query and returns every option with the count it would match under the _other_ facets, so picking a value doesn't zero out its siblings (`FacetCountsDto`; options with 0 are hidden unless selected, and a facet with no options left is hidden). Search text and sort stay in a bar above the results. `GET /entries/facets` (plain option lists) still serves the pick criteria page. List, queue and wishlist pages open in the row layout, which is the only one that reorders, removes or edits (drag handles, move buttons, wishlist platform/note); their tile layout is browse-only, with the position as a badge on each cover. `/pick` is a hub with two modes: `pick/criteria` (server-side `POST /api/pick` over the backlog, queue, a list or a smart list with filters; the platform, genre and tag groups are collapsed `<details>` sections showing how many are selected) and `pick/choose` (client-only: the user gathers contenders by search or by loading a list/the queue, and `pickRandom` from `pick.ts` chooses among them, shown with the same shuffling-cards animation as the criteria mode (`Rolling` and `rollDelay` in `components/PickResult.tsx`); re-roll never repeats until all have been shown). Query keys group by area (`entries`, `entry`, `facets`, `platforms`, `search`, `playthroughs`, lists, slots, queue, wishlist); mutations invalidate the relevant groups. Every page sets its browser tab title with `usePageTitle()` (`lib.ts`) as `<page> | GameQueue` (e.g. `Collection`, a game's or list's name, `<username>'s Profile`), falling back to plain `GameQueue` until the name is known; a new page must call it. The lists page shows each list as a tile of its first four covers cut into equal vertical slices (`ListSummaryDto.covers`, cover image ids of the first games with a cover, from `listLists`) under a dark scrim holding the name and count; an empty list is a plain tile. Below the list tiles the lists page has a Smart lists section: the same tiles (`SmartListSummaryDto`), a New smart list button and, for each preset in `SMART_LIST_PRESETS` that the user doesn't have yet (matched by name), a one-click Add that creates an ordinary editable smart list. `SmartListPage` shows the rules in words, the matching games in the grid or row layout (read-only: membership is computed, so no reordering or removing), Random pick, Edit, Export CSV and Delete. `SmartListEditPage` edits name, rules and sort; each rule is a field select plus checkboxes (status, platform, genre, tag; options come from `GET /entries/facets`) or an at-least/at-most/unknown comparison and a number (time to beat is entered in hours), and a live preview evaluates the draft against the whole collection (`useEntries` with no filters) in the browser using the same `evaluateSmartList` as the server, so no preview endpoint exists. Confirmations use `useConfirm()` and dialogs use native `<dialog>` via `useModalDialog`. Platforms are shown as an icon plus short name (`PlatformTags`/`PlatformTag` in `components/PlatformIcon.tsx`, joined with other metadata by `MetaLine`). Icons are Simple Icons glyphs (CC0, v11.14.0, vendored as path strings in `platformIconPaths.ts`) or Lucide for web/arcade, mapped from IGDB platform ids in `platformIcons.ts`; platforms with no mapping (e.g. DOS, older Nintendo, Amiga) show text only. To add one, vendor its path and add the id to a family.

## Data model

SQLite via better-sqlite3, WAL mode, `PRAGMA foreign_keys = ON`. Schema in `apps/server/src/db/schema.ts`; migrations in `apps/server/drizzle/` run automatically when the DB is opened (startup and every test DB). Timestamps are epoch milliseconds; game dates are `YYYY-MM-DD` text.

**Shared game metadata cache** (no `user_id`; ids are IGDB ids):

| Table                           | Purpose                                                                                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `games`                         | name, slug, summary, release date (+ `release_precision`: day/month/quarter/year, null = unknown; `release_checked_at`), cover `image_id`, IGDB rating, game type, time-to-beat (seconds), `fetched_at` |
| `platforms`, `genres`, `themes` | Lookup tables                                                                                                                                                                                           |
| `game_platforms/genres/themes`  | Many-to-many join tables, cascade on game delete                                                                                                                                                        |
| `series`                        | IGDB series ("collections"): id, name, `members_fetched_at`. Shared cache like `games`                                                                                                                  |
| `game_series`                   | `(game_id, series_id)`, cascade on both; which series a cached game belongs to (a game can be in several)                                                                                               |
| `series_members`                | `(series_id, game_id)` plus name, cover, release date/precision: IGDB's list of a series' main entries, cached for the series page. Not necessarily in `games`                                          |

**Per-user data** (every row carries `user_id`, directly or through its entry; all queries filter by it):

| Table                               | Purpose                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`                             | username (unique, stored lowercase), email (unique), argon2id `password_hash`, `role` (`gamer` default or `admin`)                                                                                                                                                                                                                                                                                                   |
| `sessions`                          | `id` = SHA-256 of the cookie token, `expires_at`; cascades with the user                                                                                                                                                                                                                                                                                                                                             |
| `entries`                           | A game in a user's collection: `status` (unplayed/playing/paused/finished/abandoned), `rating` 1-5 stars, `favorite` (boolean, default false). Unique per `(user_id, game_id)`                                                                                                                                                                                                                                       |
| `entry_platforms`                   | Platforms the user owns the game on                                                                                                                                                                                                                                                                                                                                                                                  |
| `tags`, `entry_tags`                | Per-user tags, unique case-insensitively; unused tags are deleted when tags change                                                                                                                                                                                                                                                                                                                                   |
| `playthroughs`                      | Per entry: platform, `started_on`/`ended_on` (nullable = unknown), `outcome` (null = open, finished, abandoned), rating, `playtime_minutes` (optional total play time the user enters, mostly when finishing; null = not recorded). Partial unique index: at most one open playthrough per entry                                                                                                                     |
| `slots`                             | Named "currently playing" slots with `position`; `entry_id` holds at most one game. Partial unique index on `(user_id, entry_id)` so a game can't be in two slots; `ON DELETE set null` on the entry                                                                                                                                                                                                                 |
| `lists`                             | User lists. `kind` is `list` or `queue`; a partial unique index allows one `queue` per user (created lazily by `ensureQueue`). `description` is the owner's free text (max 500, `MAX_LIST_DESCRIPTION`; always empty for the queue)                                                                                                                                                                                  |
| `smart_lists`                       | Saved rules: `name`, `description` (the owner's free text, as on `lists`; the rules in words are `ruleText` in the DTOs), `rules` (JSON, validated by `smartRulesSchema` on write), `sort`, `dir`. No items table: the matching games are computed from the collection on every read                                                                                                                                 |
| `list_items`                        | `(list_id, entry_id)` primary key plus 0-based `position`; rewritten on reorder (wholesale for `PUT /order`, just the moved range for `PUT /move`)                                                                                                                                                                                                                                                                   |
| `error_events`                      | Errors the server recorded for the admin page: `at`, `kind` (`ERROR_KINDS` in shared), `message`, `status`, `route`, `stack`, `context` (JSON text); pruned by age (30 days) and to the newest 5000 rows                                                                                                                                                                                                             |
| `igdb_daily`                        | IGDB HTTP attempts per UTC day: `day` (PK), `ok`, `rate_limited` (429), `failed`; kept 90 days                                                                                                                                                                                                                                                                                                                       |
| `server_runs`                       | One row per server start: `started_at`, `version` (git commit), `last_seen_at` (heartbeat, about every minute), `ended_at`, `ended` (`clean`, `crash`, `unclean`; null while running); kept 90 days                                                                                                                                                                                                                  |
| `settings`                          | Runtime settings an admin can change: `key` (PK), `value`, `updated_at`; absent key = use the environment default (only `signups_enabled` so far)                                                                                                                                                                                                                                                                    |
| `avatars`                           | A user's uploaded avatar: `user_id` (PK, cascade), `content_type`, `data` BLOB (a small client-made square image), `updated_at`. No row = generated identicon. Separate from `users` so user lookups never load the blob.                                                                                                                                                                                            |
| `wishlists`                         | Games the user wants but doesn't own. A user's first wishlist (lowest id) is _the_ wishlist; `ensureWishlist` creates it lazily. No unique index per user, so several wishlists need no schema change                                                                                                                                                                                                                |
| `game_prices`                       | Cached IsThereAnyDeal price per game (shared like `games`, cascades with it): ITAD id (null = no title match), cheapest current price, shop, link, history low, the `country` it was fetched for and `checked_at`                                                                                                                                                                                                    |
| `dismissed_games`                   | Games a user told Discover not to suggest again: `(user_id, game_id)` primary key (IGDB id, no `games` FK since suggestions are usually uncached), cascades with the user. Not in the export file                                                                                                                                                                                                                    |
| `activity_events`                   | What a user did, for the public profile feed: `type` (`ACTIVITY_TYPES`), `at`, optional `game_id` (FK to `games`), `subject_id`/`subject_name` (grid, tier list, list or slot) and `detail` (rating stars). Index `(user_id, at)`; cascades with the user. Not in the export file                                                                                                                                    |

Relationships to remember:

- A user owns entries; an entry points at a cached `games` row. Deleting an entry cascades to its platforms, tags, playthroughs and list items, and empties its slot.
- The backlog is not stored: it is every entry with status `unplayed`.
- **Favorites** (`entries.favorite`): a per-user, per-game flag set with `PATCH /api/entries/:id {favorite}`. It is independent of rating, lists and the queue, and a patch containing only `favorite` does not touch `updated_at` (so it doesn't reset the "last changed" smart list field). Filter: `favorite=true` on `GET /api/entries`, with a `favorites` count in `GET /api/entries/facet-counts` (scoped by the other active facets). The web shows a heart toggle on the game page (`FavoriteButton` in `EntryPage`, colour token `--favorite`) and a "Favorites only" option in the collection filters.
- **Smart lists** (`services/smart-lists.ts`, `packages/shared/src/smart-lists.ts`, routes `/api/smart-lists`: `GET /`, `POST /`, `POST /preview`, `GET|PUT|DELETE /:id`, `GET /:id/export.csv`): a smart list is a name, an AND-ed array of rules and a sort. Rules are `status`/`platform` (ids)/`genre`/`tag`/`finishedYear` any-of sets, `favorite` (no parameters: "Is a favorite") (`finishedYear` tests `EntryDto.finishedYears`, every year with a finished playthrough that has an end date, so it agrees with the profile's finished-by-year pages), or a number field (`ttb` in minutes, `igdbScore`, `rating`, `addedDays`, `changedDays`, `finishedDays`, `releaseYear`) with `gte`/`lte`/`unknown`; an unknown value never satisfies `gte`/`lte` (as with the pick's max time). "Days" fields count whole days back from now; `changedDays` uses `entries.updated_at`, which any status, rating, notes, tag or platform edit bumps (and import resets), so it means "last touched", not strictly "last played". Evaluation is pure over `EntryDto`s (`evaluateSmartList`): the service loads every entry once (`hydrate`) and filters and sorts in memory, which is fine at personal-collection scale and keeps one definition of "matches" for the server and the editor preview. Sorting puts missing values last whichever way it goes. A smart list holds no games, so it can't be reordered; the random pick can use it as a source (`source: {type: 'smart', smartListId}`) with the usual rule that only unplayed games, plus paused if asked, are candidates. They are collection-only and never include wishlist games.
- **Stats** (`services/stats.ts` loads the entries and the finished playthroughs, `computeStats` in `packages/shared/src/stats.ts` does the arithmetic; `GET /api/stats` for the owner, `GET /api/profiles/:username/stats` public, registered before `:view`): overview (counts, backlog size and summed time to beat of backlog games with a known time, average rating), games finished per year and over the last 12 months (a game counts once per period; playthroughs with unknown dates only appear under `unknown` in the yearly view), top-10 platform/genre/tag breakdowns with finished and unplayed counts, rating distribution and top-rated games, and total play time. Play time is the `playtime_minutes` the user entered, summed over _finished playthroughs_ (replays count again); finishes without one are counted as `unrecordedCount` and add nothing. Nothing is timed. The DTO holds only counts and `PublicEntryDto`s, so the same payload serves the private and public pages.
- **Recap** (`services/recap.ts` loads the entries and every playthrough, `computeRecap` in `packages/shared/src/recap.ts` does the arithmetic; `GET /api/recap?year=` for the owner, `GET /api/profiles/:username/recap?year=` public, registered before `:view`; a malformed `year` is a 400): the **Save File** (the user-facing name; the code, routes and `--recap-*` tokens still say "recap"), a year in review. Without `year` it picks the current year if it has activity, else the latest one (`defaultRecapYear`); `years` lists every year with a finish, abandon, start or added game. A game counts once per year however often it was finished. Fields: finished/previous-year/abandoned/started/added counts, replays (finished games also finished in an earlier year), play time (entered play time over the year's finished playthroughs, like stats), finishes per month and the busiest one, top 3 genres and platforms (the platform of the playthrough), best-rated finishes, longest/shortest game by time to beat, the longest start-to-finish haul (both dates known), first/last finish, every finished game, and a playful `archetype` (first matching rule of collector, marathoner, sprinter, returner, explorer, finisher, else steady). Unknown dates never count towards a year. The DTO holds only counts and `PublicEntryDto`s (no notes), so one payload serves the private and public pages.
- **Series** (`services/series.ts`, `routes/series.ts`, `SeriesPage`): a series is an IGDB _collection_ (type "Series"; franchises were deliberately not used, they mix spin-offs and media). `fetchGame` returns `collections`, `saveGame` stores them (`series` + `game_series`), and `GameDto.series` carries them. Games cached before this, and games saved from an import file (no series in the snapshot, so they are saved with `series_checked_at` null), are filled in by `backfillSeries`: one request per 100 games, run in the background at startup and after an import commit, one run at a time, failures retried next time. The collection/backlog sidebar has a Series facet (`?series=`, any-of like genre) offering only series with two or more of the user's games (or one already selected). `GET /api/series/:id` returns the series' games in release order (undated last): `series_members` (cached from IGDB, re-read after a week, stale data served if IGDB fails) plus any game of the series the user owns or wishlisted whatever its type, each with the user's entry (id, status, queued) and wishlist flag. `POST /api/series/:id/queue` appends the owned _unplayed_, not-yet-queued games to the queue in release order and returns `{added}`. The web page (`/series/:id`, linked from the game and entry pages) shows rows with a status badge, "queued", "On wishlist" or a Wishlist button; unowned games link to their IGDB game page, where they are added. Series are not in the export file (they come back from IGDB).
- **Screenshots** (`games.screenshots`, JSON array of IGDB image ids; `MAX_SCREENSHOTS` = 6 from `screenshots.image_id` in the game query, `mapScreenshots`): `GameDto.screenshots` (empty when unknown or none). Null in the column means IGDB was never asked: games cached before the column existed, and games saved from an import file. `ensureScreenshots` (`services/games.ts`) asks IGDB once for those when the game is opened (`GET /api/entries/:id`, `GET /api/igdb/games/:igdbId`), best effort, and stores `[]` when there are none. The `Screenshots` component sits under the cover on `EntryPage` and `GameDetailPage`: the first three as a single column of thumbnails in their own proportions (`720p`, since the `screenshot_*` sizes crop to 16:9), a click opens a native-`<dialog>` lightbox at 1080p with previous/next (buttons and arrow keys) over all of them. Hidden under 760px, where the page is one column (the hidden images aren't downloaded). Not in the export file.
- **Onboarding**: the home page renders `Welcome` (`components/Welcome.tsx`: greeting, calls to action to search, import or start a wishlist, and a three-step intro) instead of the slots and queue when `useStats().overview.total` and the wishlist are both 0 (queue, lists and slots can only hold owned games, so the collection being empty covers them). It switches back on its own as soon as a game is added.
- **Release dates** (`packages/shared/src/release.ts`, `mapRelease` in `igdb/mappers.ts`, `refreshReleaseDates` in `services/games.ts`): IGDB has one timestamp per release, and for a vague release it is a placeholder (a game announced for "2028" is 2028-12-31), so `games.release_precision` records how exact it is, from the `date_format` of the per-platform `release_dates` that carry `first_release_date` (the most exact wins; TBD means no date). Quarter and month are read from the date's own month, so it doesn't matter whether IGDB puts the placeholder at the start or the end of the period. The wishlist shows `releaseLabel` ("Nov 19, 2026", "Nov 2026", "Q4 2027", "2028", "TBA") in the meta line and, over the cover of every game not out yet, a `ReleaseBadge` (`releaseBadge`: "in 6 days", "in 3 weeks", "in 3 months", "in 2 years" for an exact day; the vague date itself for month/quarter/year/TBA, since a count would claim too much; nothing once released). The home page's "Releasing soon" section (`ReleasingSoon`, under Up next) reuses `useWishlist` and lists wishlisted games whose exact release day (`releasesWithin`: day precision only, today through 14 days ahead) is coming up, soonest first, as covers with the same badge; it is hidden when there are none. The badge is a fixed dark pill on tiles (top right) and a strip along the bottom of the 64px cover in rows. `GET /api/wishlist` first calls `refreshWishlistReleases`: cached games that aren't released yet (`isReleased` = the whole period is over; no date counts as unreleased) and weren't checked in the last 24h are re-read from IGDB in one request, and `release_checked_at` is stamped. It is best effort (IGDB errors are logged and the cached dates are served) and only runs for the owner's own wishlist; the public wishlist shows what is cached. Rows saved before the column existed have a null precision (shown as an exact day) and are refreshed once if unreleased; imported rows are saved unchecked, so they refresh on the next wishlist load.
- **Wishlist prices** (`itad/client.ts`, `services/prices.ts`, `GamePriceDto` in shared, `PriceLine` in `WishlistPage`): optional, on when `ITAD_API_KEY` is set (`ITAD_COUNTRY`, default US, picks shops and currency). `GET /api/wishlist` calls `refreshWishlistPrices` for the requested page only: games with no cache row, a row older than 6h, or a row for another country are matched to ITAD by title (`GET /games/lookup/v1`, accepted only when the returned title equals ours after stripping punctuation and case, since a wrong game's price is worse than none; unmatched games are retried after 7 days) and priced in one `POST /games/prices/v3` (cheapest well-known shop wins, see `isMajorShop`, or the cheapest shop of all if none is well-known; amounts are minor units). Best effort like the release refresh: failures go to the error log as `job_price_refresh` and cached prices are served. The key is sent in the `ITAD-API-Key` header. `WishlistItemDto.price` is null without a key, match or shop; the public wishlist doesn't carry prices. The page credits IsThereAnyDeal when any price is shown. Not in the export file.
- **Game page prices** (`GET /api/igdb/games/:igdbId/prices`, `gameOffers` in `services/prices.ts`, `GameOffers` component on `GameDetailPage`): every shop's current offer (shop, price, regular price, percent off, the operating systems it covers, link), cheapest first, plus the all-time low. Fetched live from ITAD (`ItadClient.offers`, the same `/games/prices/v3` call without picking a winner) and kept 30 minutes in a per-process `TtlCache`, nothing stored in the database. The ITAD id comes from the `game_prices` row when the game is wishlisted, otherwise a title lookup (same exact-title rule). It is its own endpoint and query so ITAD can never delay the page, which shows a skeleton panel meanwhile. `{enabled: false}` (no key) hides the panel; an ITAD failure is a 502 (logged as `job_price_refresh`) and the panel says prices couldn't load. The panel leads with well-known storefronts (`splitShops`/`isMajorShop` in `packages/shared/src/shops.ts`: a lowercase-substring allowlist of shop names such as Steam, GOG, Epic, Humble, Fanatical, Green Man Gaming, Microsoft, Ubisoft) and puts the rest behind a "Show N more shops" toggle; if a game has no well-known shop it shows the cheapest five. The server still returns every offer. Only the IGDB-id page shows it; the page of an owned game doesn't.
- **Grids** (`services/grids.ts`, `routes/grids.ts`, `packages/shared/src/grids.ts`, web `GridsPage`/`GridPage`/`ProfileGridPage`, `GridBoard`, `GameSearchPicker`, `ShareLink`; nav group "Social"): a user's boards of labelled games, like grids.fun. Owner API at `/api/grids` (`GET`, `POST`, `GET|PATCH|DELETE /:id`, `PUT /:id/cells/:position {label?, igdbId?}`, `PUT /:id/swap {a, b}`), max 50 per user. They are public by design: anyone reads one at `GET /api/profiles/:username/grids/:id` (web `/u/:username/grids/:id`, no login; a grid under the wrong username is a 404) and the profile lists them as tiles (`ProfileDto.grids`). A DTO always has every cell (`cols * rows`, empty ones included). Resizing keeps each cell at its row and column, dropping those cut off (the web confirms first). **IGDB cost**: placing a game calls `ensureGame`, one request only if the game was never cached, made when a person clicks; reading, editing labels, swapping and the public page never call IGDB. Cells point at `games` with a real FK, so `purgeUnusedGames` counts `grid_cells` as a reference. The same game may fill several cells. **Download image** (`gridImage.ts` on the shared canvas helpers in `shareImage.ts`, `DownloadGridImage`/`DownloadImageButton`, on the editor and the public page): drawn in the browser on a canvas and saved as a JPEG (quality 0.92; much smaller than PNG for cover art, and social sites recompress anyway) with a fixed dark brand palette: title, `by username`, description, the board with each cell's label and game name, and a GameQueue footer with the IGDB credit. Canvas rather than the server's satori cards because satori only has the bundled Latin glyphs, while a canvas uses system fonts for any script; it costs the server nothing. Covers (`cover_big_2x`) are fetched with `crossOrigin='anonymous'`, which works because `images.igdb.com` answers `access-control-allow-origin: *`; a cover that fails to load is drawn as a plain tile with the game's name. In the export file (see Export/import); no share card yet. The editor is click-a-cell (dialog with label, search and move arrows) plus drag-to-swap.
- **Tier lists** (`services/tier-lists.ts`, `routes/tier-lists.ts`, `packages/shared/src/tiers.ts`, web `TierListsPage`/`TierListPage`/`ProfileTierListPage`, `TierBoard`; nav "Social" > Tier lists): games ranked into named, coloured tiers, like tiermaker. Owner API at `/api/tier-lists` (`GET`, `POST`, `GET|PATCH|DELETE /:id`; tiers: `POST /:id/tiers`, `PUT /:id/tiers/order {tierIds}`, `PATCH|DELETE /:id/tiers/:tierId`; games: `POST /:id/items {igdbId, tierId?}`, `PUT /:id/items/move {igdbId, tierId|null, toIndex}`, `DELETE /:id/items/:igdbId`). A new list gets `DEFAULT_TIERS` (S red, A orange, B yellow, C green, D blue, F purple); names (max 24 chars) and colours (the fixed `TIER_COLORS` palette: the same hex in light, dark and the image, each light enough for dark text) are editable, up to 10 tiers, 100 games and 50 lists per user. Public like grids: `GET /api/profiles/:username/tier-lists/:id` (web `/u/:username/tiers/:id`, no login; the public view shows the tiers only, not the unranked pool) and tiles on the profile (`ProfileDto.tierLists`, ranked games only). A game is in a list once; adding it again changes nothing. Items live in containers (each tier, plus the pool); `moveTierItem` rewrites the dense positions of the target and, if it changed container, the source, in one transaction, and deleting a tier appends its games to the pool in order. **IGDB cost**: as with grids, adding a game calls `ensureGame` (one request, only if never cached, per click); moving, renaming, reading and the public page never call IGDB, and `purgeUnusedGames` and the admin database stats count `tier_items` as a use of a game. The editor drags tiles between tiers (HTML5 drag and drop; the bar before a tile shows where it lands) and, as the keyboard route, a click opens a dialog to move a game to a tier or the pool, earlier/later, or remove it; the gear on a tier opens rename/colour/reorder/delete. Download image (`tierImage.ts`) draws the tiers, not the pool, with the same canvas helpers as grids (`shareImage.ts`). In the export file (see Export/import); no share card yet.
- The wishlist is deliberately not part of the collection: wishlisted games have no entry, so they are not in the collection, backlog, stats, random pick, slots or lists. The two are kept disjoint: wishlisting an owned game is a 409 carrying the `entryId`, and adding a game to the collection (`addEntry`, or an import) removes it from the user's wishlists (`dropFromWishlists`). Service functions take a `wishlistId`; only the routes resolve "the" wishlist.
- Status is kept consistent with playthroughs by `syncStatus`; slot rules are enforced in `services/playthroughs.ts` and `services/slots.ts` (a slotted game is always `playing` or `paused`; starting a game removes it from the queue).
- Registering a user also inserts the default slots (`DEFAULT_SLOT_NAMES`).

**Changing the schema**: edit `schema.ts`, run `npm run db:generate`, commit the new SQL. Check generated SQL for added FK columns: drizzle-kit drops `ON DELETE` from `ALTER TABLE ... ADD COLUMN ... REFERENCES` on SQLite and it must be patched by hand (see `0003`).

**Export/import** (`services/export.ts`, `services/import.ts`, `packages/shared/src/export.ts`, routes `/api/data/*`): one versioned JSON file (`format: gamequeue-export`, `version: 1`) with a metadata snapshot per game so import never calls IGDB. Each game carries an optional `favorite`; import only ever sets it (a file never clears a favorite you have). Smart lists travel as an optional top-level `smartLists` (name, rules, sort, dir; no games, since those are computed), merged by case-insensitive name so ones you already have are left alone. The wishlist travels as an optional top-level `wishlist` (in order, each item with its own snapshot (the game snapshot's `releasePrecision` is optional), target platform and note), so files without it are still valid v1; import appends missing games to the end of the existing wishlist, fills only empty platform/note fields, and skips games you own. Grids and tier lists travel as optional top-level `grids` and `tierLists` (still v1): a grid is its title, description, size and only its non-empty cells (position, label, game); a tier list is its title, description, tiers top to bottom (name, colour, games in order) and the unranked games. Every game in them carries its own metadata snapshot (they may be in nothing else of the file), so the export's snapshot query also covers `grid_cells` and `tier_items`, and import never calls IGDB. Import matches them by **title, case-insensitively**, and one you already have is left exactly as it is (noted in the report, counted as `skipped`) rather than merged cell by cell, so importing twice changes nothing; they are also skipped, with a note, past the per-user limits. Import is a merge matched on `igdb_id`, list and slot names, and playthrough platform+dates+outcome. `POST /api/data/import` is a dry run unless `?commit=true`; the dry run runs the real merge in a transaction and rolls it back. Changing the format means bumping `EXPORT_VERSION` and keeping a reader for the old one.

**Notes** (`entry_notes`: `entry_id` with `ON DELETE cascade`, `body`, `public` default false, `created_at`, `updated_at`; `EntryDto.notes` is the list, newest first, up to 200 per game and 10,000 characters each): a game has many notes, each private or public. Routes (all return the updated entry): `POST /api/entries/:id/notes {body, public?}`, `PATCH /api/entries/:id/notes/:noteId {body?, public?}`, `DELETE /api/entries/:id/notes/:noteId`; `PATCH /api/entries/:id` no longer takes notes. Adding, deleting or changing the text of a note bumps `entries.updated_at` (so it still resets "gathering dust"); flipping `public` doesn't. Notes are never in `PublicEntryDto`, so lists, tiles, stats, recap, share cards and the activity feed can't leak them; the only public place is `ProfileGameDto.notes` (id, body, date, public ones only) on `/u/:username/games/:igdbId`, shown by `PublicNotes`. No activity event is recorded for notes. Export carries them as optional `noteItems` per game (`body`, `public`, `createdAt`); older files with the single `notes` text still import, as one private note. Import merges: a note whose text you already have on that game is skipped (your copy and its visibility win). Migration `0028` turned each non-empty `entries.notes` into one private note and dropped the column. The CSV has one Notes column (all of a game's notes, public and private, separated by a blank line). Web: `NotesPanel` on the game page (add form with a "Show on my public profile" checkbox, per-note edit, delete with confirmation, and a Public/Private toggle).

**CSV export** (`packages/shared/src/csv.ts`, `csvResponse` in `http.ts`): `GET /api/lists/:id/export.csv` (works for the queue too, via its list id), `GET /api/smart-lists/:id/export.csv` and `GET /api/data/export.csv` (the whole collection, by title) return one row per game in list order: title, status, platforms, tags, genres, rating, favorite (yes/no), IGDB score, time to beat in hours, release date, added, last finished, playthrough count, notes and IGDB id. It's a read-only spreadsheet export, not an import format. The file is UTF-8 with a BOM (so Excel reads it correctly) and CRLF row endings, and text cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading apostrophe so a spreadsheet can't run them as formulas.

## Auth and sessions

- **Accounts**: `POST /api/auth/register` (403 when `SIGNUPS_ENABLED=false`) hashes the password with argon2id (`@node-rs/argon2`, parameters pinned in `auth/password.ts`), inserts the user and default slots in one transaction (the unique username and email indexes are the duplicate check; failure is a generic 409). Usernames are 3-30 chars of `a-z 0-9 _ -`, lowercased by `usernameSchema`; email is kept but is not used to log in, then logs the user in. **Signup alert** (`services/notify.ts`): after a successful register, `notify(subject, text)` emails the owner through Resend's HTTP API (`POST https://api.resend.com/emails`), fire-and-forget with a 10 s timeout; failures are logged and never affect the signup. It sends only the username (no email address) and is a no-op unless both `RESEND_API_KEY` and `NOTIFY_EMAIL` are set (`NOTIFY_FROM` defaults to Resend's shared `onboarding@resend.dev`, which only delivers to the Resend account's own address). `createApp` takes an optional `notify` so tests can inject a fake; admin-created users don't trigger it. `GET /api/auth/config` (public) returns `{signupsEnabled}`; the web login page hides its "Create an account" link, and `/register` redirects to `/login`, when it is false.
- **Login** (`POST /api/auth/login`): checks two in-memory `FailureLimiter`s first (per `username|ip`: 5 failures / 15 min; per IP: 30 / 15 min; 429 with `Retry-After`). It always runs an argon2 verify, against a dummy hash if the username is unknown, so timing doesn't reveal which accounts exist. Wrong credentials return one generic 401. Success resets the per-account counter. The client IP comes from the socket, or from `X-Forwarded-For` only when `TRUST_PROXY=true`. The limiters are per process, which is fine for a single-instance deployment.
- **Sessions** (`auth/sessions.ts`): on login a random 32-byte token is generated; only its SHA-256 hash is stored (`sessions.id`), so a DB leak doesn't yield usable cookies. The raw token goes to the browser in the `gq_session` cookie (httpOnly, SameSite=Lax, `Secure` when `NODE_ENV=production`, path `/`). TTL is 30 days, sliding: when less than half remains, the expiry is extended and the cookie re-issued. Expired sessions found on lookup are deleted, and a periodic purge removes the rest.
- **Per-request auth** (`auth/middleware.ts`): `requireAuth` reads the cookie, calls `resolveSession`, and sets `c.var.user = {id, username, email}`. A missing or invalid session returns 401 (and clears a stale cookie). Handlers get the user id from `c.get('user')`; every service query is scoped by it.
- **Roles and admin** (`users.role`, `USER_ROLES` in shared: `gamer` is the default standard user, `admin` also gets the admin area): `resolveSession` joins `users`, so `c.var.user` carries the current role and a grant or revoke applies to live sessions at once. `requireAdmin` (`auth/middleware.ts`) is used after `requireAuth` on admin-only routers (`routes/admin.ts`, mounted at `/api/admin`): 401 when signed out, 403 `Admin access required` for a gamer. `UserDto.role` is only a UI hint: the web `Shell` shows the Admin link, and `App` routes `/admin` (`AdminPage`, the dashboard: a Users tile with counts and a Backups panel; `admin/users`, `AdminUsersPage`, the list; `admin/users/new` and `admin/users/:id`, `AdminUserPage`), only when it is `admin`; the server is what enforces it. **Backup status** (`GET /api/admin/backup`, `services/backup-status.ts`, `packages/shared/src/backup.ts`): `scripts/backup.sh` writes `backup-status.json` next to the database (in the mounted `/data`, atomically via a temp file and `mv`) at the end of every run, also when it fails (an `EXIT` trap records the failing step): `lastRunAt`, `ok`, `error`, `lastSuccessAt` (carried over from the previous file so a failure doesn't erase it), the snapshot `file` and `sizeBytes`, and `offsite` (`uploaded`, `not-configured`, `failed`). The app only reads it (the container has no `sqlite3` or `rclone`, and the backups directory isn't mounted): the route returns `{backup, unreadable}`, with `backup: null` when the file doesn't exist yet and `unreadable: true` when it isn't valid. `backupHealth` (shared, pure) turns it into `healthy`, `no-offsite`, `stale` (no success in 26 hours, as the job runs nightly) or `failed`/`never`; the Backups panel on `AdminPage` shows that as a coloured banner (icon and text, not colour alone) plus last run, last success, off-site state and latest snapshot, with a skeleton while loading. The app can only report, not start a backup. If `HEALTHCHECK_URL` is set (read by name from `.env`, or the environment), the script also pings healthchecks.io (`/start`, success, `/fail` with the error), which covers a dead Pi or cron that the admin page can't. **Database stats** (`GET /api/admin/database`, `services/database-stats.ts`, `DatabaseStatsDto` in shared): file and WAL size from the filesystem, page size/count and free pages from pragmas, row counts for the IGDB cache (`games`, how many are referenced by an entry or wishlist item, series, series members, platforms/genres/themes, oldest and newest `fetched_at`) and for what users store (entries, playthroughs, lists, avatars and their bytes, sessions and expired ones), plus every table's row count and bytes (SQLite's `dbstat` virtual table, each index folded into its table), largest first. Computed on request, nothing stored. The dashboard's Database tile shows size, cached games and table count and links to `AdminDatabasePage` (`/admin/database`, with a skeleton).
  **Traffic** (`GET /api/admin/traffic`, `services/traffic.ts`, `cloudflare/client.ts`, `AdminTrafficPage`, `TrafficTile` on `/admin`; `TrafficDto` and `trafficTotals` in shared): optional, on when `CLOUDFLARE_API_TOKEN` (Zone > Analytics > Read) and `CLOUDFLARE_ZONE_ID` are both set. The server asks Cloudflare's GraphQL Analytics API for `httpRequests1dGroups` (daily groups: requests, cached requests, bytes, page views, unique visitors) from 29 days back, with the token in an `Authorization` header, and returns the last 30 UTC days oldest first with missing days zero-filled (`cached + uncached = requests`). ## IGDB communication

All IGDB access is server-side; the browser never talks to IGDB or sees credentials. Code is in `apps/server/src/igdb/`, behind the `IgdbClient` interface (`search`, `fetchGame`, `fetchReleaseDates`, `fetchGameSeries`, `fetchSeries`, `fetchSimilarGames`, `fetchPlatforms`) so tests inject a fake. If `IGDB_CLIENT_ID` / `IGDB_CLIENT_SECRET` are unset, `igdb` is undefined and IGDB-backed endpoints return 503 (`requireIgdb`).

- **Token** (`token.ts`): Twitch client-credentials flow (`id.twitch.tv/oauth2/token`). The token is cached in memory and refreshed an hour before expiry; concurrent callers share one refresh. A 401 from IGDB invalidates it and retries once.
- **Rate limiting** (`limiter.ts`): every request goes through `RequestLimiter`, a queue that starts at most 4 requests per rolling second with at most 8 in flight (IGDB's documented limits). A 429 response is retried up to 3 times, honouring `Retry-After`.
- **Requests** (`client.ts`): POST to `https://api.igdb.com/v4/<endpoint>` with `Client-ID` and bearer headers, APICalypse bodies (user text escaped by `quote`).
    - `search`: `games` endpoint, text search with `version_parent = null` (drops editions), limit 30, then filtered by `isCollectable` and cut to 20.
    - `fetchGame`: one `/multiquery` combining the game and its `game_time_to_beats` row (seconds).
    - `fetchReleaseDates`: `first_release_date` plus per-platform `release_dates` for up to 100 ids per request, used only by the release refresh below.
    - `fetchGameSeries`: `collections` of up to 100 games per request, for the backfill below.
    - `fetchSeries`: one collection's name plus its games limited to `SERIES_GAME_TYPES` (Main Game, Standalone Expansion, Remake, Remaster; `version_parent = null`), up to 500, with release dates and covers.
    - `fetchSimilarGames`: the game's `similar_games` expanded in one `games` request (name, release date, cover, rating, type, `version_parent`), with add-ons and editions dropped by `mapSimilarGames`.
    - `fetchPlatforms`: the full platform list.
- **Mapping** (`mappers.ts`): raw IGDB shapes become `GameRecord` / `IgdbSearchHit`. Only add-on game types are excluded (`EXCLUDED_TYPES`: DLC, Mod, Pack / Addon); see the comment there before changing it. Covers are kept as `image_id` only and turned into URLs by `packages/shared/src/igdb-images.ts`.
- **Search flow** (`routes/igdb.ts`): `GET /api/igdb/search?q=` checks a 5-minute, 200-entry `TtlCache` keyed by lowercased query, otherwise calls IGDB. The result is then annotated per user with the `entryId` of already-collected games and a `wishlisted` flag (never cached, since both are per user).
- **Similar games** (`GET /api/igdb/games/:igdbId/similar`, `similarGames` in `services/similar.ts`, `SimilarGames` component on `EntryPage` and `GameDetailPage`): IGDB's curated `similar_games` for a game, best rated first (unrated last), at most 12, never the game itself. The IGDB list is kept 6 hours in a per-process `TtlCache` (nothing in the database, so it is never stale for long and needs no migration); the user's `entryId` / `wishlisted` marks are added on every request. A separate endpoint and query, like prices, so IGDB can't delay the page; a skeleton panel shows meanwhile, and the panel is hidden when IGDB lists none or the request fails. Cards link to the game's own page when owned, otherwise to the IGDB-id page where it can be added or wishlisted. Not in the export file.
- **Discover** (`GET /api/discover`, `PUT|DELETE /api/discover/dismissed/:igdbId`, `services/discover.ts`, `DiscoverPage`, "Discover" in the sidebar's Library group and the footer site map): suggestions built from the same cached similar-game lists as the game pages (one `similarCache` per app, shared by both routers). Seeds are the user's loved games: favorites first, then entries rated 4+, newest change first, at most 20 (`MAX_SEEDS`). A candidate scores one point per seed whose list contains it, IGDB rating breaks ties; owned, wishlisted and dismissed games are removed. The response has `picks` (top 12, each with up to three `becauseOf` seed names and its `seedMatches`) and `rows` (up to 6 seeds, each with its own best 8, "Because you loved X"). Lookups run in parallel through the IGDB limiter and are cached 6 hours, so the first visit costs up to 20 requests and later ones none; a failed seed is skipped (error kind `discover_lookup`), and only if every lookup fails does the request fail. Cards link to the IGDB-id page and carry a Wishlist button (which also drops the card, since wishlisted games are hidden) and a "Not interested" button that writes `dismissed_games`; the page offers Undo for the last dismissal. With no loved games the page explains how to get suggestions; its skeleton is a grid of card placeholders. Dismissals are permanent until undone, and there is no page yet for reviewing them.
- **Game by id** (`GET /api/igdb/games/:igdbId`): `ensureGame` (so IGDB is called only for a game never cached, one multiquery) then the cached `GameDto` plus the user's `entryId` and `wishlisted` (`GameDetailDto`). Viewing a game therefore caches it in the shared `games` table even if it is never added; ownership lives in `entries`, so nothing treats a cached game as owned.
- **Adding a game** (`addEntry` -> `ensureGame` in `services/games.ts`): if the game isn't in the shared `games` table, `fetchGame` is called and `saveGame` writes it and its relations; cached metadata is never re-fetched, with one exception: release dates (below). IGDB failures are wrapped by `callIgdb` as 502. The entry is then created with the chosen platforms, and tags default to the game's genres and themes. `AddEntryInput` may also carry `status: 'paused' | 'abandoned'` (default unplayed) for games with prior history: `paused` inserts an open playthrough started on `date` (client's local day, else UTC today) and `abandoned` a closed one with unknown dates, in the same transaction. The playthrough platform is set only when a single platform was chosen. Such entries are never slotted; a paused one can be resumed or assigned like any other. The add dialog's platform step has an "Add as" select for this.
- **Platforms** (`listPlatforms`): `GET /api/igdb/platforms` serves the platform table, doing a one-time full sync from IGDB when it holds fewer than 50 rows (only games' own platforms so far).
- **Import** never calls IGDB; it writes snapshot metadata from the file into the cache for games not cached yet (existing rows are never overwritten).
