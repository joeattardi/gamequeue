# Architecture

How GameQueue is put together. `CLAUDE.md` holds the working notes and product decisions; this file explains the structure and the main flows. **Keep it up to date whenever functionality is added or changed** (new routes, tables, services, auth or IGDB behaviour, web pages).

## Repo layout

npm workspaces monorepo.

```
apps/
  server/            Hono API + Drizzle (SQLite)
    src/
      index.ts       Entry point: load config, open DB, build app, serve built web, start listening
      app.ts         createApp({db, config, igdb}): middleware, route mounting, error handler
      config.ts      Env vars -> Config
      errors.ts      HttpError (status + message + extra JSON)
      http.ts        validate(zodSchema, value), parseId
      auth/          password hashing, sessions, requireAuth middleware, login rate limiter
      db/            schema.ts (Drizzle tables), client.ts (open + migrate)
      igdb/          IGDB client, token provider, request limiter, mappers, search cache
      routes/        Thin HTTP layer: parse + validate input, call a service, return JSON
      services/      Business logic; all DB work lives here
    drizzle/         Generated SQL migrations (committed)
    test/            Vitest suites + helpers (in-memory SQLite, fake IGDB)
  web/               React + Vite + TanStack Query + React Router
    src/
      main.tsx       Providers: QueryClient, Router, ConfirmProvider
      App.tsx        Auth gate + route table
      api/           fetch wrapper (client.ts) and TanStack Query hooks per area
      routes/        One component per page
      components/    Shared UI (dialogs, slot bay, score gauge, ...)
      styles/        tokens.css (design tokens, light/dark), app.css
packages/
  shared/            Zod schemas, DTO types and pure logic used by both apps (consumed as TS source)
```

`packages/shared` is the contract between the two apps: request schemas (`addEntrySchema`, `loginSchema`, ...), response DTOs (`EntryDto`, `SlotDto`, ...), the export file schema, status rules (`status.ts`), the random-pick algorithm (`pick.ts`, pure with an injectable RNG), smart-list rules and their evaluator (`smart-lists.ts`, pure with an injectable clock; also runs in the web editor's live preview), the CSV writer (`csv.ts`), the stats computation (`stats.ts`, pure), the year-in-review computation (`recap.ts`, pure), the avatar identicon generator (`avatar.ts`, pure) and IGDB image URL helpers. There is no build step for it; both apps import the TypeScript directly.

Useful commands: `npm run dev` (server :3000 + web :5173, Vite proxies `/api`), `npm run build && NODE_ENV=production npm start` (one process serves API and built web), `npm test`, `npm run typecheck`, `npm run db:generate`.

## Request flow

```
Browser
  -> React component calls a TanStack Query hook (apps/web/src/api/*.ts)
  -> api() in client.ts: fetch('/api/...'), same-origin cookies, JSON body
  -> Hono app (apps/server/src/app.ts)
       1. csrf() on /api/*
       2. origin + content-type guard for POST/PUT/PATCH/DELETE
       3. router matched by prefix
       4. requireAuth(db, config)   (every router except /api/auth, /api/health and /api/profiles)
       5. route handler: validate(sharedSchema, input) -> service function(db, userId, ...)
  -> service reads/writes SQLite via Drizzle, returns a DTO
  -> JSON response; errors thrown as HttpError (or Zod failures via validate) are turned into
     { error, ...extra } by app.onError; anything else is a 500
  -> mutation hook's onSuccess invalidates related query keys, so the UI refetches
```

Details:

- **Route mounting** (`app.ts`): `/api/auth`, `/api/admin` (admin role only), `/api/igdb`, `/api/entries` (two routers share the prefix: CRUD and playthrough/status actions), `/api/playthroughs`, `/api/slots`, `/api/lists`, `/api/smart-lists`, `/api/queue`, `/api/wishlist`, `/api/series`, `/api/stats`, `/api/recap`, `/api/pick`, `/api/data`, and the public `/api/profiles`. Each router applies `requireAuth` itself; `requireAuth` is a no-op if an earlier router on the same prefix already authenticated the request. Mount new routers under a specific prefix, never a `use('*', requireAuth)` router at `/api`, which would also gate login.
- **CSRF**: Hono's `csrf()` only checks form content types, so `app.ts` additionally rejects mutations whose `Origin` isn't same-origin or in `ALLOWED_ORIGINS` (403), and any body that isn't `application/json` (415). Body-less mutations (DELETE, logout) need an `Origin` header; browsers send one, curl and tests must add it.
- **Validation**: input schemas live in `packages/shared` and are applied with `validate()`; failure is a 400 with `details: [{path, message}]`.
- **Errors**: `HttpError(status, message, extra)` is thrown from services. Statuses in use: 400, 404, 409 (e.g. already collected, slot occupied; `extra` carries the conflicting data), 502 (IGDB down), 503 (IGDB not configured). Throwing inside `db.transaction` rolls it back.
- **Transactions**: services call each other inside `db.transaction` (Drizzle uses savepoints for nesting). For example `assignToSlot` reuses `startPlaythrough` and `togglePause`.
- **Services** (`apps/server/src/services/`): `entries` (collection CRUD, listing/filtering, facets, tags, hydrating `EntryDto`), `playthroughs` (status transitions, history, `vacateSlots`, `syncStatus`), `slots`, `lists` (lists and the queue), `smart-lists` (saved rules, evaluation, export rows), `wishlist`, `stats`, `recap`, `pick`, `games` (IGDB-backed metadata cache, plus `loadGames`, which builds `GameDto`s from it for entries and wishlist items alike), `export`, `import`.
- **Production serving** (`index.ts`): if the built web dir exists (`WEB_DIST`, default `../web/dist`) it is served statically with an SPA fallback to `index.html`. Expired sessions are purged at startup and every 6 hours.
- **Web client**: `App.tsx` calls `useMe()`; unauthenticated users get `/login`, `/register` and the public profile `/u/:username`, `/u/:username/wishlist` (`ProfileWishlistPage`) and `/u/:username/:view` (`ProfilePage`, `ProfileGamesPage`, which bring their own header and `Footer` instead of the `Shell`; also reachable when logged in), authenticated users get the `Shell` layout (a sticky left sidebar with the logo, the main nav and the user/sign-out block; under 900px the sidebar becomes a slide-in drawer opened by the hamburger in a slim bar at the top (it scrolls away with the page), closed by its ✕, the backdrop, Escape or navigating, with the rest of the page `inert` while it is open; the main column ends in a `Footer`) with pages for home, search (`/search?q=`, `SearchPage`: IGDB search whose results link to the game's page), collection, backlog, game (`games/:id`, owned games), game by IGDB id (`games/igdb/:igdbId`, `GameDetailPage`: summary, score, time to beat and platforms with Add to collection (the platform step of `AddGameDialog`) and Add/Remove wishlist; redirects to `games/:id` when the game is owned), queue, wishlist, lists, list, smart list (`smart-lists/:id`, plus `smart-lists/new` and `smart-lists/:id/edit`), stats (`StatsPage`, with the public twin `ProfileStatsPage` at `/u/:username/stats`; both render the shared `StatsView`, which draws its bar charts as plain HTML/CSS in the accent colour: vertical bars from a zero baseline with values over non-empty bars, horizontal two-tone bars for the breakdowns, a visually hidden table behind each chart), recap (`RecapPage` at `/recap` and `/recap/:year`, public twin `ProfileRecapPage`; the private page has a Share button that copies the public URL for the shown year at `/u/:username/recap[/:year]`; both render the shared `RecapView`, a stack of big coloured "Wrapped" cards on the fixed `--recap-*` tokens, with a year picker), pick, data (export/import) and, for admins only, admin (`/admin`). Collection and backlog (`CollectionPage`) show games as a cover-art grid (title and details in a band over the cover on hover or focus) or as rows, chosen with the shared `LayoutToggle`/`useLayout` (`components/LayoutToggle.tsx`, also used by `PublicGameList`; remembered in `localStorage`), with matching skeletons while loading (the grid card is `GameCard` in `components/GameCard.tsx`). Beside the results sits a faceted-filter sidebar (`FacetSidebar` in `components/FacetSidebar.tsx`; above the results as a collapsible "Filters" disclosure under 900px): status (collection only), platform, genre and tag checkboxes with counts, kept in the URL as repeated params (`?platform=1&platform=2`). Values within a facet are any-of, facets combine with AND (`filterWhere` in `services/entries.ts`); `GET /api/entries/facet-counts` takes the same query and returns every option with the count it would match under the _other_ facets, so picking a value doesn't zero out its siblings (`FacetCountsDto`; options with 0 are hidden unless selected, and a facet with no options left is hidden). Search text and sort stay in a bar above the results. `GET /entries/facets` (plain option lists) still serves the pick criteria page. List, queue and wishlist pages open in the row layout, which is the only one that reorders, removes or edits (drag handles, move buttons, wishlist platform/note); their tile layout is browse-only, with the position as a badge on each cover. `/pick` is a hub with two modes: `pick/criteria` (server-side `POST /api/pick` over the backlog, queue, a list or a smart list with filters; the platform, genre and tag groups are collapsed `<details>` sections showing how many are selected) and `pick/choose` (client-only: the user gathers contenders by search or by loading a list/the queue, and `pickRandom` from `pick.ts` chooses among them, shown with the same shuffling-cards animation as the criteria mode (`Rolling` and `rollDelay` in `components/PickResult.tsx`); re-roll never repeats until all have been shown). Query keys group by area (`entries`, `entry`, `facets`, `platforms`, `search`, `playthroughs`, lists, slots, queue, wishlist); mutations invalidate the relevant groups. Every page sets its browser tab title with `usePageTitle()` (`lib.ts`) as `<page> | GameQueue` (e.g. `Collection`, a game's or list's name, `<username>'s Profile`), falling back to plain `GameQueue` until the name is known; a new page must call it. The lists page shows each list as a tile of its first four covers cut into equal vertical slices (`ListSummaryDto.covers`, cover image ids of the first games with a cover, from `listLists`) under a dark scrim holding the name and count; an empty list is a plain tile. Below the list tiles the lists page has a Smart lists section: the same tiles (`SmartListSummaryDto`), a New smart list button and, for each preset in `SMART_LIST_PRESETS` that the user doesn't have yet (matched by name), a one-click Add that creates an ordinary editable smart list. `SmartListPage` shows the rules in words, the matching games in the grid or row layout (read-only: membership is computed, so no reordering or removing), Random pick, Edit, Export CSV and Delete. `SmartListEditPage` edits name, rules and sort; each rule is a field select plus checkboxes (status, platform, genre, tag; options come from `GET /entries/facets`) or an at-least/at-most/unknown comparison and a number (time to beat is entered in hours), and a live preview evaluates the draft against the whole collection (`useEntries` with no filters) in the browser using the same `evaluateSmartList` as the server, so no preview endpoint exists. Confirmations use `useConfirm()` and dialogs use native `<dialog>` via `useModalDialog`. Platforms are shown as an icon plus short name (`PlatformTags`/`PlatformTag` in `components/PlatformIcon.tsx`, joined with other metadata by `MetaLine`). Icons are Simple Icons glyphs (CC0, v11.14.0, vendored as path strings in `platformIconPaths.ts`) or Lucide for web/arcade, mapped from IGDB platform ids in `platformIcons.ts`; platforms with no mapping (e.g. DOS, older Nintendo, Amiga) show text only. To add one, vendor its path and add the id to a family.

## Data model

SQLite via better-sqlite3, WAL mode, `PRAGMA foreign_keys = ON`. Schema in `apps/server/src/db/schema.ts`; migrations in `apps/server/drizzle/` run automatically when the DB is opened (startup and every test DB). Timestamps are epoch milliseconds; game dates are `YYYY-MM-DD` text.

**Shared game metadata cache** (no `user_id`; ids are IGDB ids):

| Table                           | Purpose                                                                                                                                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `games`                         | name, slug, summary, release date (+ `release_precision`: day/month/quarter/year, null = unknown; `release_checked_at`), cover `image_id`, IGDB rating, game type, time-to-beat (seconds), `fetched_at` |
| `platforms`, `genres`, `themes` | Lookup tables                                                                                                                                                                                           |
| `game_platforms/genres/themes`  | Many-to-many join tables, cascade on game delete                                                                                                                                                        |
| `series`                        | IGDB series ("collections"): id, name, `members_fetched_at`. Shared cache like `games`                                                                                                                  |
| `game_series`                   | `(game_id, series_id)`, cascade on both; which series a cached game belongs to (a game can be in several)                                                                                               |
| `series_members`                | `(series_id, game_id)` plus name, cover, release date/precision: IGDB's list of a series' main entries, cached for the series page. Not necessarily in `games`                                          |

**Per-user data** (every row carries `user_id`, directly or through its entry; all queries filter by it):

| Table                | Purpose                                                                                                                                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`              | username (unique, stored lowercase), email (unique), argon2id `password_hash`, `role` (`gamer` default or `admin`)                                                                                                        |
| `sessions`           | `id` = SHA-256 of the cookie token, `expires_at`; cascades with the user                                                                                                                                                  |
| `entries`            | A game in a user's collection: `status` (unplayed/playing/paused/finished/abandoned), `rating` 1-5 stars, notes, time-to-beat override. Unique per `(user_id, game_id)`                                                   |
| `entry_platforms`    | Platforms the user owns the game on                                                                                                                                                                                       |
| `tags`, `entry_tags` | Per-user tags, unique case-insensitively; unused tags are deleted when tags change                                                                                                                                        |
| `playthroughs`       | Per entry: platform, `started_on`/`ended_on` (nullable = unknown), `outcome` (null = open, finished, abandoned), rating. Partial unique index: at most one open playthrough per entry                                     |
| `slots`              | Named "currently playing" slots with `position`; `entry_id` holds at most one game. Partial unique index on `(user_id, entry_id)` so a game can't be in two slots; `ON DELETE set null` on the entry                      |
| `lists`              | User lists. `kind` is `list` or `queue`; a partial unique index allows one `queue` per user (created lazily by `ensureQueue`)                                                                                             |
| `smart_lists`        | Saved rules: `name`, `rules` (JSON, validated by `smartRulesSchema` on write), `sort`, `dir`. No items table: the matching games are computed from the collection on every read                                           |
| `list_items`         | `(list_id, entry_id)` primary key plus 0-based `position`; rewritten wholesale on reorder                                                                                                                                 |
| `avatars`            | A user's uploaded avatar: `user_id` (PK, cascade), `content_type`, `data` BLOB (a small client-made square image), `updated_at`. No row = generated identicon. Separate from `users` so user lookups never load the blob. |
| `wishlists`          | Games the user wants but doesn't own. A user's first wishlist (lowest id) is _the_ wishlist; `ensureWishlist` creates it lazily. No unique index per user, so several wishlists need no schema change                     |
| `wishlist_items`     | `(wishlist_id, game_id)` primary key plus 0-based `position`, optional target `platform_id` (`set null`), private `note`. Points at the shared `games` cache, not at an entry                                             |

Relationships to remember:

- A user owns entries; an entry points at a cached `games` row. Deleting an entry cascades to its platforms, tags, playthroughs and list items, and empties its slot.
- The backlog is not stored: it is every entry with status `unplayed`.
- **Smart lists** (`services/smart-lists.ts`, `packages/shared/src/smart-lists.ts`, routes `/api/smart-lists`: `GET /`, `POST /`, `GET|PUT|DELETE /:id`, `GET /:id/export.csv`): a smart list is a name, an AND-ed array of rules and a sort. Rules are `status`/`platform` (ids)/`genre`/`tag`/`finishedYear` any-of sets (`finishedYear` tests `EntryDto.finishedYears`, every year with a finished playthrough that has an end date, so it agrees with the profile's finished-by-year pages), or a number field (`ttb` in minutes, `igdbScore`, `rating`, `addedDays`, `changedDays`, `finishedDays`, `releaseYear`) with `gte`/`lte`/`unknown`; an unknown value never satisfies `gte`/`lte` (as with the pick's max time). "Days" fields count whole days back from now; `changedDays` uses `entries.updated_at`, which any status, rating, notes, tag or platform edit bumps (and import resets), so it means "last touched", not strictly "last played". Evaluation is pure over `EntryDto`s (`evaluateSmartList`): the service loads every entry once (`hydrate`) and filters and sorts in memory, which is fine at personal-collection scale and keeps one definition of "matches" for the server and the editor preview. Sorting puts missing values last whichever way it goes. A smart list holds no games, so it can't be reordered; the random pick can use it as a source (`source: {type: 'smart', smartListId}`) with the usual rule that only unplayed games, plus paused if asked, are candidates. They are collection-only and never include wishlist games.
- **Stats** (`services/stats.ts` loads the entries and the finished playthroughs, `computeStats` in `packages/shared/src/stats.ts` does the arithmetic; `GET /api/stats` for the owner, `GET /api/profiles/:username/stats` public, registered before `:view`): overview (counts, backlog size and summed time to beat of backlog games with a known time, average rating), games finished per year and over the last 12 months (a game counts once per period; playthroughs with unknown dates only appear under `unknown` in the yearly view), top-10 platform/genre/tag breakdowns with finished and unplayed counts, rating distribution and top-rated games, and an estimated play time. Play time is the time to beat summed over _finished playthroughs_ (replays count again), not tracked time. The DTO holds only counts and `PublicEntryDto`s, so the same payload serves the private and public pages.
- **Recap** (`services/recap.ts` loads the entries and every playthrough, `computeRecap` in `packages/shared/src/recap.ts` does the arithmetic; `GET /api/recap?year=` for the owner, `GET /api/profiles/:username/recap?year=` public, registered before `:view`; a malformed `year` is a 400): the "year in review". Without `year` it picks the current year if it has activity, else the latest one (`defaultRecapYear`); `years` lists every year with a finish, abandon, start or added game. A game counts once per year however often it was finished. Fields: finished/previous-year/abandoned/started/added counts, replays (finished games also finished in an earlier year), estimated play time (time to beat over the year's finished playthroughs, like stats), finishes per month and the busiest one, top 3 genres and platforms (the platform of the playthrough), best-rated finishes, longest/shortest game by time to beat, the longest start-to-finish haul (both dates known), first/last finish, every finished game, and a playful `archetype` (first matching rule of collector, marathoner, sprinter, returner, explorer, finisher, else steady). Unknown dates never count towards a year. The DTO holds only counts and `PublicEntryDto`s (no notes), so one payload serves the private and public pages.
- **Series** (`services/series.ts`, `routes/series.ts`, `SeriesPage`): a series is an IGDB _collection_ (type "Series"; franchises were deliberately not used, they mix spin-offs and media). `fetchGame` returns `collections`, `saveGame` stores them (`series` + `game_series`), and `GameDto.series` carries them. Games cached before this, and games saved from an import file (no series in the snapshot, so they are saved with `series_checked_at` null), are filled in by `backfillSeries`: one request per 100 games, run in the background at startup and after an import commit, one run at a time, failures retried next time. The collection/backlog sidebar has a Series facet (`?series=`, any-of like genre) offering only series with two or more of the user's games (or one already selected). `GET /api/series/:id` returns the series' games in release order (undated last): `series_members` (cached from IGDB, re-read after a week, stale data served if IGDB fails) plus any game of the series the user owns or wishlisted whatever its type, each with the user's entry (id, status, queued) and wishlist flag. `POST /api/series/:id/queue` appends the owned _unplayed_, not-yet-queued games to the queue in release order and returns `{added}`. The web page (`/series/:id`, linked from the game and entry pages) shows rows with a status badge, "queued", "On wishlist" or a Wishlist button; unowned games link to their IGDB game page, where they are added. Series are not in the export file (they come back from IGDB).
- **Screenshots** (`games.screenshots`, JSON array of IGDB image ids; `MAX_SCREENSHOTS` = 6 from `screenshots.image_id` in the game query, `mapScreenshots`): `GameDto.screenshots` (empty when unknown or none). Null in the column means IGDB was never asked: games cached before the column existed, and games saved from an import file. `ensureScreenshots` (`services/games.ts`) asks IGDB once for those when the game is opened (`GET /api/entries/:id`, `GET /api/igdb/games/:igdbId`), best effort, and stores `[]` when there are none. The `Screenshots` component sits under the cover on `EntryPage` and `GameDetailPage`: the first three as a single column of thumbnails in their own proportions (`720p`, since the `screenshot_*` sizes crop to 16:9), a click opens a native-`<dialog>` lightbox at 1080p with previous/next (buttons and arrow keys) over all of them. Hidden under 760px, where the page is one column (the hidden images aren't downloaded). Not in the export file.
- **Release dates** (`packages/shared/src/release.ts`, `mapRelease` in `igdb/mappers.ts`, `refreshReleaseDates` in `services/games.ts`): IGDB has one timestamp per release, and for a vague release it is a placeholder (a game announced for "2028" is 2028-12-31), so `games.release_precision` records how exact it is, from the `date_format` of the per-platform `release_dates` that carry `first_release_date` (the most exact wins; TBD means no date). Quarter and month are read from the date's own month, so it doesn't matter whether IGDB puts the placeholder at the start or the end of the period. The wishlist shows `releaseLabel` ("Nov 19, 2026", "Nov 2026", "Q4 2027", "2028", "TBA") in the meta line and, over the cover of every game not out yet, a `ReleaseBadge` (`releaseBadge`: "in 6 days", "in 3 weeks", "in 3 months", "in 2 years" for an exact day; the vague date itself for month/quarter/year/TBA, since a count would claim too much; nothing once released). The home page's "Releasing soon" section (`ReleasingSoon`, under Up next) reuses `useWishlist` and lists wishlisted games whose exact release day (`releasesWithin`: day precision only, today through 14 days ahead) is coming up, soonest first, as covers with the same badge; it is hidden when there are none. The badge is a fixed dark pill on tiles (top right) and a strip along the bottom of the 64px cover in rows. `GET /api/wishlist` first calls `refreshWishlistReleases`: cached games that aren't released yet (`isReleased` = the whole period is over; no date counts as unreleased) and weren't checked in the last 24h are re-read from IGDB in one request, and `release_checked_at` is stamped. It is best effort (IGDB errors are logged and the cached dates are served) and only runs for the owner's own wishlist; the public wishlist shows what is cached. Rows saved before the column existed have a null precision (shown as an exact day) and are refreshed once if unreleased; imported rows are saved unchecked, so they refresh on the next wishlist load.
- The wishlist is deliberately not part of the collection: wishlisted games have no entry, so they are not in the collection, backlog, stats, random pick, slots or lists. The two are kept disjoint: wishlisting an owned game is a 409 carrying the `entryId`, and adding a game to the collection (`addEntry`, or an import) removes it from the user's wishlists (`dropFromWishlists`). Service functions take a `wishlistId`; only the routes resolve "the" wishlist.
- Status is kept consistent with playthroughs by `syncStatus`; slot rules are enforced in `services/playthroughs.ts` and `services/slots.ts` (a slotted game is always `playing` or `paused`; starting a game removes it from the queue).
- Registering a user also inserts the default slots (`DEFAULT_SLOT_NAMES`).

**Changing the schema**: edit `schema.ts`, run `npm run db:generate`, commit the new SQL. Check generated SQL for added FK columns: drizzle-kit drops `ON DELETE` from `ALTER TABLE ... ADD COLUMN ... REFERENCES` on SQLite and it must be patched by hand (see `0003`).

**Export/import** (`services/export.ts`, `services/import.ts`, `packages/shared/src/export.ts`, routes `/api/data/*`): one versioned JSON file (`format: gamequeue-export`, `version: 1`) with a metadata snapshot per game so import never calls IGDB. Smart lists travel as an optional top-level `smartLists` (name, rules, sort, dir; no games, since those are computed), merged by case-insensitive name so ones you already have are left alone. The wishlist travels as an optional top-level `wishlist` (in order, each item with its own snapshot (the game snapshot's `releasePrecision` is optional), target platform and note), so files without it are still valid v1; import appends missing games to the end of the existing wishlist, fills only empty platform/note fields, and skips games you own. Import is a merge matched on `igdb_id`, list and slot names, and playthrough platform+dates+outcome. `POST /api/data/import` is a dry run unless `?commit=true`; the dry run runs the real merge in a transaction and rolls it back. Changing the format means bumping `EXPORT_VERSION` and keeping a reader for the old one.

**CSV export** (`packages/shared/src/csv.ts`, `csvResponse` in `http.ts`): `GET /api/lists/:id/export.csv` (works for the queue too, via its list id), `GET /api/smart-lists/:id/export.csv` and `GET /api/data/export.csv` (the whole collection, by title) return one row per game in list order: title, status, platforms, tags, genres, rating, IGDB score, time to beat in hours, release date, added, last finished, playthrough count, notes and IGDB id. It's a read-only spreadsheet export, not an import format. The file is UTF-8 with a BOM (so Excel reads it correctly) and CRLF row endings, and text cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading apostrophe so a spreadsheet can't run them as formulas.

## Auth and sessions

- **Accounts**: `POST /api/auth/register` (403 when `SIGNUPS_ENABLED=false`) hashes the password with argon2id (`@node-rs/argon2`, parameters pinned in `auth/password.ts`), inserts the user and default slots in one transaction (the unique username and email indexes are the duplicate check; failure is a generic 409). Usernames are 3-30 chars of `a-z 0-9 _ -`, lowercased by `usernameSchema`; email is kept but is not used to log in, then logs the user in. `GET /api/auth/config` (public) returns `{signupsEnabled}`; the web login page hides its "Create an account" link, and `/register` redirects to `/login`, when it is false.
- **Login** (`POST /api/auth/login`): checks two in-memory `FailureLimiter`s first (per `username|ip`: 5 failures / 15 min; per IP: 30 / 15 min; 429 with `Retry-After`). It always runs an argon2 verify, against a dummy hash if the username is unknown, so timing doesn't reveal which accounts exist. Wrong credentials return one generic 401. Success resets the per-account counter. The client IP comes from the socket, or from `X-Forwarded-For` only when `TRUST_PROXY=true`. The limiters are per process, which is fine for a single-instance deployment.
- **Sessions** (`auth/sessions.ts`): on login a random 32-byte token is generated; only its SHA-256 hash is stored (`sessions.id`), so a DB leak doesn't yield usable cookies. The raw token goes to the browser in the `gq_session` cookie (httpOnly, SameSite=Lax, `Secure` when `NODE_ENV=production`, path `/`). TTL is 30 days, sliding: when less than half remains, the expiry is extended and the cookie re-issued. Expired sessions found on lookup are deleted, and a periodic purge removes the rest.
- **Per-request auth** (`auth/middleware.ts`): `requireAuth` reads the cookie, calls `resolveSession`, and sets `c.var.user = {id, username, email}`. A missing or invalid session returns 401 (and clears a stale cookie). Handlers get the user id from `c.get('user')`; every service query is scoped by it.
- **Roles and admin** (`users.role`, `USER_ROLES` in shared: `gamer` is the default standard user, `admin` also gets the admin area): `resolveSession` joins `users`, so `c.var.user` carries the current role and a grant or revoke applies to live sessions at once. `requireAdmin` (`auth/middleware.ts`) is used after `requireAuth` on admin-only routers (`routes/admin.ts`, mounted at `/api/admin`): 401 when signed out, 403 `Admin access required` for a gamer. `UserDto.role` is only a UI hint: the web `Shell` shows the Admin link, and `App` routes `/admin` (`AdminPage`, the dashboard: a Users tile with counts and a Backups panel; `admin/users`, `AdminUsersPage`, the list; `admin/users/new` and `admin/users/:id`, `AdminUserPage`), only when it is `admin`; the server is what enforces it. **Backup status** (`GET /api/admin/backup`, `services/backup-status.ts`, `packages/shared/src/backup.ts`): `scripts/backup.sh` writes `backup-status.json` next to the database (in the mounted `/data`, atomically via a temp file and `mv`) at the end of every run, also when it fails (an `EXIT` trap records the failing step): `lastRunAt`, `ok`, `error`, `lastSuccessAt` (carried over from the previous file so a failure doesn't erase it), the snapshot `file` and `sizeBytes`, and `offsite` (`uploaded`, `not-configured`, `failed`). The app only reads it (the container has no `sqlite3` or `rclone`, and the backups directory isn't mounted): the route returns `{backup, unreadable}`, with `backup: null` when the file doesn't exist yet and `unreadable: true` when it isn't valid. `backupHealth` (shared, pure) turns it into `healthy`, `no-offsite`, `stale` (no success in 26 hours, as the job runs nightly) or `failed`/`never`; the Backups panel on `AdminPage` shows that as a coloured banner (icon and text, not colour alone) plus last run, last success, off-site state and latest snapshot, with a skeleton while loading. The app can only report, not start a backup. If `HEALTHCHECK_URL` is set (read by name from `.env`, or the environment), the script also pings healthchecks.io (`/start`, success, `/fail` with the error), which covers a dead Pi or cron that the admin page can't. **Database stats** (`GET /api/admin/database`, `services/database-stats.ts`, `DatabaseStatsDto` in shared): file and WAL size from the filesystem, page size/count and free pages from pragmas, row counts for the IGDB cache (`games`, how many are referenced by an entry or wishlist item, series, series members, platforms/genres/themes, oldest and newest `fetched_at`) and for what users store (entries, playthroughs, lists, avatars and their bytes, sessions and expired ones), plus every table's row count and bytes (SQLite's `dbstat` virtual table, each index folded into its table), largest first. Computed on request, nothing stored. The dashboard's Database tile shows size, cached games and table count and links to `AdminDatabasePage` (`/admin/database`, with a skeleton).
  **User management** (`/api/admin/users`, `services/admin-users.ts`, schemas in `packages/shared/src/admin-users.ts`): `GET /users`, `GET /users/:id` (`AdminUserDto`: `UserDto` plus `createdAt` and `gameCount`; never the hash), `POST /users` (`{username, email, password, role}`; creates the default slots like register and works with `SIGNUPS_ENABLED=false`), `PATCH /users/:id` (all of username, email, role, real name fields and the four gaming accounts, validated by the same schemas users use themselves; avatars are not editable), `PUT /users/:id/password` (no current password needed; deletes all of the user's sessions, except the requesting one when an admin resets their own) and `DELETE /users/:id` (FK cascades, as in account deletion). Duplicate username/email is a 409 with `details` naming the field. Guards: an admin can't delete themselves here (the Account page does that) and the last admin can't be demoted or deleted, so the instance can't lock itself out. A role change applies to live sessions at once. The Users tile on the `AdminPage` dashboard shows user, admin, joined-in-30-days and game totals (computed in the browser from `GET /users`, so no stats endpoint) and links to `AdminUsersPage`, which lists everyone (both with skeletons); `AdminUserPage` has the details form, a reset-password panel and a danger-zone delete (both behind `useConfirm`). Promoting the very first admin still needs SQL (see DEPLOYMENT.md, "Making a user an admin").
- **Public profile** (`GET /api/profiles/:username`, `routes/profile.ts` + `services/profile.ts`): no login. Returns username, join date, slot contents, a count per status plus the queue length (the web page shows these as icon stat tiles plus a status bar) the user's lists with their games and their smart lists (name, rules in words, and the games matching right now), as `PublicEntryDto` (no notes, email or slot/list internals). Unknown or malformed usernames are 404. It is read-only: it never calls `ensureQueue`. `GET /api/profiles/:username/:view` (`view` is one of `PROFILE_VIEWS`: queue, collection, backlog, playing, paused, finished, abandoned; anything else is 404) returns that list of games as `PublicEntryDto`: the queue in queue order (empty if they never queued anything), the rest by title. Each stat tile on the profile links to its web page `/u/:username/:view` (`ProfileGamesPage`, all rendering through the shared `PublicGameList` component, so layout tweaks happen in one place; it offers a cover-art grid, the default, or the row list (hover or focus a cover for name, status and rating), remembered in `localStorage`; while loading it shows shimmering skeletons built on the real list classes, with the layout selector and page heading always visible; real items fade in with a short stagger (`--i` per item, off for reduced motion)). The finished view is special: `GET /api/profiles/:username/finished` lists games whose status is finished, newest finish first (unknown dates last), and `GET /api/profiles/:username/finished/:year` (`:year` is four digits or `unknown`, otherwise 404) lists games with a _finished playthrough_ ending that year, oldest finish first, once per game per year, so a replayed or restarted game stays on its old year pages. Both carry `years` (`{year, count}`, newest first, `unknown` last) which the web page (`/u/:username/finished[/:year]`) renders as a year link row. `GET /api/profiles/:username/wishlist` (registered before `:view`; web `/u/:username/wishlist`) returns the wishlist in order as `PublicWishlistItemDto` (game and target platform, never the note), empty if they never created one; the summary carries `wishlisted` for the profile's "On wishlist" tile. Everything is public; there is no visibility setting.
- **Avatars**: every user has a procedural identicon derived from their username, so nothing is stored and no endpoint exists. `generateIdenticon` (`packages/shared/src/avatar.ts`) hashes the lowercased username (FNV-1a) into a seeded PRNG and returns a hue plus a left-right mirrored 5x5 cell grid; the web `Avatar` component (`components/Avatar.tsx`) draws it as an SVG whose colours come from `--avatar-h` and the light/dark rules in `app.css`. It is decorative (`aria-hidden`; the username is always beside it) and shows in the sidebar user link and the profile hero (with a matching skeleton). Users can replace it with an uploaded picture. The web `AccountPage` (`/account`, linked as "Account" in the sidebar) crops the chosen image to a centred square and re-encodes it to 256px WebP (JPEG where the browser can't encode WebP) in the browser (`avatarImage.ts`, which also drops EXIF/GPS), shrinking quality until it fits `AVATAR_MAX_BYTES` (128 KB), then `PUT /api/avatar` sends `{contentType, data(base64)}` as JSON (the API takes only JSON bodies); `DELETE /api/avatar` goes back to the identicon. The server (`routes/avatar.ts`, `services/avatars.ts`) accepts only png/jpeg/webp, checks the magic bytes match the declared type and the size, and upserts the `avatars` row. `GET /api/profiles/:username/avatar` is public and serves the bytes with `nosniff` and an immutable cache header; callers add `?v=<updatedAt>` (`avatarUrl`), taken from `UserDto.avatarUpdatedAt` (`/auth/me`, login) or `ProfileDto.avatarUpdatedAt` (null = no upload), so a new upload is a new URL. `Avatar` renders the `<img>` when a version is set and falls back to the identicon if it fails to load. Uploaded avatars are not part of the export file.
- **Real name** (`users.first_name`, `last_name`, `show_real_name`; all optional, private by default): `PATCH /api/account` (`routes/account.ts`, `services/users.ts`) takes `{firstName, lastName, showRealName}` (`accountProfileSchema`: trimmed, inner whitespace collapsed, max 50, no control characters, empty = unset). `getUserDto` builds the `UserDto` for `/auth/me`, login and register, so it always carries the name fields. `ProfileDto.realName` is the joined name only when `show_real_name` is on (null otherwise, so the name never reaches the public API without the opt-in), shown as the profile hero's heading, with the username beneath it in smaller muted text (the username is the heading when there is no shown name). The `AccountPage` has the two fields and the checkbox. The first name (`useFirstName()`, `greeting()` in `lib.ts`) personalises the home subtitle (time-of-day greeting) and the Random pick subtitle; everything falls back to the plain text when it isn't set. Names are not in the export file.
- **Password change** (`PUT /api/account/password`, `routes/account.ts`, `changePassword` in `services/users.ts`; `changePasswordSchema`): needs the current password and a new one meeting the usual rules (different from the current). A wrong current password is a 400 with `details` on `currentPassword` (not a 401, which the web client treats as signed out) and counts against the shared login failure limiter under key `password|<userId>` (5 per 15 minutes, then 429). On success the hash is replaced and every _other_ session of the user is deleted in the same transaction; the requesting session stays. The Account page has a Password panel (current, new, confirm; the confirm check is client-side).
- **Account deletion** (`DELETE /api/account` with `{password}`, `deleteAccount` in `services/users.ts`): re-checks the password (wrong = 400 with `details` on `password`, counted by the same limiter as the password change) and deletes the `users` row; every table that belongs to the user (entries and everything under them, slots, lists, wishlist, tags, smart lists, avatar, sessions) goes through `ON DELETE cascade`, and `test/delete-account.test.ts` checks that no table keeps a row for them and that other users are untouched. The shared game cache stays. The session cookie is cleared and the web client sets `me` to null, which drops it on the login page. The Account page's red Delete account panel asks for the password, then a `useConfirm` danger dialog, and links to the export page first. Anything new that is keyed by `user_id` must cascade, or this breaks.
- **Gaming accounts** (`users.steam_id`, `xbox_gamertag`, `psn_id`, `discord_name`, all optional; `social.ts` in shared): `PUT /api/account/social` takes `{steam, xbox, playstation, discord}` (`socialLinksSchema`: trimmed, leading `@` dropped, empty = unset, and a strict pattern per service because the values end up in links on a public page; failures are a 400 with per-field `details`). They are on `UserDto.socialLinks` and always on `ProfileDto.socialLinks` (there is no per-account visibility: filling one in publishes it, and the Account form says so). `socialUrl` builds the link: Steam `steamcommunity.com/id/<name>` (or `/profiles/<id64>` for a 17-digit id), Xbox `account.xbox.com/en-us/profile?gamertag=`, PlayStation `profile.playstation.com/<id>` (Sony's own profile page), values URL-encoded; Discord has no profile URL by name, so it is a copy-to-clipboard chip. `SocialLinksList` renders the chips (external links `rel="noopener noreferrer"`, brand glyphs from Simple Icons) under the name in the profile hero. Not in the export file.
- **Logout** (`POST /api/auth/logout`) deletes the session row and clears the cookie. `GET /api/auth/me` backs the web app's `useMe()` gate.
- **CSRF**: see the origin/content-type guard under Request flow.

## IGDB communication

All IGDB access is server-side; the browser never talks to IGDB or sees credentials. Code is in `apps/server/src/igdb/`, behind the `IgdbClient` interface (`search`, `fetchGame`, `fetchReleaseDates`, `fetchGameSeries`, `fetchSeries`, `fetchPlatforms`) so tests inject a fake. If `IGDB_CLIENT_ID` / `IGDB_CLIENT_SECRET` are unset, `igdb` is undefined and IGDB-backed endpoints return 503 (`requireIgdb`).

- **Token** (`token.ts`): Twitch client-credentials flow (`id.twitch.tv/oauth2/token`). The token is cached in memory and refreshed an hour before expiry; concurrent callers share one refresh. A 401 from IGDB invalidates it and retries once.
- **Rate limiting** (`limiter.ts`): every request goes through `RequestLimiter`, a queue that starts at most 4 requests per rolling second with at most 8 in flight (IGDB's documented limits). A 429 response is retried up to 3 times, honouring `Retry-After`.
- **Requests** (`client.ts`): POST to `https://api.igdb.com/v4/<endpoint>` with `Client-ID` and bearer headers, APICalypse bodies (user text escaped by `quote`).
    - `search`: `games` endpoint, text search with `version_parent = null` (drops editions), limit 30, then filtered by `isCollectable` and cut to 20.
    - `fetchGame`: one `/multiquery` combining the game and its `game_time_to_beats` row (seconds).
    - `fetchReleaseDates`: `first_release_date` plus per-platform `release_dates` for up to 100 ids per request, used only by the release refresh below.
    - `fetchGameSeries`: `collections` of up to 100 games per request, for the backfill below.
    - `fetchSeries`: one collection's name plus its games limited to `SERIES_GAME_TYPES` (Main Game, Standalone Expansion, Remake, Remaster; `version_parent = null`), up to 500, with release dates and covers.
    - `fetchPlatforms`: the full platform list.
- **Mapping** (`mappers.ts`): raw IGDB shapes become `GameRecord` / `IgdbSearchHit`. Only add-on game types are excluded (`EXCLUDED_TYPES`: DLC, Mod, Pack / Addon); see the comment there before changing it. Covers are kept as `image_id` only and turned into URLs by `packages/shared/src/igdb-images.ts`.
- **Search flow** (`routes/igdb.ts`): `GET /api/igdb/search?q=` checks a 5-minute, 200-entry `TtlCache` keyed by lowercased query, otherwise calls IGDB. The result is then annotated per user with the `entryId` of already-collected games and a `wishlisted` flag (never cached, since both are per user).
- **Game by id** (`GET /api/igdb/games/:igdbId`): `ensureGame` (so IGDB is called only for a game never cached, one multiquery) then the cached `GameDto` plus the user's `entryId` and `wishlisted` (`GameDetailDto`). Viewing a game therefore caches it in the shared `games` table even if it is never added; ownership lives in `entries`, so nothing treats a cached game as owned.
- **Adding a game** (`addEntry` -> `ensureGame` in `services/games.ts`): if the game isn't in the shared `games` table, `fetchGame` is called and `saveGame` writes it and its relations; cached metadata is never re-fetched, with one exception: release dates (below). IGDB failures are wrapped by `callIgdb` as 502. The entry is then created with the chosen platforms, and tags default to the game's genres and themes.
- **Platforms** (`listPlatforms`): `GET /api/igdb/platforms` serves the platform table, doing a one-time full sync from IGDB when it holds fewer than 50 rows (only games' own platforms so far).
- **Import** never calls IGDB; it writes snapshot metadata from the file into the cache for games not cached yet (existing rows are never overwritten).
