# Architecture

How GameQueue is put together. `CLAUDE.md` holds the working notes and product decisions; this file explains the structure and the main flows. New to the codebase? Read `OVERVIEW.md` first: a gentler, diagram-led tour of the same subsystems. **Keep it up to date whenever functionality is added or changed** (new routes, tables, services, auth or IGDB behaviour, web pages).

## Repo layout

npm workspaces monorepo.

```
apps/
  server/            Hono API + Drizzle (SQLite)
    src/
      index.ts       Entry point: load config, open DB, build app, serve built web, start listening
      app.ts         createApp({db, config, igdb}): middleware, route mounting, error handler
      config.ts      Env vars -> Config
      web.ts         Production serving of the built web app: static files + SPA fallback (adds link-preview tags, robots rules)
      og/            Share cards: satori layout (cards.ts), resvg PNG + LRU (render.ts), cover/font loading, meta tags (meta.ts)
      errors.ts      HttpError (status + message + extra JSON)
      http.ts        validate(zodSchema, value), parseId
      auth/          password hashing, sessions, requireAuth middleware, login and request rate limiters, client IP
      db/            schema.ts (Drizzle tables), client.ts (open + migrate)
      igdb/          IGDB client, token provider, request limiter, mappers, search cache
      mirror/        IGDB data-dump mirror: dump source, streaming CSV import, `igdb.db` schema, build + atomic swap, the job + CLI that report to `mirror-status.json`; reader + `IgdbClient` wrapper that answers from it
      routes/        Thin HTTP layer: parse + validate input, call a service, return JSON
      services/      Business logic; all DB work lives here
    drizzle/         Generated SQL migrations (committed)
    test/            Vitest suites + helpers (in-memory SQLite, fake IGDB)
  web/               React + Vite + TanStack Query + React Router
    src/
      main.tsx       Providers: QueryClient, Router, ConfirmProvider
      App.tsx        Auth gate + route table
      api/           fetch wrapper (client.ts) and TanStack Query hooks per area
      routes/        One component per page
      components/    Shared UI (dialogs, playing card, score gauge, ...)
      styles/        tokens.css (design tokens, light/dark: three surface levels bg-0..bg-3, text, line, accent, and one `--status-*` colour per game state), app.css
packages/
  shared/            Zod schemas, DTO types and pure logic used by both apps (consumed as TS source)
```

`packages/shared` is the contract between the two apps: request schemas (`addEntrySchema`, `loginSchema`, ...), response DTOs (`EntryDto`, `SlotDto`, ...), the export file schema, status rules (`status.ts`), the random-pick algorithm (`pick.ts`, pure with an injectable RNG), smart-list rules and their evaluator (`smart-lists.ts`, pure with an injectable clock; also runs in the web editor's live preview), the CSV writer (`csv.ts`), the stats computation (`stats.ts`, pure), the year-in-review computation (`recap.ts`, pure), the avatar identicon generator (`avatar.ts`, pure), the preset avatar icons and colours (`avatar-icons.ts`) and IGDB image URL helpers. There is no build step for it; both apps import the TypeScript directly.

Useful commands: `npm run dev` (server :3000 + web :5173, Vite proxies `/api`), `npm run build && NODE_ENV=production npm start` (one process serves API and built web), `npm test`, `npm run typecheck`, `npm run db:generate`.

## Request flow

```
Browser
  -> React component calls a TanStack Query hook (apps/web/src/api/*.ts)
  -> api() in client.ts: fetch('/api/...'), same-origin cookies, JSON body
  -> Hono app (apps/server/src/app.ts)
       1. csrf() on /api/*
       2. origin + content-type guard for POST/PUT/PATCH/DELETE
       3. router matched by prefix
       4. requireAuth(db, config)   (every router except /api/auth, /api/health and /api/profiles)
       5. route handler: validate(sharedSchema, input) -> service function(db, userId, ...)
  -> service reads/writes SQLite via Drizzle, returns a DTO
  -> JSON response; errors thrown as HttpError (or Zod failures via validate) are turned into
     { error, ...extra } by app.onError; anything else is a 500
  -> mutation hook's onSuccess invalidates related query keys, so the UI refetches
```

Details:

- **Route mounting** (`app.ts`): `/api/auth`, `/api/admin` (admin role only), `/api/igdb`, `/api/entries` (two routers share the prefix: CRUD and playthrough/status actions), `/api/playthroughs` (edit/delete, plus a playthrough's posts and visibility), `/api/posts` (the owner's posts and images), `/api/lists`, `/api/smart-lists`, `/api/queue`, `/api/wishlist`, `/api/discover`, `/api/series`, `/api/stats`, `/api/recap`, `/api/pick`, `/api/data`, `/api/ai` (game helper), and the public `/api/profiles`, `/api/journals`, `/api/showcase` and `/api/og`. Each router applies `requireAuth` itself; `requireAuth` is a no-op if an earlier router on the same prefix already authenticated the request. Mount new routers under a specific prefix, never a `use('*', requireAuth)` router at `/api`, which would also gate login.
- **Pagination** (`packages/shared/src/pagination.ts`, `usePagedQuery` in `apps/web/src/api/paging.ts`, `LoadMore` component): every endpoint that returns games takes `?limit=&offset=` (`pageQuerySchema`: default 48, max 200) and answers with one page plus `total` (the whole match count): `GET /api/entries` (`pageEntries`), `GET /api/lists/:id` and `GET /api/queue` (`getList`), `GET /api/smart-lists/:id`, `GET /api/wishlist`, and on the public profile `/:username/:view`, `/:username/wishlist` and the per-list `/:username/lists/:id` and `/:username/smart-lists/:id` (the profile itself shows each list and smart list only as a tile, `ProfileListTileDto`: name, total and a few covers, like the Lists page's `ListCard`; a tile links to `/u/:username/lists/:id` or `/smart-lists/:id`, `ProfileListPage`, which pages the games). Offset paging is enough here: one user's data, and clients only ever load a contiguous prefix. Server-side callers that need everything (stats, recap, pick, exports, smart-list evaluation) call `listEntries`/`getList`/`wishlistItemsOf` without a page. Mutation responses return the first page. The web uses `useInfiniteQuery` with a "Load more" button (not scroll-triggered, so the footer stays reachable and navigating back keeps the loaded pages in the query cache). A page's first response also carries the list's own fields (name, years…), which `usePagedQuery` exposes as `head`. Purpose-built endpoints replace "fetch everything and filter" in the client: `GET /api/wishlist/releasing-soon?days=&today=` (home page), `POST /api/smart-lists/preview` (the editor's live preview; rules and sort in the body), and `GET /api/entries/facets` carries `finishedYears`.
- **Lists hold any game** (`services/lists.ts`): items are `(list_id, game_id)` and addressed by IGDB id: `POST /api/lists/:id/items {igdbId}` (`addGameToList` caches the game through `ensureGame` first, never for a refused queue add), `DELETE /api/lists/:id/items/:igdbId`, `PUT /api/lists/:id/move {igdbId, toIndex}`, `PUT /api/lists/:id/order {igdbIds}`; `/api/queue/*` mirrors them with `igdbId`. `getList` returns `ListDetailDto.items` of `{igdbId, game, entry | null}` (`itemsFor`: the owned entry hydrated through `hydrate`, else `loadGames`); `entry` is found by `(user_id, game_id)`, so `EntryDto.lists`/`queued` are computed by the same join. The queue refuses a game the user doesn't own (400). Deleting an entry calls `dequeue` for its game and leaves regular lists alone, so those games stay as ones the user no longer owns. Server-side callers that want the owned games only use `ownedEntries(items)` (CSV export, pick, public queue page). `POST /api/pick` from a list picks among its owned games of any status (narrowed by `filters.statuses`) and returns `skippedUnowned` (the list games it could not consider), which the web shows in the result note. The result also carries `poolStatuses` (the source's owned games by status before filtering) so an empty result can say why, e.g. "2 games are here, but none are Not Started (1 paused, 1 finished)" with a hint about the paused toggle. `purgeUnusedGames` and the database stats count `list_items` as a use of a cached game. Export/import: list games travel as IGDB ids whether or not they are in `games` (the cross-reference check in the schema applies to the queue only), the importer adds them to `fileGameIds` so they are looked up like any other game, and ones IGDB doesn't know are skipped with a note. Public `GET /api/profiles/:username/lists/:id` returns `items` with `status`/`rating` null for games the owner doesn't have (`PublicListItemDto`). Web: the list page's add box searches IGDB (`useGameSearch`) for regular lists and the collection for the queue; unowned rows and tiles say "Not in collection" and link to `/games/igdb/:id`.
- **List descriptions**: `POST /api/lists` takes an optional `description`; `PATCH /api/lists/:id` takes `name` and/or `description` (whatever is left out stays; the queue can't be edited); smart lists carry it in their `PUT`/`POST` body. It is shown under the title on the list pages and on the public list pages (so it is public like the rest of a list), and it is in the export file as an optional `description` on `lists` and `smartLists` (still format v1). Import fills an empty description on a list you already have and never overwrites one.
- **Reordering** (queue, lists, wishlist): `PUT /api/lists/:id/move`, `/api/queue/move` and `/api/wishlist/move` take one item and an absolute `toIndex` (`moveInOrder` in `services/order.ts`; only the rows between the old and new place are rewritten), so they work while only the first pages are loaded. The old whole-list `PUT .../order` still exists for API callers; the web no longer uses it. Because the client holds a contiguous prefix, an index in the loaded items is also the item's index in the whole list, and drag-and-drop can only move within what is loaded.
- **Request body limit** (`app.ts`, `MAX_JSON_BODY_BYTES` = 256 KB): Hono's `bodyLimit` on all of `/api/*`, checked against `Content-Length` and, when a body has none, while it streams in; past it a 413 `Request body too large` before the body is read. Without it `c.req.json()` read whatever arrived (Cloudflare passes up to 100 MB), so a few requests to the public login route could exhaust the Pi's memory (security review, `docs/archive/REVIEW.md`). The largest legitimate bodies are the API-only full reorders (`PUT .../order`, ~30,000 ids) and avatar uploads (~196 KB). `/api/data/import` is exempt (`OWN_BODY_LIMIT`) and keeps its own 50 MB limit; it sits behind `requireAuth`, which answers before the body is read. The screenshot upload (`POST /api/posts/:id/images`, matched by `IMAGE_UPLOAD_PATH` in `routes/journal.ts`) has its own 8 MB limit (`MAX_UPLOAD_BYTES`) and is the one route that may carry an image `Content-Type` (JPEG, PNG, WebP) instead of JSON: images are not form types, so a cross-site form can't send them and a script needs a CORS preflight, and the `Origin` check applies to it like any mutation.
- **CSRF**: Hono's `csrf()` only checks form content types, so `app.ts` additionally rejects mutations whose `Origin` isn't same-origin or in `ALLOWED_ORIGINS` (403), and any body that isn't `application/json` (415). Body-less mutations (DELETE, logout) need an `Origin` header; browsers send one, curl and tests must add it.
- **Security headers** (`secureHeaders` at the top of `createApp`, so on every response, the web pages included): `X-Frame-Options: DENY` plus `Content-Security-Policy: frame-ancestors 'none'` (nothing is meant to be framed; stops clickjacking on Account and admin), `X-Content-Type-Options: nosniff` and an explicit `Referrer-Policy: strict-origin-when-cross-origin`. The other `secureHeaders` defaults are off on purpose: HSTS is Cloudflare's job, and a resource or opener policy could break link-preview images or OAuth-style popups later.
- **Validation**: input schemas live in `packages/shared` and are applied with `validate()`; failure is a 400 with `details: [{path, message}]`.
- **Errors**: `HttpError(status, message, extra)` is thrown from services. Statuses in use: 400, 404, 409 (e.g. already collected; `extra` carries the conflicting data), 502 (IGDB down), 503 (IGDB not configured). Throwing inside `db.transaction` rolls it back.
- **Transactions**: services call each other inside `db.transaction` (Drizzle uses savepoints for nesting). For example `startPlaythrough` dequeues the game in the same transaction. `POST /entries/:id/start` also accepts `paused: true` (open the playthrough already paused, for a game started before tracking; the game page offers it for unplayed games as "Mark paused"). The game page's "Mark abandoned" for an unplayed game is just `POST /entries/:id/playthroughs {outcome: 'abandoned'}` with unknown dates.
- **Services** (`apps/server/src/services/`): `entries` (collection CRUD, listing/filtering, facets, tags, hydrating `EntryDto`), `playthroughs` (status transitions, history, `syncStatus`), `lists` (lists and the queue), `smart-lists` (saved rules, evaluation, export rows), `wishlist`, `stats`, `recap`, `pick`, `games` (IGDB-backed metadata cache, plus `loadGames`, which builds `GameDto`s from it for entries and wishlist items alike), `export`, `import`.
- **Production serving** (`index.ts`): if the built web dir exists (`WEB_DIST`, default `../web/dist`) it is served statically with an SPA fallback to `index.html` (`web.ts`, `mountWeb`).
- **Share cards / link previews** (`og/`, `routes/og.ts`, `services/og.ts`, `web.ts`): crawlers (Discord, Twitter, Slack) don't run the SPA, so the SPA fallback in `web.ts` adds `<title>`, `og:*` and `twitter:*` tags to `index.html` for `/u/:username` and `/u/:username/recap[/:year]` (`pageMeta`/`injectMeta` in `og/meta.ts`; unknown users and every other path get the plain shell, and a failure while building tags is logged and the plain page served). `og:image` points at the public, login-free `GET /api/og/profile/:username.png` or `GET /api/og/recap/:username/:year.png` (1200x630; anything else, including a missing `.png`, is a 404). Absolute URLs use `PUBLIC_URL` (default: the first `ALLOWED_ORIGINS` entry). The card shows only public, reduced data (`services/og.ts`: `profileCardData`/`recapCardData`; counts, genre names, the username and cover art, never game titles or notes, which also keeps it to glyphs the bundled fonts have). The sha1 of that data is `cardKey`: it is the `?v=` in the `og:image` URL (so a changed profile is a new URL for the unfurlers' own caches) and the key of the in-memory LRU (`og/lru.ts`, 32 cards, roughly 20 MB; concurrent requests for one key share a single render). Nothing is written to disk. Layout is plain objects for satori (`og/cards.ts`: flexbox-only CSS, Bricolage Grotesque and Figtree static WOFF from `@fontsource/*`, since satori can't read WOFF2 or variable fonts) rasterised by `@resvg/resvg-js` (`og/render.ts`). Cover art is fetched from the IGDB CDN as data URIs (`og/covers.ts`, own small LRU, 4 s timeout; a failed fetch draws a placeholder, never an error). Uploaded avatars are converted to PNG with `sharp` first because resvg silently draws nothing for WebP; a corrupt upload falls back to the identicon.
- **Search engines** (`seo.ts`, `web.ts`): `GET /robots.txt` (production only, from `mountWeb`) disallows `/api/` except `/api/og/` (share-card images stay fetchable for link previews). The app and profile pages are deliberately _not_ disallowed in `robots.txt`: a crawler must fetch a page to see its `noindex`, and a blocked URL can still be listed. The indexing rules live in `pageSeo` (used by the SPA fallback): `/` is indexable and gets a description, canonical and text-only (`twitter:card=summary`) tags; `/u/:username/...` is indexable only when that user ticked **Allow search engines to index my public profile** (`users.search_indexable`, default off; `PUT /api/account/search-indexing {searchIndexable}`, Account page, `UserDto.searchIndexable`), otherwise it is served with `X-Robots-Tag: noindex`; a username that doesn't exist is a real 404 (still with the app shell, so the web app shows its not-found page); everything else (login, register, the signed-in app) is `noindex`. Link-preview and canonical tags are added whatever the opt-in, so shared links keep their previews. Not done yet: sitemap, server-rendered landing/profile content, JSON-LD. Unknown top-level paths still return 200 with the shell (the server doesn't know the web routes), but are `noindex`.
  Expired sessions are purged at startup and every 6 hours.

On phones the game page (`EntryPage`) pins its main actions above the tab bar in `EntryActionBar` (`components/EntryActionBar.tsx`): Start playing or Play again (a single tap when the game has at most one platform, otherwise it scrolls to the Status panel, which asks which), Pause or Resume, Mark finished (opens the finish form in the Status panel and scrolls there; `StatusPanel` takes a `finishRequest` counter for this) and the favorite heart; an IntersectionObserver on the Status panel (`#status`) slides the bar away while the panel itself is on screen, and `.content:has(.action-bar)` gets extra bottom padding. There is no service worker, so nothing is cached offline. Render crashes never show React Router's default error page: `ErrorPage` (`components/ErrorPage.tsx`: logo tile, "Something went wrong", a plain explanation, Reload page and Go home, and a Show details toggle with the error text and a Copy button) has a dark round power button with a glowing green power symbol inside a ring of four lights with three glowing red (an inline SVG, a nod to the old console "red ring"; the lit arcs flicker out of step, steady under reduced motion) and comes in two variants. `page` is drawn by `ErrorBoundary` (a class component that clears itself when its `resetKey`, the path, changes) around the `Outlet` in `Shell`, so a crashing page leaves the sidebar usable and any navigation recovers; `full` is the router's `errorElement` (`RouteErrorPage`, on the splat route), the last resort for anything outside the shell (public pages, the App itself), which takes the whole window and uses a plain `<a href="/">` to go home. Event-handler and async errors are not caught by either (React boundaries only see render errors). The 404 card (`NotFoundPage`, headline "Cartridge not found", art by `CartridgeArt`: an inline-SVG game cartridge with a pixel "?" label, tilted above a dashed outline and hovering gently; `empty-state--shake`) gives the same jolt and icon wobble once when it appears (the error card's keyframes; off under reduced motion). Query keys group by area (`entries`, `entry`, `facets`, `platforms`, `search`, `playthroughs`, lists, queue, wishlist); mutations invalidate the relevant groups. Every page sets its browser tab title with `usePageTitle()` (`lib.ts`) as `<page> | GameQueue` (e.g. `Collection`, a game's or list's name, `<username>'s Profile`), falling back to plain `GameQueue` until the name is known; a new page must call it. The lists page shows each list as a tile of its first four covers cut into equal vertical slices (`ListSummaryDto.covers`, cover image ids of the first games with a cover, from `listLists`) under a dark scrim holding the name and count; an empty list is a plain tile. Confirmations use `useConfirm()` and dialogs use native `<dialog>` via `useModalDialog`. Every `.dialog` scales and fades in on opening, with its backdrop fading in (opening only: most dialogs clear their content as they close). The add-game dialog also carries `dialog--sheet`: under 640px it is a full-screen view (100% × 100dvh, no border or radius) that slides up from the bottom and back down on close (a `transform` transition with `display` and `overlay` set to `allow-discrete`, entry state from `@starting-style`; `AddGameDialog` keeps its content mounted for 350 ms after closing so the sheet doesn't empty as it leaves; browsers without discrete transitions just close it at once), with larger platform checkboxes. Motion flourishes, all off under reduced motion: `components/motion.ts` holds Web Animations API helpers (`reveal`, a callback ref that fades collection, list, wishlist and smart list cards and rows in as they mount, staggered per batch of mounts so "Load more" pages stagger too, played once per element so drags and re-sorts don't replay it; `pop` for a status badge changing in place on the game page; `celebrate`, a confetti burst in a fixed `.confetti` layer when a game is finished from the game page or a playing card); `CountUp` (`components/CountUp.tsx`) counts stat figures up (fading in from transparent over the same 700 ms the first time they appear, `.count-up`) on the Stats pages, the profile tiles and the admin dashboard (only values that are one number with an optional unit, e.g. `1,234`, `4.2`, `12.5 MB`; screen readers get the final text); the favorite heart pops with a ring of dots and a star pick fills its stars in turn (CSS keyframes keyed by the click). Game-like flourishes (CSS, all off or static under reduced motion): a card for a game being played on Home (`play-card--live`, not a paused one) glows with a breathing blue edge and shows a small pulsing play icon next to its title (decoration, `aria-hidden`: the status badge already says "playing"); the random pick result enters as a loot reveal (`LootCover` in `PickResult.tsx`: a face-down logo card flips over with a burst of rays behind it and a glint across the art, then the details rise in; used by both the owned and unowned results); the `--texture` token (faint scanlines plus a 4px pixel grid, `tokens.css`) is a background layer on the home and profile hero banners, the sidebar (and so the mobile drawer; a fainter `--texture-faint` that fades into the plain surface towards the bottom) and on `.empty` and `.empty-state` boxes. Page transitions: `main.tsx` builds a data router (`createBrowserRouter` with one splat route whose element is `App`, so the real routes stay `App`'s descendant `<Routes>`; `RouterProvider` from `react-router/dom`) only for React Router's view transitions and `<ScrollRestoration>` (new pages open at the top, back and forward restore the old position). `withPageTransitions` (`src/pageTransitions.ts`) wraps `router.navigate` so every link, `navigate()` and `<Navigate>` that changes the pathname gets `viewTransition: true` (not search-param-only changes such as filters and paging, not `replace` redirects, not under reduced motion or without `document.startViewTransition`; an explicit `viewTransition` option wins; browser back/forward never animate): the page crossfades in 180 ms. `withPageTransitions` also wraps `document.startViewTransition` once to catch the `ready`/`finished` rejections the browser raises when it aborts a transition because the viewport resized (a phone's address bar, rotation), which would otherwise log an uncaught `InvalidStateError`; the navigation itself is unaffected. Links to an owned game's page from `GameCard`, `GameRow`, playing cards and list rows use `useEntryLink`, which names that one cover `game-cover` while its page is opening (`useViewTransitionState`) and seeds the `['entry', id]` query with the entry on click (stale at once, so the page still refetches), so the game page renders its cover immediately and the cover flies from the card to the big cover (`COVER_TRANSITION` on `EntryPage`, 320 ms; the old image stays solid under the new one while the larger image loads). Signing out or deleting the account goes through `useSignedOut` (`api/auth.ts`): it navigates to `/` (replace) and then clears `me` and the private query cache, because the signed-out routes only know the landing page, auth pages and public profiles and any other path would show the 404 page. Platforms are shown as an icon plus short name (`PlatformTags`/`PlatformTag` in `components/PlatformIcon.tsx`, joined with other metadata by `MetaLine`). Icons are Simple Icons glyphs (CC0, v11.14.0, vendored as path strings in `platformIconPaths.ts`) or Lucide for web/arcade, mapped from IGDB platform ids in `platformIcons.ts`; platforms with no mapping (e.g. DOS, older Nintendo, Amiga) show text only. To add one, vendor its path and add the id to a family.

## Data model

SQLite via better-sqlite3, WAL mode, `PRAGMA foreign_keys = ON`. Schema in `apps/server/src/db/schema.ts`; migrations in `apps/server/drizzle/` (a single baseline `0000_*.sql`, then normal migrations) run automatically when the DB is opened (startup and every test DB). Timestamps are epoch milliseconds; game dates are `YYYY-MM-DD` text.

**Shared game metadata cache** (no `user_id`; ids are IGDB ids):

| Table                                          | Purpose                                                                                                                                                                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `games`                                        | name, slug, summary, release date (+ `release_precision`: day/month/quarter/year, null = unknown; `release_checked_at`), cover `image_id`, IGDB rating, game type, time-to-beat (seconds), `fetched_at` |
| `platforms`, `genres`, `themes`                | Lookup tables                                                                                                                                                                                           |
| `game_platforms`, `game_genres`, `game_themes` | Many-to-many join tables, cascade on game delete                                                                                                                                                        |
| `series`                                       | IGDB series ("collections"): id, name, `members_fetched_at`. Shared cache like `games`                                                                                                                  |
| `game_series`                                  | `(game_id, series_id)`, cascade on both; which series a cached game belongs to (a game can be in several)                                                                                               |
| `series_members`                               | `(series_id, game_id)` plus name, cover, release date/precision: IGDB's list of a series' main entries, cached for the series page. Not necessarily in `games`                                          |

Relationships to remember:

- A user owns entries; an entry points at a cached `games` row. Deleting an entry cascades to its platforms, tags, playthroughs and list items.
- The backlog is not stored: it is every entry with status `unplayed`.
- **Favorites** (`entries.favorite`): a per-user, per-game flag set with `PATCH /api/entries/:id {favorite}`. It is independent of rating, lists and the queue, and a patch containing only `favorite` does not touch `updated_at` (so it doesn't reset the "last changed" smart list field). Filter: `favorite=true` on `GET /api/entries`, with a `favorites` count in `GET /api/entries/facet-counts` (scoped by the other active facets). The web shows a heart toggle on the game page (`FavoriteButton` in `EntryPage`, colour token `--favorite`) and a "Favorites only" option in the collection filters.
- **Smart lists** (`services/smart-lists.ts`, `packages/shared/src/smart-lists.ts`, routes `/api/smart-lists`: `GET /`, `POST /`, `POST /preview`, `GET|PUT|DELETE /:id`, `GET /:id/export.csv`): a smart list is a name, an AND-ed array of rules and a sort. Rules are `status`/`platform` (ids)/`genre`/`tag`/`finishedYear` any-of sets, `favorite` (no parameters: "Is a favorite") (`finishedYear` tests `EntryDto.finishedYears`, every year with a finished playthrough that has an end date, so it agrees with the profile's finished-by-year pages), or a number field (`ttb` in minutes, `igdbScore`, `rating`, `addedDays`, `changedDays`, `finishedDays`, `releaseYear`) with `gte`/`lte`/`unknown`; an unknown value never satisfies `gte`/`lte` (as with the pick's max time). "Days" fields count whole days back from now; `changedDays` uses `entries.updated_at`, which any status, rating, notes, tag or platform edit bumps (and import resets), so it means "last touched", not strictly "last played". Evaluation is pure over `EntryDto`s (`evaluateSmartList`): the service loads every entry once (`hydrate`) and filters and sorts in memory, which is fine at personal-collection scale and keeps one definition of "matches" for the server and the editor preview. Sorting puts missing values last whichever way it goes. A smart list holds no games, so it can't be reordered; the random pick can use it as a source (`source: {type: 'smart', smartListId}`) with the usual rule that only unplayed games, plus paused if asked, are candidates. They are collection-only and never include wishlist games.
- **Stats** (`services/stats.ts` loads the entries and the finished playthroughs, `computeStats` in `packages/shared/src/stats.ts` does the arithmetic; `GET /api/stats` for the owner, `GET /api/profiles/:username/stats` public, registered before `:view`): overview (counts, backlog size and summed time to beat of backlog games with a known time, average rating), games finished per year and over the last 12 months (a game counts once per period; playthroughs with unknown dates only appear under `unknown` in the yearly view), top-10 platform/genre/tag breakdowns with finished and unplayed counts, rating distribution and top-rated games, and total play time. Play time is the `playtime_minutes` the user entered, summed over _finished playthroughs_ (replays count again); finishes without one are counted as `unrecordedCount` and add nothing. Nothing is timed. The DTO holds only counts and `PublicEntryDto`s, so the same payload serves the private and public pages.
- **Recap** (`services/recap.ts` loads the entries and every playthrough, `computeRecap` in `packages/shared/src/recap.ts` does the arithmetic; `GET /api/recap?year=` for the owner, `GET /api/profiles/:username/recap?year=` public, registered before `:view`; a malformed `year` is a 400): the **Save File** (the user-facing name; the code, routes and `--recap-*` tokens still say "recap"), a year in review. Without `year` it picks the current year if it has activity, else the latest one (`defaultRecapYear`); `years` lists every year with a finish, abandon, start or added game. A game counts once per year however often it was finished. Fields: finished/previous-year/abandoned/started/added counts, replays (finished games also finished in an earlier year), play time (entered play time over the year's finished playthroughs, like stats), finishes per month and the busiest one, top 3 genres and platforms (the platform of the playthrough), best-rated finishes, longest/shortest game by time to beat, the longest start-to-finish haul (both dates known), first/last finish, every finished game, and a playful `archetype` (first matching rule of collector, marathoner, sprinter, returner, explorer, finisher, else steady). Unknown dates never count towards a year. The DTO holds only counts and `PublicEntryDto`s (no notes), so one payload serves the private and public pages.
- **Series** (`services/series.ts`, `routes/series.ts`, `SeriesPage`): a series is an IGDB _collection_ (type "Series"; franchises were deliberately not used, they mix spin-offs and media). `fetchGame` returns `collections`, `saveGame` stores them (`series` + `game_series`), and `GameDto.series` carries them. Games cached before this, and games saved from an import file back when imports stored the file's snapshot (`series_checked_at` null), are filled in by `backfillSeries`: one request per 100 games, run in the background at startup, one run at a time, failures retried next time. The web page (`/series/:id`, linked from the game and entry pages) shows rows with a status badge, "queued", "On wishlist" or a Wishlist button; unowned games link to their IGDB game page, where they are added. Series are not in the export file (they come back from IGDB).
- **Screenshots** (`games.screenshots`, JSON array of IGDB image ids; `MAX_SCREENSHOTS` = 6 from `screenshots.image_id` in the game query, `mapScreenshots`): `GameDto.screenshots` (empty when unknown or none). Null in the column means IGDB was never asked: games cached before the column existed, and games saved from an import file back when imports stored the file's snapshot. `ensureScreenshots` (`services/games.ts`) asks IGDB once for those when the game is opened (`GET /api/entries/:id`, `GET /api/igdb/games/:igdbId`), best effort, and stores `[]` when there are none. The `Screenshots` component sits under the cover on `EntryPage` and `GameDetailPage`: the first three as a single column of thumbnails in their own proportions (`720p`, since the `screenshot_*` sizes crop to 16:9), a click opens a native-`<dialog>` lightbox at 1080p with previous/next (buttons and arrow keys) over all of them. Hidden under 760px, where the page is one column (the hidden images aren't downloaded). Not in the export file.
- **Onboarding**: the home page renders `Welcome` (`components/Welcome.tsx`: greeting, calls to action to search, import or start a wishlist, and a three-step intro) instead of the playing games and queue when `useStats().overview.total` and the wishlist are both 0 (the queue and lists only hold owned games, so the collection being empty covers them). It switches back on its own as soon as a game is added.
- **Release dates** (`packages/shared/src/release.ts`, `mapRelease` in `igdb/mappers.ts`, `refreshReleaseDates` in `services/games.ts`): IGDB has one timestamp per release, and for a vague release it is a placeholder (a game announced for "2028" is 2028-12-31), so `games.release_precision` records how exact it is, from the `date_format` of the per-platform `release_dates` that carry `first_release_date` (the most exact wins; TBD means no date). Quarter and month are read from the date's own month, so it doesn't matter whether IGDB puts the placeholder at the start or the end of the period. The wishlist shows `releaseLabel` ("Nov 19, 2026", "Nov 2026", "Q4 2027", "2028", "TBA") in the meta line and, over the cover of every game not out yet, a `ReleaseBadge` (`releaseBadge`: "in 6 days", "in 3 weeks", "in 3 months", "in 2 years" for an exact day; the vague date itself for month/quarter/year/TBA, since a count would claim too much; nothing once released). The home page's "Releasing soon" section (`ReleasingSoon`, under Up next) reuses `useWishlist` and lists wishlisted games whose exact release day (`releasesWithin`: day precision only, today through 14 days ahead) is coming up, soonest first, as covers with the same badge; it is hidden when there are none. The badge is a fixed dark pill on tiles (top right) and a strip along the bottom of the 64px cover in rows. `GET /api/wishlist` first calls `refreshWishlistReleases`: cached games that aren't released yet (`isReleased` = the whole period is over; no date counts as unreleased) and weren't checked in the last 24h are re-read from IGDB in one request, and `release_checked_at` is stamped. It is best effort (IGDB errors are logged and the cached dates are served) and only runs for the owner's own wishlist; the public wishlist shows what is cached. Rows saved before the column existed have a null precision (shown as an exact day) and are refreshed once if unreleased; imported rows are saved unchecked, so they refresh on the next wishlist load.
- **Picking** (`services/pick.ts`, `pickMany` in `packages/shared/src/pick.ts`, web `PickCriteriaPage`, `PickResult`): `POST /api/pick` takes `count` (1 to 3, `PICK_MAX_COUNT`) and returns `entries` (distinct, at most `count`, fewer only when fewer match) besides `entry` (the first). `pickMany` draws games not shown yet first, then wraps through the shown ones with the most recent pick last; one game is drawn exactly as before (`pickRandom` is `pickMany` with 1). The result card has Start playing as the primary button and Add to queue (`QueueButton`) as the secondary, plus Re-roll and Pick 3; a pick of three shows the games side by side (`PickChoices`) and the chosen one becomes the result. Each result of the visit goes into a strip of covers under the card (`RollHistory`), and selecting one puts it back on the card. The history lives in the page only.
- **Ask AI page** (`/chat`, `routes/AskAiPage.tsx`, nav item "Ask AI" shown when AI is available or only the budget is spent): the pick-my-next-game chat and the user's saved game chats. `POST /api/ai/pick {messages}` (feature `pick`; the conversation is sent whole each turn and not saved): `buildPickContext` (`services/ai-pick.ts`) gives the model the signed-in user's last 15 finished games with ratings and genres, their queue and up to 150 Not Started games with genres, tags, hours to beat and IGDB score (a random sample when there are more; queued games listed once), asks for structured JSON output (`jsonSchema` on `AiProvider.generate`, sent as `output_config.format`) with a message and suggestions citing entry ids, and drops any suggestion whose id isn't a queue or backlog candidate (and repeats; at most 5). A reply that isn't JSON becomes a plain message. Suggestions render as cards with Start playing and Add to queue; the chat changes nothing by itself. `GET /api/ai/chats` without `entryId` returns the 30 most recently used saved chats across games with each game (`recentChats`); the page shows one row per game linking to `/games/:id/chat`, and a collection search to start a chat about any game.
- **AI** (`ai/provider.ts`, `services/ai.ts`, `services/ai-usage.ts`, `routes/ai.ts`, web `components/GameChat.tsx`, `routes/GameChatPage.tsx`, `routes/AdminAiPage.tsx`; the chat is its own page, `/games/:id/chat`, reached from an "Ask about this game" button on the game page that shows only when AI is available; the question box stays at the bottom of the screen and the page follows a growing answer unless the reader scrolls up): on only with `ANTHROPIC_API_KEY` (model `AI_MODEL`, default `claude-sonnet-5-5`) **and** the user's `ai_enabled` switch (admin user page). `AiProvider.generate({system, messages, maxTokens})` returns text plus token usage; `createAnthropicProvider` calls the Messages API through `@anthropic-ai/sdk` (beta endpoint for server-side `fallbacks: "default"` on models that take it, `effort: low`, no streaming) and turns any failure into an `AiProviderError` whose message is only the HTTP status, so neither the key nor the prompt reaches logs; tests inject `fakeAi()` through `createApp({ai})`. `GET /api/ai/status` (`available` plus a reason: `not_configured`, `not_enabled`, `budget_spent`; the web renders no AI control unless available), `POST /api/ai/chat {entryId, chatId?, includeNotes, message}` (the server keeps the conversation in `ai_chats`; the client sends only the new question and which chat it continues, the server loads the history, checks the caps and saves the question and answer together once the answer is complete, returning `chatId`; `GET /api/ai/chats?entryId=`, `GET|DELETE /api/ai/chats/:id`, opening one bumps `used_at`) (the web uses `POST /api/ai/chat/stream`, the same turn as server-sent events: `delta` pieces as they arrive, then `done` with the whole answer, which wins, or `error`; everything that can refuse a turn without an AI call is checked first by `prepareChat` and answered as a plain HTTP error; usage is recorded when the answer completes) and `POST /api/ai/summarize {chatId}` (returns a draft; saving goes through the normal notes and journal routes, so nothing saves without the user's click). A question is at most 4,000 characters, and a chat at most 20 messages and 24,000 characters (`AI_MAX_*`), checked by `prepareChat` against the saved history. `buildSystemPrompt` uses only the requesting user's entry: IGDB data, the open playthrough's latest 12 journal posts, the entry's notes when `includeNotes`, and the `NO_SPOILERS` instruction, with the data marked as data. Each call writes one `ai_usage` row; the conversation is kept only in the user's `ai_chats` row and never logged (a failure is logged as `ai_failed` with the provider's status only). Cost: `PRICES_PER_MTOK` (input/output $ per million tokens, an estimate; unknown models are charged at the dearest rate). Budget: settings key `ai_budget_usd` (default $5, `DEFAULT_AI_BUDGET_USD`) per calendar month in UTC; at 80% the admin card warns, at 100% calls are refused (429) until the month ends or the budget is raised (a call that starts under budget may finish over it). Limits: per-IP tier `ai` (20 POSTs a minute) plus 60 calls per user per hour (`AI_CALLS_PER_USER_HOUR`). Replies are Markdown, rendered with `react-markdown` (no raw HTML, images dropped, links open in a new tab without a referrer); summaries are asked for in plain text because notes and journal posts show plain text. Admin: `GET /api/admin/ai` (month spend, budget, split by feature, last 20 calls), `PUT /api/admin/ai/budget`; dashboard tile and `/admin/ai`.
- **Journals** (`services/journal.ts`, `services/screenshots.ts`, `routes/journal.ts`, web `components/Journal.tsx`, `routes/JournalPage.tsx`): every playthrough has a journal of posts (note, hours, screenshots). Owner API (404 for anyone else's rows): `GET|POST /api/playthroughs/:id/posts`, `PUT /api/playthroughs/:id/visibility {visibility}` (mints `share_slug` on first share; going private **deletes** it, so the page and image URLs stop at once and sharing again makes a new link), `PATCH|DELETE /api/posts/:id`, `POST /api/posts/:id/images` (raw bytes, one picture per request), `DELETE /api/posts/images/:imageId`, `GET /api/posts/images/:imageId` (owner's copy). Public, no login: `GET /api/journals/:slug` (a `JournalDto` with posts newest first (the page puts the Finished marker above them and Started below), never entry notes, user ids or the game's collection data) and `GET /api/journals/:slug/images/:imageId` (404 unless the image belongs to that shared journal), `GET /api/profiles/:username/journals` (public ones only, 404 for unconfirmed accounts like the rest of the profile). Image responses are `Cache-Control: private, no-cache` with an ETag, so a journal set back to private stops serving on the next request. `PlaythroughDto` carries `visibility`, `shareSlug`, `finalThoughts` and `loggedMinutes` (sum of hours posts, from `loggedMinutesFor`, which the finish dialog pre-fills the total time with); `closeSchema`/`patchPlaythroughSchema` take `finalThoughts`. Web: the open playthrough's journal is a panel on the game page, finished ones open from their history row; `/p/:slug` is a public page (own header, loading skeleton, spoiler posts collapsed until clicked, lightbox) served `noindex` with a text-only preview and a generic title (`journalSeo` in `seo.ts`, a real 404 unless the link is live); public journals show in a Journals section on the profile. Finishing from the game page, Home or the finish dialog opens one dialog (`FinishDialog`: date, total time, rating, final thoughts); abandoning keeps the small inline form.
- **Screenshot storage** (`services/screenshots.ts`): `storeImage` accepts JPEG, PNG and WebP judged by the bytes (not the header), refuses originals over 8 MB (413) and more than 64 megapixels, applies the EXIF orientation, scales to at most 1920 px on the longest side and re-encodes to WebP with **sharp** (which drops all metadata unless asked to keep it), then writes `<sha256>.webp` to `SCREENSHOTS_PATH` (default `screenshots/` next to the database) through a temp file and rename. sharp ships prebuilt libvips binaries for linux arm64 (glibc) as optional dependencies, so the Docker build needs no compiler for it; the lockfile pins them. The Dockerfile smoke-tests it after the production install, and CI builds the arm64 image on every push and PR (job `image`), so a failure shows up there and not at deploy time. The total of distinct files is capped by the `settings` key `screenshot_cap_bytes` (default 1 GiB, `DEFAULT_SCREENSHOT_CAP_BYTES`); an upload that would pass it is refused with a 507 and a clear message, and a new cap applies to the next upload. `GET /api/admin/screenshots` (used, cap, file count, free disk), `PUT /api/admin/screenshots/cap`, `POST /api/admin/screenshots/cleanup`; web: the Admin tile and `/admin/screenshots` with a meter. Files are removed when a post, image, playthrough, entry, account or admin-deleted user goes: the route collects the file names first (`imageFilesOf`), the database cascade does the rest, and `removeUnreferencedFiles` deletes the files no row still points at. `cleanupScreenshots` runs at startup and daily (`index.ts`): files nobody points at older than an hour, `.tmp` leftovers, image rows whose file is gone, and screenshot posts with no picture older than a day. `scripts/backup.sh` copies new files to `backups/screenshots` (and to the `offsite` remote with `rclone copy`); see DEPLOYMENT.md.
- **Wishlist** (`services/wishlist.ts`, `routes/wishlist.ts`): the user's one `wishlist`-kind list, so it shares `list_items` with every list: `(list_id, game_id)`, `position`, the optional target `platform_id` and private `note` (columns used by the wishlist only), `added_at`. **`/api/wishlist` stays as a thin wrapper** (`GET`, `GET releasing-soon`, `POST items`, `PATCH|DELETE items/:igdbId`, `PUT move|order`) that resolves the list with `ensureWishlist` and keeps the `WishlistDto` shape, so the web needs no list id; move, reorder and remove call the generic `moveInList`/`reorderList`/`removeItem`, and `/api/lists/:id/...` works on it as well. The wishlist is not part of the collection: wishlisted games have no entry, so they are not in the collection, backlog, stats or random pick. The two are kept disjoint inside `addToList` (so the generic route can't bypass it): wishlisting an owned game is a 409 carrying the `entryId`, and adding a game to the collection (`addEntry`, or an import) calls `dropFromWishlist`. `wishlistedIds(db, userId, among?)` answers "which of these are wishlisted" for search, similar, series, Discover and the public game page. Unreleased wishlisted games get their release dates refreshed when the wishlist is read.
- Status is kept consistent with playthroughs by `syncStatus`; starting a game removes it from the queue (`startPlaythrough` in `services/playthroughs.ts`). Home lists every `playing` entry (no cap) and a smaller row of `paused` ones, both from `GET /entries?status=…`.

**Changing the schema**: edit `schema.ts`, run `npm run db:generate`, commit the new SQL. Check generated SQL for added FK columns: drizzle-kit drops `ON DELETE` from `ALTER TABLE ... ADD COLUMN ... REFERENCES` on SQLite and it must be patched by hand (see `0003`).

**Export/import** (`services/export.ts`, `services/import.ts`, `packages/shared/src/export.ts`, routes `/api/data/*`): one versioned JSON file (`format: gamequeue-export`, `version: 1`) with a metadata snapshot per game. Import never stores the snapshots (only the name is used, in report notes): before the merge, `resolveImportCatalog` (`services/import.ts`) looks up every game the file mentions that isn't cached yet (entries and wishlist) with `IgdbClient.fetchGames`, which answers from the mirror and sends the rest to live IGDB at 100 games per multiquery, and caches what comes back like any other IGDB data. It also loads the platform list when the file names a platform we don't have. A game IGDB doesn't know is skipped with a note (`report.games.skipped`), and so is everything of it (list and queue items, wishlist item); a platform IGDB doesn't list is dropped (a playthrough or wishlist item keeps no platform, and a game left with no owned platform is skipped). This runs before a dry run too, so the preview matches the commit; what it caches is real IGDB data, as browsing a game page would. Uncached games with no IGDB configured make the import a 503 that writes nothing. Limits: `MAX_IMPORT_GAMES` (10,000) games, queue and wishlist items per file; at most `MAX_NEW_GAMES_PER_IMPORT` (5,000) uncached games looked up per run, the rest left for the next run of the same file with one note; and `IMPORTS_PER_DAY` (10) committed imports per user (in memory, `HitLimiter` in `routes/data.ts`; dry runs are free; a 429 past it), on top of the per-IP `data` tier. Each game carries an optional `favorite`; import only ever sets it (a file never clears a favorite you have). Smart lists travel as an optional top-level `smartLists` (name, rules, sort, dir; no games, since those are computed), merged by case-insensitive name so ones you already have are left alone. The wishlist travels as an optional top-level `wishlist` (in order, each item with its own snapshot (the game snapshot's `releasePrecision` is optional), target platform and note), so files without it are still valid v1; import appends missing games to the end of the existing wishlist, fills only empty platform/note fields, and skips games you own. Files written before the refactor may still carry top-level keys for features that were removed; the schema does not declare them, so zod drops them and the importer ignores them (a test in `data.test.ts` keeps such a fixture). A snapshot's `coverImageId` must look like an IGDB image id (`IGDB_IMAGE_ID` in `igdb-images.ts`: lowercase letters and digits, as every id in the IGDB dump is), since cover ids end up in `srcset`, where a space or comma would add an image URL of the file author's choosing; `coverUrl`/`screenshotUrl` also URL-encode every id, whatever its source. Import is a merge matched on `igdb_id`, list names, and playthrough platform+dates+outcome. `POST /api/data/import` is a dry run unless `?commit=true`; the dry run runs the real merge in a transaction and rolls it back. Changing the format means bumping `EXPORT_VERSION` and keeping a reader for the old one.

**Notes** (`entry_notes`: `entry_id` with `ON DELETE cascade`, `body`, `public` default false, `created_at`, `updated_at`; `EntryDto.notes` is the list, newest first, up to 200 per game and 10,000 characters each): a game has many notes, each private or public. Routes (all return the updated entry): `POST /api/entries/:id/notes {body, public?}`, `PATCH /api/entries/:id/notes/:noteId {body?, public?}`, `DELETE /api/entries/:id/notes/:noteId`; `PATCH /api/entries/:id` no longer takes notes. Adding, deleting or changing the text of a note bumps `entries.updated_at` (so it still resets "gathering dust"); flipping `public` doesn't. Notes are never in `PublicEntryDto`, so lists, tiles, stats, recap, share cards and the activity feed can't leak them; the only public place is `ProfileGameDto.notes` (id, body, date, public ones only) on `/u/:username/games/:igdbId`, shown by `PublicNotes`. No activity event is recorded for notes. Export carries them as optional `noteItems` per game (`body`, `public`, `createdAt`); older files with the single `notes` text still import, as one private note. Import merges: a note whose text you already have on that game is skipped (your copy and its visibility win). Migration `0028` turned each non-empty `entries.notes` into one private note and dropped the column. The CSV has one Notes column (all of a game's notes, public and private, separated by a blank line). Web: `NotesPanel` on the game page (add form with a "Show on my public profile" checkbox, per-note edit, delete with confirmation, and a Public/Private toggle).

**CSV export** (`packages/shared/src/csv.ts`, `csvResponse` in `http.ts`): `GET /api/lists/:id/export.csv` (works for the queue too, via its list id), `GET /api/smart-lists/:id/export.csv` and `GET /api/data/export.csv` (the whole collection, by title) return one row per game in list order: title, status, platforms, tags, genres, rating, favorite (yes/no), IGDB score, time to beat in hours, release date, added, last finished, playthrough count, notes and IGDB id. It's a read-only spreadsheet export, not an import format. The file is UTF-8 with a BOM (so Excel reads it correctly) and CRLF row endings, and text cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading apostrophe so a spreadsheet can't run them as formulas.

## Auth and sessions

- **Accounts**: `POST /api/auth/register` (403 when `SIGNUPS_ENABLED=false`) hashes the password with argon2id (`@node-rs/argon2`, parameters pinned in `auth/password.ts`), inserts the user in one transaction (the unique username and email indexes are the duplicate check; a duplicate is a 409 that names the field, `That email is already registered…` or `That username is taken`, with `details` like the admin form; this deliberately lets anyone check whether an address has an account). Usernames are 3-30 chars of `a-z 0-9 _ -`, lowercased by `usernameSchema`; email is kept but is not used to log in, then logs the user in. **Signup alert** (`services/notify.ts`): after a successful register, `notify(subject, text)` emails the owner through Resend's HTTP API (`POST https://api.resend.com/emails`), fire-and-forget with a 10 s timeout; failures are logged and never affect the signup. It sends only the username (no email address) and is a no-op unless both `RESEND_API_KEY` and `NOTIFY_EMAIL` are set (`NOTIFY_FROM` defaults to Resend's shared `onboarding@resend.dev`, which only delivers to the Resend account's own address). `createApp` takes an optional `notify` so tests can inject a fake; admin-created users don't trigger it. `GET /api/auth/config` (public) returns `{signupsEnabled}`; the web login page hides its "Create an account" link, and `/register` redirects to `/login`, when it is false.
- **Email verification** (`services/email-verification.ts`, `services/mailer.ts`, `routes/auth.ts`; on only when both `RESEND_API_KEY` and `MAIL_FROM` are set, `Config.emailVerification`; without them register marks the account verified at once and the server warns at startup): `register` creates the user with `email_verified_at = null`, signs them in and emails a link `PUBLIC_URL/verify-email#token=…` (32 random bytes, only the SHA-256 stored, valid 24 h, sent through Resend with `MAIL_FROM`, a failed send is recorded as `email_failed` and never fails the signup). **Hard wall**: `requireAuth(db, config, {allowUnverified})` answers 403 `{code: 'email_unverified'}` to an unconfirmed user on every router except `GET /auth/me`, sign out and the verification endpoints (the Account page, delete account included, waits too); the web app then shows only `VerifyEmailGate` ("Check your inbox": resend, fix the address, sign out). Their public profile, avatar and share cards are 404 until confirmed (`email_verified_at is not null` in the username lookups). **Email links** (verify and reset): the token is in the URL fragment, which browsers never send, so it stays out of server, Cloudflare and proxy logs; `useLinkToken` (`apps/web/src/linkToken.ts`) reads it (or `?token=` from links sent before the switch), keeps it in memory and removes it from the address bar. `VerifyEmailPage` sends it only when the user presses **Confirm my email**: confirming on page load let mail scanners that run scripts (Safe Links and the like) confirm accounts nobody looked at. Endpoints: `POST /auth/verify-email {token}` (public, a POST so link scanners can't use the token up; single use, deletes the account's other tokens, valid only while the account's email is still the address it was sent to; notifies the owner of the signup now), `POST /auth/resend-verification` (60 s cooldown and 5 per hour per account, counted from `email_verifications.created_at`, 429 otherwise; 502 if Resend fails) and `PUT /auth/email {email}` (fix a mistyped address while unconfirmed; sends a new link; 409 once confirmed). All three also share a per-IP `verify-email` tier (20/h). Accounts unconfirmed after 7 days are deleted (`purgeUnverified`, at startup and every 6 h; cascades). Admin: users created by an admin are confirmed, changing a user's email as admin confirms it, and `POST /admin/users/:id/verify-email` / `resend-verification` plus an "unverified" badge on the Users page. `UserDto.emailVerified`. The owner's "New signup" alert fires at confirmation when verification is on, at register otherwise.
- **Daily email limit** (`services/mail-budget.ts`, table `mail_daily`): `createApp` wraps the user mailer (verification and reset emails, admin resends included; not the owner alerts) in `limitMailer`, which counts every send on today's UTC row and refuses past `MAIL_DAILY_LIMIT` (default 80, under Resend's free 100 a day). Signup and `PUT /auth/email` can mail any address, so without it a few IPs could use up the quota and block real confirmations. A refused email throws `MailQuotaError`: recorded as `email_quota` (not also as `email_failed`), the owner gets one notifier email the first time each day (in memory), and callers treat it as a failed send (signup still succeeds, resend answers 502, forgot-password stays silent).
- **Forgot password** (`services/password-reset.ts`, `routes/auth.ts`, table `password_resets`; web `/forgot-password` and `/reset-password#token=…`, `PasswordResetPages.tsx`, linked from the login page and from signup's "email already registered" error, which is how the owner of an address someone else signed up with gets the account back): available when there is a mailer, or outside production (`GET /auth/config` says `passwordReset`; when false the login page hides the link, the forgot page says to ask the admin, and the endpoint answers 503, so a production server without Resend never writes live reset links to its logs). `POST /auth/forgot-password {email}` is public and always answers `{ok: true}` whether or not the address has an account, so it can't be used to look addresses up. For a known address it emails (same Resend mailer; in development the link goes to the console) `PUBLIC_URL/reset-password#token=…` (32 random bytes, only the SHA-256 stored, valid 1 h, mentions the username since login is by username). Asking again within 60 s, or more than 5 times an hour for one account, is silently ignored; a failed send is recorded as `email_failed`. The route doesn't wait for the send: waiting only for real accounts would let the response time reveal which addresses exist. Each token stores the address it went to and is void once the account's email differs; changing the password (Account page or admin reset) deletes the account's pending links. `POST /auth/reset-password {token, password}` (public, password rules as at signup; 400 for an unknown, used, expired or re-addressed token) sets the password, deletes every session of the account (signed out everywhere, no auto-login), voids its other reset links and marks an unconfirmed email as confirmed (the link reached the inbox; its pending confirmation links are deleted too, so a late click can't re-send the signup alert). **Password changed notice** (`sendPasswordChangedNotice`): after a reset, a change on the Account page or an admin reset (not of the admin's own account) the owner gets "Your GameQueue password was changed" saying how, with a link to `/forgot-password`, so a takeover doesn't go unnoticed; fire and forget, counted in the daily limit, and never sent to an unconfirmed address (an admin reset must not mail a stranger). Both share the per-IP `verify-email` tier (20/h). Expired rows are purged with the unverified accounts (startup and every 6 h).
- **Login** (`POST /api/auth/login`): checks two in-memory `FailureLimiter`s first (per `username|ip`: 5 failures / 15 min; per IP: 30 / 15 min; 429 with `Retry-After`). It always runs an argon2 verify, against a dummy hash if the username is unknown, so timing doesn't reveal which accounts exist. Wrong credentials return one generic 401. Success resets the per-account counter. The client IP is `clientIp` (`auth/client-ip.ts`): with `TRUST_PROXY=true` it is `CF-Connecting-IP`, else the first `X-Forwarded-For` entry, otherwise the socket address; IPv6 is collapsed to its /64. The limiters are per process, which is fine for a single-instance deployment.
- **Request limits** (`auth/request-limits.ts`, `HitLimiter` in `auth/rate-limit.ts`; middleware on `/api/*` mounted first in `createApp`, off with `requestLimits: false`, which the test helper does): every request counts per client address (not per user: the check runs before authentication, so it can't be dodged with a made-up session cookie) toward `general` (300 / min, `/api/health` exempt) and toward the first matching specific tier: `signup` (`POST /api/auth/register`, 10 / hour), `data` (`/api/data/*`, import and exports, 20 / 10 min), `share-card` (`/api/og/*`, 60 / min) and `igdb` (`/api/igdb/*` and `/api/discover`, 60 / min). Past a limit: 429 `{error}` with `Retry-After`, and one `console.warn` (`Rate limited: tier=… ip=…`) per client and window. Fixed windows, in memory, so a restart clears them. Static files and the SPA are not limited (Cloudflare covers those). The web `QueryClient` doesn't retry a 429.
- **Sessions** (`auth/sessions.ts`): on login a random 32-byte token is generated; only its SHA-256 hash is stored (`sessions.id`), so a DB leak doesn't yield usable cookies. The raw token goes to the browser in the `gq_session` cookie (httpOnly, SameSite=Lax, `Secure` when `NODE_ENV=production`, path `/`). TTL is 30 days, sliding: when less than half remains, the expiry is extended and the cookie re-issued. Expired sessions found on lookup are deleted, and a periodic purge removes the rest.
- **Per-request auth** (`auth/middleware.ts`): `requireAuth` reads the cookie, calls `resolveSession`, and sets `c.var.user = {id, username, email}`. A missing or invalid session returns 401 (and clears a stale cookie). Handlers get the user id from `c.get('user')`; every service query is scoped by it.

Hover or keyboard focus (left/right = a week, up/down = a day) shows a popup anchored to the square (`position: fixed` so the scroller can't clip it, above the square or below if there's no room, kept in the window; it never moves the layout) with the day's date, games played and up to 8 events as plain lines; click/tap pins it (closes on Escape or a click elsewhere) and then it has links to the games. Shown on the public profile (only when activity isn't hidden), on `/stats` and on `/u/:username/stats`. The window is fixed at the last 12 months.
- **Avatars**: every user has a procedural identicon derived from their username, so nothing is stored and no endpoint exists. `generateIdenticon` (`packages/shared/src/avatar.ts`) hashes the lowercased username (FNV-1a) into a seeded PRNG and returns a hue plus a left-right mirrored 5x5 cell grid; the web `Avatar` component (`components/Avatar.tsx`) draws it as an SVG whose colours come from `--avatar-h` and the light/dark rules in `app.css`. It is decorative (`aria-hidden`; the username is always beside it) and shows in the sidebar user link and the profile hero (with a matching skeleton). Users can replace it with an uploaded picture. The web `AccountPage` (`/account`, linked as "Account" in the sidebar) crops the chosen image to a centred square and re-encodes it to 256px WebP (JPEG where the browser can't encode WebP) in the browser (`avatarImage.ts`, which also drops EXIF/GPS), shrinking quality until it fits `AVATAR_MAX_BYTES` (128 KB), then `PUT /api/avatar` sends `{contentType, data(base64)}` as JSON (the API takes only JSON bodies); `DELETE /api/avatar` goes back to the identicon. The server (`routes/avatar.ts`, `services/avatars.ts`) accepts only png/jpeg/webp, checks the magic bytes match the declared type and the size, and upserts the `avatars` row. `GET /api/profiles/:username/avatar` is public and serves the bytes with `nosniff` and an immutable cache header; callers add `?v=<updatedAt>` (`avatarUrl`), taken from `UserDto.avatarUpdatedAt` (`/auth/me`, login) or `ProfileDto.avatarUpdatedAt` (null = no upload), so a new upload is a new URL. `Avatar` renders the `<img>` when a version is set and falls back to the identicon if it fails to load. Uploaded avatars are not part of the export file.
  **Preset icons** (`packages/shared/src/avatar-icons.ts`): 51 icons from game-icons.net (CC BY 3.0, authors Lorc and Delapouite; SVG path data copied in, no runtime fetch) drawn white on one of 8 background colours (`AVATAR_COLORS`, indexes stored, each >= 4.5:1 with white). The choice lives on the user row (`users.avatar_icon` key + `users.avatar_color` index, both null = none) and is exposed as `avatarIcon` on `UserDto` and `ProfileDto` next to `avatarUpdatedAt`. `PUT /api/avatar/icon {icon, color}` (validated by `avatarIconSchema`; unknown key or colour = 400) sets it; an upload and an icon are mutually exclusive (each clears the other, in `services/avatars.ts`), and `DELETE /api/avatar` clears both back to the identicon. `Avatar` precedence: upload, then icon, then identicon. The Account page shows only the current picture with a "Change picture" button; everything else (upload, "Use generated avatar", colour row, icon grid) is in `AvatarDialog` (`components/AvatarDialog.tsx`, a native dialog via `useModalDialog`), and choices are held in a draft until **Save** (Cancel/✕/Esc discards them). The share cards draw icons too (`avatarIcon` is part of every card's data, so it is in the content hash; the icon margin is done with the SVG viewBox because satori ignores path transforms). Adding an icon by a new author means adding the author to `AVATAR_ICON_AUTHORS`, which feeds the credits page.
- **Credits page** (`/credits`, `CreditsPage.tsx`, public, linked from the user menu and from the footer of pages outside the shell): attributions for IGDB, game-icons.net (the per-author icon list is generated from `AVATAR_ICONS`), fonts and open-source software. New third-party data, art or fonts that need attribution get an entry there.
- **Real name** (`users.first_name`, `last_name`, `show_real_name`; all optional, private by default): `PATCH /api/account` (`routes/account.ts`, `services/users.ts`) takes `{firstName, lastName, showRealName}` (`accountProfileSchema`: trimmed, inner whitespace collapsed, max 50, no control characters, empty = unset). `getUserDto` builds the `UserDto` for `/auth/me`, login and register, so it always carries the name fields. `ProfileDto.realName` is the joined name only when `show_real_name` is on (null otherwise, so the name never reaches the public API without the opt-in), shown as the profile hero's heading, with the username beneath it in smaller muted text (the username is the heading when there is no shown name). The `AccountPage` has the two fields and the checkbox. The first name (`useFirstName()`, `greeting()` in `lib.ts`) personalises the home subtitle (time-of-day greeting) and the Random pick subtitle; everything falls back to the plain text when it isn't set. Names are not in the export file.
- **Password change** (`PUT /api/account/password`, `routes/account.ts`, `changePassword` in `services/users.ts`; `changePasswordSchema`): needs the current password and a new one meeting the usual rules (different from the current). A wrong current password is a 400 with `details` on `currentPassword` (not a 401, which the web client treats as signed out) and counts against the shared login failure limiter under key `password|<userId>` (5 per 15 minutes, then 429). On success the hash is replaced and every _other_ session of the user is deleted in the same transaction; the requesting session stays. The Account page has a Password panel (current, new, confirm; the confirm check is client-side).
- **Account deletion** (`DELETE /api/account` with `{password}`, `deleteAccount` in `services/users.ts`): re-checks the password (wrong = 400 with `details` on `password`, counted by the same limiter as the password change) and deletes the `users` row; every table that belongs to the user (entries and everything under them, lists, wishlist, tags, smart lists, avatar, sessions) goes through `ON DELETE cascade`, and `test/delete-account.test.ts` checks that no table keeps a row for them and that other users are untouched. The shared game cache stays. The session cookie is cleared and the web client sets `me` to null, which drops it on the login page. The Account page's red Delete account panel asks for the password, then a `useConfirm` danger dialog, and links to the export page first. Anything new that is keyed by `user_id` must cascade, or this breaks.
- **Badges** (`ProfileDto.badge`, `profileBadge` in `services/users.ts`, web `ProfileBadge`): a pill beside the name in the profile hero. `founder` goes to the account whose id equals the `FOUNDER_USER_ID` environment setting (`config.founderUserId`, a positive integer, anything else is ignored; set in `.env` and passed through `compose.yaml`; the id is in the URL of the user's page under Admin > Users). It is tied to the id, not the email, because email isn't verified and ids are never reused (autoincrement), so deleting the founder account can't hand the badge to whoever registers that address next. `staff` goes to every other admin (`role = 'admin'`); founder wins when one account is both. Only the badge name reaches the client. Not shown on share cards or the header identity.
- **Bio** (`users.bio`, optional; `bioSchema`/`BIO_MAX` = 160 in shared): a one-line tagline under the name on the public profile. `PUT /api/account/bio {bio}` trims, collapses all whitespace (newlines too) to single spaces, refuses control characters and anything over 160 characters, and stores empty as null; it is on `UserDto.bio` and `ProfileDto.bio`, and always public once set (free text, not moderated; React escapes it). The Account page has a "Bio" panel with a character counter. Not in the export file. When the signed-in viewer is the profile's owner, the hero shows "Copy link" and "Edit profile" (`/account`) instead of the signup call to action.
- **Gaming accounts** (`users.steam_id`, `xbox_gamertag`, `psn_id`, `discord_name`, all optional; `social.ts` in shared): `PUT /api/account/social` takes `{steam, xbox, playstation, discord}` (`socialLinksSchema`: trimmed, leading `@` dropped, empty = unset, and a strict pattern per service because the values end up in links on a public page; failures are a 400 with per-field `details`). They are on `UserDto.socialLinks` and always on `ProfileDto.socialLinks` (there is no per-account visibility: filling one in publishes it, and the Account form says so). `socialUrl` builds the link: Steam `steamcommunity.com/id/<name>` (or `/profiles/<id64>` for a 17-digit id), Xbox `account.xbox.com/en-us/profile?gamertag=`, PlayStation `profile.playstation.com/<id>` (Sony's own profile page), values URL-encoded; Discord has no profile URL by name, so it is a copy-to-clipboard chip. `SocialLinksList` renders the chips (external links `rel="noopener noreferrer"`, brand glyphs from Simple Icons) under the name in the profile hero. Not in the export file.
- **Logout** (`POST /api/auth/logout`) deletes the session row and clears the cookie. `GET /api/auth/me` backs the web app's `useMe()` gate.
- **CSRF**: see the origin/content-type guard under Request flow.

## IGDB communication

All IGDB access is server-side; the browser never talks to IGDB or sees credentials. Code is in `apps/server/src/igdb/`, behind the `IgdbClient` interface (`search`, `fetchGame`, `fetchReleaseDates`, `fetchGameSeries`, `fetchSeries`, `fetchSimilarGames`, `fetchPlatforms`) so tests inject a fake. If `IGDB_CLIENT_ID` / `IGDB_CLIENT_SECRET` are unset, `igdb` is undefined and IGDB-backed endpoints return 503 (`requireIgdb`).

- **Token** (`token.ts`): Twitch client-credentials flow (`id.twitch.tv/oauth2/token`). The token is cached in memory and refreshed an hour before expiry; concurrent callers share one refresh. A 401 from IGDB invalidates it and retries once.
- **Rate limiting** (`limiter.ts`): every request goes through `RequestLimiter`, a queue that starts at most 4 requests per rolling second with at most 8 in flight (IGDB's documented limits). A 429 response is retried up to 3 times, honouring `Retry-After`.
- **Requests** (`client.ts`): POST to `https://api.igdb.com/v4/<endpoint>` with `Client-ID` and bearer headers, APICalypse bodies (user text escaped by `quote`).
    - `search`: `games` endpoint, text search with `version_parent = null` (drops editions), limit 30, then filtered by `isCollectable` and cut to 20.
    - `fetchGame`: one `/multiquery` combining the game and its `game_time_to_beats` row (seconds).
    - `fetchGames`: the same for up to 100 games per `/multiquery` (imports); ids IGDB doesn't know are left out.
    - `fetchReleaseDates`: `first_release_date` plus per-platform `release_dates` for up to 100 ids per request, used only by the release refresh below.
    - `fetchGameSeries`: `collections` of up to 100 games per request, for the backfill below.
    - `fetchSeries`: one collection's name plus its games limited to `SERIES_GAME_TYPES` (Main Game, Standalone Expansion, Remake, Remaster; `version_parent = null`), up to 500, with release dates and covers.
    - `fetchSimilarGames`: the game's `similar_games` expanded in one `games` request (name, release date, cover, rating, type, `version_parent`), with add-ons and editions dropped by `mapSimilarGames`.
    - `fetchPlatforms`: the full platform list.
- **Mapping** (`mappers.ts`): raw IGDB shapes become `GameRecord` / `IgdbSearchHit`. Only add-on game types are excluded (`EXCLUDED_TYPES`: DLC, Mod, Pack / Addon); see the comment there before changing it. Covers are kept as `image_id` only and turned into URLs by `packages/shared/src/igdb-images.ts`.
- **Game page** (`routes/EntryPage.tsx`, `routes/GameDetailPage.tsx`, `components/GameHero.tsx`, web only): a hero with the cover blurred and enlarged behind it (the cover's own colours, no extra request or server work; a typographic gradient when there is no cover), the cover, a status chip with year and genres, the title, and facts that have data behind them (IGDB score ring with its tier in words, IGDB time to beat "normally", the platforms you own it on; a fact with no data is left out, and there are no sessions or progress). Under the facts: **one contextual primary button** (`primaryAction` in `statusMoves.ts`: Start playing for Not Started, Resume for Paused, Mark finished for Playing, Play again for Finished and Abandoned), "Add to queue" / "On your queue" as a secondary toggle (hidden for a game being played), the favorite heart, a ••• menu (Ask about this game when AI is available, Remove from collection) and the **segmented status control** (`StatusControl`). Moving to another status uses `moveTo` (pure, tested against the shared status rules): start (a game on several platforms asks which one in place), start paused, pause, resume, the finish dialog, the abandon form, or logging a never-started game as abandoned; a status the app has no move to from here (Finished from Not Started, anything but Playing from Finished) is shown disabled with the reason in its tooltip. Below the hero two columns of about equal length: the game and where it sits (a description clamped to four lines with Read more, a row of all screenshots that opens the lightbox, the journal of the playthrough in progress, IGDB's time-to-beat breakdown, and Lists and "I own it on" as panels that stay shut until opened) and your own record (Your take: rating and notes; My tags; Playthroughs, which stays folded until there is one). Similar games is a full-width section below both, so the columns stay even whether or not a game has any. The old Status panel and the phone's pinned action bar (`EntryActionBar`) are gone; the hero's button is the same action. The not-owned page uses the same hero with Add to collection and the wishlist toggle and no status control.
- **Collection page** (`routes/CollectionPage.tsx`, web only): everything lives in the address (`?status=&platform=&genre=&series=&tag=&favorite=true&sort=&q=`), so a view can be linked and Back works. **Tabs** (`StatusTabs`, `collectionModel.ts`): All, Playing, Paused, Finished, Abandoned, Not Started (`unplayed`) and Wishlist, each with a count from `GET /entries/facet-counts` (the server counts every status with the other filters applied, so All is their sum; the wishlist count is its own query). Wishlist is a list, not a status: its tab renders `WishlistTab` (the old wishlist page's content) and sends no `status` to the entries API. `/backlog` and `/wishlist` are redirects to `?status=unplayed` and `?status=wishlist`. **Filter bar** (`FilterBar`): Platform, Genre, Series (only series with two or more games) and My tags as chip menus with counts (a menu with one option is hidden unless something is selected in it), a Favorites toggle, accent-outlined active chips with a clear button, Clear filters, and the sort (Recently added is the default and is left out of the address; Title, IGDB score, Release date, My rating, Time to beat). **Density** (`DensityToggle`, `useDensity`): Wall, Grid or List, remembered in `localStorage` per user (`gq.collection.density.<userId>`, an earlier browser-wide list choice is honoured); the default is Wall on desktop and Grid on touch screens and below 768 px, where a saved Wall is drawn as the Grid (and the Wall option is hidden) without losing the choice. The Wall (`WallTile`) is art only, 150 px minimum columns with a 1px seam (`--wall-seam` on `.wall`, 0 for none), a 4px status-colour bar that never hides, and on `:hover` and `:focus-within` the title, platform, status and a quick action (Start, Continue, Resume, Play again; plus a + for the queue when the game is neither queued nor being played). The tile is a link and the actions are a sibling layer, never nested in it; the actions' hooks only mount on first hover or focus. A game with no cover gets its name as typography on a gradient. The Grid (`CollectionCard`) shows a status chip on every cover, then the title and one meta line (`entryMetaParts`: platforms, then hours logged / time to beat / finish year, then your rating; hours only when the journal recorded some). The list (`CollectionRow`) shows everything on one row. Pages of 96 (48 in the list) load as the end of the list scrolls near (`LoadMore auto`), with the button kept for keyboard users; covers are lazy. Measured with a seeded 2,024-game library: first paint under a second, and 60 fps scrolling in Wall and Grid (the Wall does not use `content-visibility`: it measurably made scrolling worse).
- **Global search** (web only, no new routes; `api/search.ts`, `searchModel.ts`, `recentSearches.ts`, `components/CommandPalette.tsx`, `routes/SearchPage.tsx`, `components/QuickAddSheet.tsx`, `components/SearchRows.tsx`): one search over the user's library (`GET /api/entries?q=`, title match, 25 results) and IGDB (`GET /api/igdb/search`, below), both cached per query for five minutes in TanStack Query, so a repeated query never reaches IGDB again, and each with its own loading state (the library answers first, the IGDB group fills in below). `buildResults` (pure, tested) merges them into the two groups both screens show (an IGDB game already in the library is not offered again; its library row is the one to open) and applies the scope (All / In library / Add new / one platform). Desktop and tablet (>= 768 px): **⌘K / Ctrl+K** from anywhere, or `/` when not typing, or the sidebar and top-bar buttons, open the palette (`Shell` owns the shortcuts and `SearchContext.openSearch`): groups In your library, Actions for the highlighted game (Start playing or Resume; Add to queue; `⌘/Ctrl+Enter` and `Shift+Enter` run them; a game on several platforms is sent to its page, which asks which), Add from IGDB. Arrow keys move, Enter opens, **Tab quick-adds** the highlighted IGDB game as Not Started on the platform the user added last (`defaultPlatformIds`), with the row updating in place and an inline Undo (a modal dialog makes the rest of the page inert, so the palette cannot use a toast). With no query it lists the last searches and page jumps. Phones (< 768 px): `/search` is the page: landing (library count, big field, last five searches per user in `localStorage` as `gq.recent-searches.<userId>` with Clear and an arrow that fills the field without running the search, "Jump back in" covers of playing games and the top of the queue), results (field with Cancel, a scope chip row with counts and the user's platforms, 80 px rows with highlighted matches, the IGDB score and a status chip or a round + button; the list scrolls on its own above the keyboard, sized with `visualViewport`, blurs the keyboard when dragged, fades at its bottom edge; typing is debounced 250 ms, starts at two characters, shows skeleton rows), and the quick-add bottom sheet (platform chips from the game's IGDB platforms, "Add it as" Play now / Up next / Not started / Wishlist, primary button label follows the choice, "View full details"). `useQuickAdd` does the writes with existing endpoints only: Play now is `POST /entries` with `status: playing` and today's date, Up next adds the entry then `POST /queue/items`, Not started is a plain add, Wishlist is `POST /wishlist/items`; after it the sheet closes, the query and results stay where they were with the row showing its new status (the search queries are only marked stale, `useInvalidateQuietly`), and a toast offers Undo (`useUndoQuickAdd`: deletes the entry, or leaves the wishlist, and puts a game that was wishlisted back on it). The Collection page no longer has a title search box (`?q=` in the address still filters).
- **Search flow** (`routes/igdb.ts`): `GET /api/igdb/search?q=` checks a 5-minute, 200-entry `TtlCache` keyed by lowercased query, otherwise calls IGDB. The result is then annotated per user with the `entryId` of already-collected games and a `wishlisted` flag (never cached, since both are per user).
- **Similar games** (`GET /api/igdb/games/:igdbId/similar`, `similarGames` in `services/similar.ts`, `SimilarGames` component on `EntryPage` and `GameDetailPage`): IGDB's curated `similar_games` for a game, best rated first (unrated last), at most 12, never the game itself. The IGDB list is kept 6 hours in a per-process `TtlCache` (nothing in the database, so it is never stale for long and needs no migration); the user's `entryId` / `wishlisted` marks are added on every request. A separate endpoint and query, so IGDB can't delay the page; a skeleton panel shows meanwhile, and the panel is hidden when IGDB lists none or the request fails. Cards link to the game's own page when owned, otherwise to the IGDB-id page where it can be added or wishlisted. Not in the export file.
- **Discover** (`GET /api/discover`, `PUT|DELETE /api/discover/dismissed/:igdbId`, `services/discover.ts`, `DiscoverPage`, "Discover" in the sidebar's Explore group): suggestions built from the same cached similar-game lists as the game pages (one `similarCache` per app, shared by both routers). Seeds are the user's loved games: favorites first, then entries rated 4+, newest change first, at most 20 (`MAX_SEEDS`). A candidate scores one point per seed whose list contains it, IGDB rating breaks ties; owned, wishlisted and dismissed games are removed. The response has `picks` (top 12, each with up to three `becauseOf` seed names and its `seedMatches`) and `rows` (up to 6 seeds, each with its own best 8, "Because you loved X"). Lookups run in parallel through the IGDB limiter and are cached 6 hours, so the first visit costs up to 20 requests and later ones none; a failed seed is skipped (error kind `discover_lookup`), and only if every lookup fails does the request fail. Cards link to the IGDB-id page and carry a Wishlist button (which also drops the card, since wishlisted games are hidden) and a "Not interested" button that writes `dismissed_games`; the page offers Undo for the last dismissal. With no loved games the page explains how to get suggestions; its skeleton is a grid of card placeholders. Dismissals are permanent until undone, and there is no page yet for reviewing them.
- **Game by id** (`GET /api/igdb/games/:igdbId`): `ensureGame` (so IGDB is called only for a game never cached, one multiquery) then the cached `GameDto` plus the user's `entryId` and `wishlisted` (`GameDetailDto`). Viewing a game therefore caches it in the shared `games` table even if it is never added; ownership lives in `entries`, so nothing treats a cached game as owned.
- **Adding a game** (`addEntry` -> `ensureGame` in `services/games.ts`): if the game isn't in the shared `games` table, `fetchGame` is called and `saveGame` writes it and its relations; cached metadata is not re-fetched on the live path, with one exception: release dates (below); when a mirror exists the mirror sync (below) overwrites it instead. IGDB failures are wrapped by `callIgdb` as 502. The entry is then created with the chosen platforms, and tags default to the game's genres and themes. `AddEntryInput` may also carry `status: 'paused' | 'abandoned'` (default unplayed) for games with prior history: `paused` inserts an open playthrough started on `date` (client's local day, else UTC today) and `abandoned` a closed one with unknown dates, in the same transaction. The playthrough platform is set only when a single platform was chosen. The add dialog's platform step has an "Add as" select for this (Not Started, Playing, Paused or Abandoned; `playing` also records a `started` event).
- **Platforms** (`listPlatforms`): `GET /api/igdb/platforms` serves the platform table, doing a one-time full sync from IGDB when it holds fewer than 50 rows (only games' own platforms so far).
- **Import** looks up uncached games with `fetchGames` (100 per multiquery) and never writes the file's own metadata to the cache (see Export/import).
- **Mirror** (`apps/server/src/mirror/`; reasoning and open items in `IGDB_MIRROR.md`): a local copy of the IGDB data the app uses, rebuilt from IGDB's partner data dumps (`GET /v4/dumps`, `GET /v4/dumps/{endpoint}` -> short-lived `s3_url`; daily CSVs, no webhooks) by `npm run igdb:mirror [-- --force]` (`dist/mirror/cli.js` in production), which cron runs daily through `scripts/mirror.sh`. It lives in its own SQLite file (`IGDB_MIRROR_PATH`, default `./data/igdb.db`; set it next to `DATABASE_PATH` in Docker), never in the user database, so it needs no backup. The server answers from it through `createMirrorIgdbClient` (below); the `games` cache table and the background jobs on top are unchanged.
    - **Build** (`build.ts`): each CSV is streamed from HTTP through `csv-parse` straight into SQLite, nothing is written to disk first. Small lookups (`platforms`, `genres`, `themes`, `collections`, `game_types`) load directly; `covers`, `screenshots`, `game_time_to_beats`, `release_dates` and `alternative_names` go into a scratch `<file>.staging` database that only feeds `games` and the search index; `games` goes last, then the FTS5 index. Release precision uses the same `releaseFromFormats` as the live mapper, and the add-on filter is the live `isCollectable`, so both sources agree.
    - **Bulk-load settings** (`configureForBulkLoad`): the build turns the rollback journal and fsync off on both databases (a rebuild is thrown away if it dies) and the file is fsynced once before it replaces the old mirror (`syncToDisk` in `run.ts`, plus the directory), so a power cut can't leave a damaged mirror in place. Two traps found on the first run on a Pi's microSD card: better-sqlite3 silently refuses `journal_mode = OFF` unless the connection is in `unsafeMode`, and a pragma without a schema name only reaches databases attached at that moment, so the scratch database had been fsyncing every commit; on a microSD card that stalled for seconds (a 1 MB dump took 16 s). A failed step also no longer hides its error behind a failing `ROLLBACK`.
    - **Retries** (`dumps.ts`, `job.ts`, `errors.ts`): two levels. Each HTTP request to IGDB (the dump list, a dump's download URL, the file itself) is tried up to three times, after 1 s and then 4 s, on a network error, a 408, a 429 or a 5xx. The whole build is tried up to three times (`BUILD_RETRY_MS`: waits of 1 and 5 minutes), from scratch, when it fails for a transient reason such as a download that breaks off midway; nothing from a failed try survives. A `PermanentMirrorError` is never retried: missing credentials, a client secret Twitch refuses (a 4xx from the token request, `TokenError.status`), a 4xx from IGDB other than 408/429 (401, 403, 404), too little free disk, a dump IGDB doesn't list, and a build rejected as too small, shrunk or with an incomplete index. `MirrorRunDto.attempts` records how many tries a run took, shown on the admin page. A worst case on a Pi is about 3 x 2.5 min plus 6 min of waiting, well inside the healthchecks.io grace time.
    - **Schema** (`schema.ts`, version 2; a file with another version is ignored): `games` carries the `GameRecord` fields (cover image id, first six screenshot image ids as JSON, rating, type, time to beat, `similar_games` as a JSON id list) plus `is_edition` and `searchable`. Every game is kept (a user may own an edition or add-on and game pages look up by id); only `searchable` ones (no edition, no add-on type) are in `games_fts`, a contentless FTS5 table over `name` and `alt` (alternative names such as "FF7"), both with apostrophes removed. Platforms, genres, themes and series are lookup tables with `game_*` join tables. `meta` records the schema version, the dump it came from and the build time.
    - **Run** (`run.ts`): skips when the `games` dump is the one the file was built from (`--force` overrides), builds into `<file>.new`, runs `verifyMirror` (integrity check, at least 100,000 games, no more than a 20% drop from the current file, FTS row count equals the searchable count), then renames it into place. A failed or rejected build leaves the old mirror untouched. Measured against the live dumps: about 50 s on a Mac and 155 s on a Raspberry Pi (8 GB, microSD), 251 MB, 383,734 games of which 338,811 searchable.
    - **Lookup** (`client.ts`, `reader.ts`): `createMirrorIgdbClient({path, fallback})` implements `IgdbClient`. `index.ts` wraps the live client with it when `IGDB_CLIENT_ID`/`SECRET` are set or the mirror file exists, so with neither the app behaves as before. `MirrorHandle` re-checks the file's inode/size/mtime every 5 s and switches to a newly renamed file (or starts using one built after boot) without a restart. Every method answers from the mirror first and asks the live client only for what is missing: `fetchGame`, `fetchScreenshots`, `fetchSeries` and `fetchSimilarGames` when the game or series isn't in the mirror, `fetchReleaseDates` and `fetchGameSeries` for just the unknown ids, `search` when there is no local hit (which also covers typos, since IGDB's search is typo-tolerant) or nothing searchable in the text. `status` and `ping` belong to the live client, so the admin IGDB page reports the live connection only. Differences from live IGDB: platforms come in id order, not IGDB's order; a game whose only release date is TBD has no year in search; ratings are as of the last dump.
    - **Daily job** (`mirror/job.ts`, `mirror/cli.ts`, `mirror/status.ts`, `scripts/mirror.sh`): `runMirrorJob` wraps `runMirror` and writes `mirror-status.json` (`MirrorRunDto`, next to the mirror file, so in `/data`) after every run: `ok`, `result` (`built` or `current`), `dump`, `seconds`, the error text on failure, and `lastSuccessAt` carried over a failed run. Before a build (not when the dump is current) `assertFreeSpace` requires 1 GiB free on the data disk (`MIN_FREE_BYTES`; measured peak is about 570 MB with the old file still in place), so a full disk fails early with a clear message instead of mid-import. `cli.ts` is thin wiring (missing credentials are reported as a failed run too) and exits 1 on failure. `scripts/mirror.sh` is the cron entry on the host: it runs `docker compose run --rm --no-deps -T gamequeue node dist/mirror/cli.js "$@"` (a throw-away container sharing `./data`, so it works while the app restarts and stays out of the web process), takes an `flock` where available, and pings healthchecks.io (`HEALTHCHECK_MIRROR_URL`, read by name from `.env`): `/start`, then success with the last output line or `/fail` with the last five. The image sets `IGDB_MIRROR_PATH=/data/igdb.db`. Schedule: 06:30 UTC daily (the dump is complete by about 06:01); the run is idempotent and takes seconds when nothing changed, so the exact time and daylight-saving drift don't matter (DEPLOYMENT.md, IGDB mirror).
    - **Lookup counters** (`lookups()` on the mirror client, `MirrorLookupsDto`, the Lookups panel on `AdminMirrorPage`): per kind of lookup (search, game details, similar games, series pages, series of a game, screenshots, release dates, platform list) the client counts whether the mirror answered it alone (`local`, a miss without a live client included) or the live client had to be asked (`live`, even for just some of the ids). They are in memory and start again when the server restarts, `ping` and `status` aren't lookups, and `getMirrorStatus` adds the totals. This is how to check that game requests really hit the mirror.
    - **Admin** (`GET /api/admin/mirror`, `services/mirror-status.ts`, `MirrorStatusDto` and `mirrorHealth` in shared, `MirrorTile` on `/admin`, `AdminMirrorPage` at `/admin/mirror`): combines the file's own `meta` table (games, built time, dump, with the dump's time parsed from the epoch in its name), the last run, and which dump the cached games were last synced from. `mirrorHealth` is `failed` (last run not ok), `stale` (no success for 36 h, or a file the job never reported on), `missing` (last run ok but no readable file), `never`, else `healthy`. The job can't write to the database, so the server reads its status file on the same 10-minute tick as the cache sync and records a failed run once in `error_events` (`job_mirror_build`, via `reportMirrorRunFailure`; the log entry only, because the owner email alert needs 5 errors of one kind in 10 minutes and a daily job produces one, so email for this job comes from healthchecks.io).
    - **Cache sync** (`services/mirror-sync.ts`): the shared `games` cache is a snapshot, so it would otherwise go stale. `syncFromMirrorIfNew` runs at startup and every 10 minutes (`MIRROR_SYNC_CHECK_MS`) and does nothing unless the mirror's `dump` differs from the one stored in `settings` (`igdb_mirror_synced_dump`). A sync calls `saveGame(..., {overwrite: true})` for every cached game the mirror has (name, summary, dates and precision, cover, screenshots, ratings, type, time to beat, and exactly the mirror's platforms, genres, themes and series), upserts the platform list, and rewrites the member list of every series page already cached (`saveSeriesMembers`). Games the mirror lacks are left alone. It works in batches of 200 per transaction, yields to the event loop between them, and asks `igdb.local()` for the current reader before each batch because a rebuilt file may replace (and close) the old one in between. A failure is recorded as `job_mirror_sync` and retried on the next tick; the dump is marked synced only after a full run. Measured on a copy of a real dev database: 216 games and 4 series pages in about 0.3 s. User data (entries, ratings, notes, playthroughs) is never touched, and the sync does not change `entries.updated_at`.
    - **Old lazy jobs** (`refreshReleaseDates`, `backfillSeries`, `ensureScreenshots`, the weekly series refresh) are unchanged. They read through the same client, so for mirrored games they are free, and for games newer than the dump they still reach live IGDB.
    - **Search ranking** (`ftsQuery`, `ftsPhrases`, the `search` statement): every typed word must match in the name or an alternative name, the last as a prefix; a sequel number also matches its Roman numeral (2-20, whole token, so "vii" never pulls in "viii"); apostrophes are ignored. Results are ordered by `igdb_rating_count + 1`, times 20 when the name equals what was typed (punctuation-normalized, so "half life" is "Half-Life"), times 1 when the typed words appear side by side in the name, 0.3 when only in an alternative name, 0.1 when merely present somewhere. IGDB's own ranking was not the target: it puts "Cyberpunk Sex" before Cyberpunk 2077. Warm queries take 1-80 ms on a Mac; the first query after a restart touches the index cold and can take about 1.5 s.
